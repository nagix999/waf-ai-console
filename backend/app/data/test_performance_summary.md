# 테스트 처리 성능 집계

`평가 → 테스트 → 테스트 선택 → 통계 요약`의 **처리 시간과 출력**에서 선택한 문항 전체를 집계합니다. 난이도와 유형, 집계 전 필터 및 답안 기준을 적용합니다. 필드별 집계의 검색, 정렬과 페이지 변경은 성능 집계 범위를 바꾸지 않습니다.

## 표시 항목

| 항목 | 계산 기준 |
| --- | --- |
| 결과 준비 시간 | 접수부터 분석과 필요한 근거 정리 작업이 끝날 때까지 |
| 접수 → 판정 완료 | 접수부터 서버 판정 완료까지. 초기 대기 포함 |
| 초기 대기 | 접수부터 첫 분석 시작까지 |
| 처리 시간 | 분석 시작부터 판정 처리 종료까지. 앞선 접수 대기는 제외 |
| P50 | 측정값의 중앙값. 일반적인 문항의 처리 시간을 확인 |
| P95 / P99 | 측정값을 정렬했을 때 95% / 99% 위치에 있는 시간. 오래 걸리는 문항의 지연을 확인 |
| 첫 호출 시간과 출력 토큰 | 역할의 최초 출력 시도 기록 |
| 전체 출력 토큰 | 같은 문항의 해당 역할에서 출력 재시도, 원문 교정 및 기록된 조건부 근거 재검토까지 합산 |
| 재시도 문항 | 해당 역할에서 출력 재시도가 한 번 이상 기록된 문항 |
| 출력 재시도 시간 | 첫 시도 이후 출력 교정 시도의 시간 합계 |
| 원문 교정 시간 | 근거 출처를 교정하는 후속 호출의 시간 |
| 근거 재검토 | 출처 교정 후 남은 근거로 판정을 다시 검토한 문항 수와 평균 시간. 해당 문항이 있을 때만 표시 |
| 모델 대기 | 서버의 동시 호출 슬롯을 기다린 시간 |
| 근거 정리 대기와 처리 | 판정 이후 별도로 진행하는 정리 작업의 시간 |
| 오류 사유 | 저장된 출력 검증 오류를 항목과 유형별로 집계 |

각 평균과 P50/P95/P99는 해당 측정값이 있는 문항으로 계산합니다. 미기록은 0으로 채우지 않습니다. 토큰 합계는 모든 시도의 사용량이 기록된 문항만 포함하며, 일부 시도의 사용량이 없으면 그 문항의 총량은 미기록입니다. 첫 출력량과 전체 출력량의 기록 문항 수가 다르면 두 평균의 차이를 재시도 출력량으로 해석할 수 없습니다. 출력 검증 실패, 출력 한도 초과 및 응답 시간 초과는 시도 횟수로 구분합니다. 한 문항에서 여러 오류가 나올 수 있으므로 오류 사유별 건수의 합계는 재시도 문항 수와 다를 수 있습니다.

단계별 시간과 재시도 시간은 서로 포함되거나 병렬로 겹칩니다. 이들을 더해서 전체 시간이라고 해석하면 안 됩니다. 모델 시도 시간에는 통신과 출력 검증이 포함되므로 순수 GPU 생성 시간이 아닙니다. 이 집계만으로 출력 토큰 증가가 지연의 원인이라고 확정하지 않습니다.

실패 항목을 재실행하면 문항별 결과와 같은 최신 실행을 사용합니다. 저장한 평가를 선택하면 해당 평가가 선택한 실행을 따릅니다. 이전 실패 실행과 새 성공 실행을 서로 다른 문항으로 중복 집계하지 않습니다. 처리 중인 문항에 남은 이전 실행 기록도 현재 실행 시간으로 섞지 않습니다.

P50은 짝수 표본에서 가운데 두 값의 평균이며, P95와 P99는 올림 순위 방식입니다. 평균과 백분위수 모두 같은 기록 문항만 사용합니다. 표본이 적으면 P99가 최댓값과 같을 수 있습니다.

## 관리자 조회 API

시간 카드의 평균과 P50/P95/P99에는 `completed_timings`를 사용합니다. `completed_cases` 중 각 측정값이 기록된 문항만 계산하고 실패, 중지와 처리 중인 문항은 제외합니다. 기존 `timings`는 호환성을 위해 그대로 보존하며 완료 문항 전용 통계로 표시하지 않습니다. 미기록은 0으로 채우지 않고 카드마다 기록 및 미기록 문항 수를 제공합니다. 분석 처리에는 초기 큐 대기를 제외한 내부 대기, 재시도와 복구가 포함됩니다. HTTP 요청부터 응답까지의 네트워크 시간은 별도로 측정하지 않습니다.

```http
POST /api/v1/test-runs/{run_id}/performance-summary
Content-Type: application/json
```

```json
{
  "reference_basis": "latest",
  "difficulty": "hard",
  "case_filter": null
}
```

기존 `TestReadScope`의 `evaluation_id`, `reference_basis`, `difficulty`, `test_category`, 각 미입력 필터와 `case_filter`를 사용합니다. 그룹 집계, 페이지 및 정렬 조건과 URL query parameter는 받지 않습니다. 관리자 인증이 필요하며 응답은 `Cache-Control: no-store`입니다. 서비스 API Key에 접근 권한을 추가하지 않습니다.

응답 버전은 `test-performance-summary-v1`입니다. `cases`, `statuses`, `timings`, `phases`, `roles`, `display`에 집계값을 제공합니다. 역할별 `tokens.first_attempt_output_tokens`와 `tokens.output_tokens`를 비교해 첫 답변 생성량과 재생성으로 늘어난 양을 구분할 수 있습니다. 문항별 원문이나 모델 출력, 암호문, 임의 오류 메시지는 반환하지 않습니다.

v2.31 조건부 재검토는 역할별 `decision_review_ms`, `reported_decision_reviews`, `cases_with_decision_reviews`로 구분합니다. 원문 교정 시간에는 재검토를 합치지 않으며 전체 시도와 토큰 및 대기에는 중복 없이 포함합니다. 호출 수와 문항 수를 구분하고, 과거 미기록은 0으로 추정하지 않습니다. `evidence_grounding_retry`의 인식 가능한 재검토 표식과 시도 기록이 있는 경우만 집계합니다. 이 추가는 관리자 통계 응답에만 적용하며 공개 분석 v3 필드는 바꾸지 않습니다.

성능 자료는 별도 요청으로 가져오므로 필드별 집계의 페이지나 정렬을 바꿀 때마다 다시 계산하지 않습니다. 선택 범위가 바뀌거나 다시 조회할 때 갱신하며, 진행 중인 분석과 근거 정리 작업은 화면이 보이는 동안 주기적으로 확인합니다.

테스트의 부모 화면에서 완료 건수가 바뀌어도 통계 요약과 처리 시간의 독립적인 조회 주기를 다시 시작하지 않습니다. 문항 접수가 열려 있으면 현재 필터에서 처리 중인 문항이 없어도 갱신하며, 종료 전환 시 마지막 값을 조회하고 멈춥니다. 같은 범위에서는 기존 표와 검색 초안, 펼침 및 스크롤 위치를 유지합니다. 같은 행의 키보드 포커스와 셀 컨트롤의 포커스 및 입력 커서도 보존하되, 사용자가 다른 곳으로 옮겼거나 행이 사라졌으면 복원하지 않습니다.

DB migration, 운영 의존성, 모델 호출 및 공개 분석 응답 v3 변경은 없습니다. 저장된 실행 수치와 허용된 오류 유형만 SQL에서 추출하며 원문 및 단계 이력을 복호화하지 않습니다.

## 운영 처리 시간

관리자 전용 `POST /api/v1/analyses/performance-summary`는 본문에 기존 `AnalysisFilters`를 받아 분석 이력의 전체 검색 범위에서 시간을 집계합니다. 운영 화면은 `analysis_purpose=production`을 지정합니다. 목록과 같은 키, 기간, 참고 판정 및 검색 조건을 적용하며 `limit`, `offset`, 정렬값은 집계 범위를 바꾸지 않습니다. query parameter와 미정의 필드는 거절합니다.

응답은 `version=analysis-performance-summary-v1`, `cases`, `statuses`, `completed_cases` 및 `completed_timings`입니다. 네 시간축과 완료 기준은 테스트와 같고 각 항목은 `recorded`, `unrecorded`, `reported_sum_ms`, `mean_ms`, `min_ms`, `p50_ms`, `p95_ms`, `p99_ms`, `max_ms`를 제공합니다. 실패와 처리 중인 분석은 완료 시간 분모에서 제외하며 결과 정리가 진행 중이면 결과 준비 시간만 미기록입니다. 원문과 모델 출력 및 암호화된 기록을 읽거나 복호화하지 않습니다.

기존 `GET /api/v1/admin/runtime/status`에도 해당 기간, 용도와 API 키 범위의 `completed_cases` 및 같은 `completed_timings`를 추가합니다. 이 범위는 분석 목록의 임의 검색 조건과 다릅니다. 호환 필드 `latency_summary`는 접수부터 완료 또는 실패 종료까지를 합친 기존 기준을 유지하므로 완료 문항 전용 시간 카드의 자료로 쓰지 않습니다. 두 API 모두 관리자 인증과 `Cache-Control: no-store`를 적용하며 서비스 API 키의 권한은 늘리지 않습니다.

운영 화면의 접힌 시간 통계는 요약 표시를 위한 최초 조회만 하고 5초 주기 조회는 하지 않습니다. 펼친 상태에서 처리 중인 분석이나 정리 작업이 있으면 주기적으로 갱신하고, 닫으면 중단합니다. 필터 변경과 명시적 새로고침 및 숨겨진 브라우저 탭에서 돌아올 때의 재조회는 유지합니다.

## 대량 범위와 갱신 부하

운영과 Runtime의 완료 시간 집계는 하나의 SQL 조회에서 필요한 시각과 상태만 읽습니다. `EvidenceDisplayJob.analysis_id`의 기존 unique 제약을 사용해 정리 작업을 연결하며 원문과 결과, 암호화된 단계 기록을 가져오지 않습니다. 조회 행은 1,024개 단위로 읽고 평균과 정확한 백분위수에 필요한 숫자만 보관합니다. 원본 행과 정리 작업의 전체 사본을 만들지는 않지만, 정확한 백분위수를 위한 수치 표본과 정렬 비용은 여전히 문항 수에 따라 늘어납니다. 큰 범위에서의 동시 운영 부하까지 보장하는 방식은 아닙니다.

합성 자료만으로 개선 전후를 비교하려면 다음 명령을 사용합니다. Python 3.12와 프로젝트 의존성이 설치된 검증 환경이 필요하며, `.env`나 운영 DB를 지정하지 않습니다.

```bash
cd backend
python scripts/benchmark_performance_summary.py --sizes 1000 10000 100000 --repetitions 2
```

이 도구는 임시 SQLite를 새로 만들고 읽기 전용 연결로 공통 시간 집계만 측정합니다. 같은 함수의 변경 전 구현과 독립적으로 계산한 합성 기대값을 함께 비교합니다. 출력 시간에는 메모리 측정 도구의 부하가 포함되므로 실제 HTTP 응답 시간이나 운영서버 처리 용량으로 해석하지 않습니다. Test의 역할별 출력과 토큰 집계, 임의 검색 필터의 SQL 비용은 별도입니다.

메모리 측정 부하 없이 시간을 비교하고 운영과 같은 CTE 구체화 방식을 적용하려면 `--wall-time-only --materialized-scope`를 추가합니다. 이 경우에도 원래 검색 조건의 비용까지 측정하는 것은 아닙니다.

2026-11-26 합성 1천/1만/10만 건, 변경 전후 각 2회로 측정한 12개 실행 모두 독립 기대값과 일치했습니다. 10만 건에서 SQL은 2회에서 1회, Python 할당 메모리 최고값은 약 90.5MiB에서 15.3MiB로 줄었습니다. 프로세스 전체 메모리나 운영 처리 용량을 나타내는 값은 아닙니다.

별도로 메모리 추적을 끄고 `MATERIALIZED` CTE를 적용한 12개 실행도 독립 기대값과 일치했습니다. 각 2회 중앙값은 다음과 같습니다. 공통 함수만 측정한 값이며 실제 필터와 HTTP 요청, 동시 조회의 지연을 뜻하지 않습니다.

| 합성 문항 수 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 1,000 | 319.70ms | 166.55ms |
| 10,000 | 1,125.60ms | 836.77ms |
| 100,000 | 13,145.44ms | 9,355.57ms |

10만 건에서는 약 28.8% 줄었지만 여전히 수 초가 걸립니다. 넓은 범위의 동시 조회나 실운영의 응답 시간 보장으로 확대 해석하지 않습니다.

## 완료 시간과 자동 갱신 보완 검증 (2026-11-26)

- 관련 backend 테스트 81개와 독립 합성 벤치마크 테스트 6개가 통과했습니다. 전체 backend 테스트 모음을 실행한 것은 아닙니다.
- 최종 frontend 테스트 865개와 production build가 통과했습니다. 기존 큰 번들 경고는 남아 있습니다.
- 실제 React 브라우저 검증에서 통계 화면의 DOM, 검색 초안, 펼침, 스크롤과 행 및 셀 포커스 보존을 확인했습니다. 범위 변경과 403 응답 시 이전 데이터를 제거하며, 종료 전환 후 마지막 조회 및 갱신 중단도 확인했습니다.
- 같은 합성 시나리오를 6.6초 관찰했을 때 부모 건수 변경으로 자식 집계를 다시 시작하던 각 조회는 3회에서 2회로 줄었습니다. 이는 특정 재현 조건의 중복 제거 확인이며 고정된 운영 감소율은 아닙니다. 운영 시간 통계의 접기와 펼치기에 따른 조회 중단 및 재개도 확인했습니다.
- 지표 펼치기와 접기 9개 조합(SK/Light/Dark, KR/EN, desktop/mobile)을 확인했습니다. 외부 요청, 실제 모델 호출 및 운영 데이터 사용은 없었습니다.
- 이번 보완은 DB migration과 공개 API 스키마, 모델 설정을 변경하지 않습니다. 실제 운영 동시 부하 검증과 재배포 및 Git 업로드는 수행하지 않았습니다.

## 최초 집계 도입 검증 기록

- 새 집계 관련 backend 테스트 14건과 기존 시간 진단, 실행 통계, 문항 필터 및 통계 내보내기 회귀 테스트 139건이 통과했습니다. 전체 backend 테스트 모음을 실행한 것은 아닙니다.
- 프런트엔드 전체 테스트 790건이 통과했고, 이후 추가한 출력 실패 유형 표시와 읽기 전용 조회의 갱신 처리 관련 테스트 11건도 통과했습니다. 두 실행은 중복 테스트를 포함하므로 합산하지 않습니다. 최종 production build도 통과했습니다.
- 실제 React 화면을 합성 API 응답으로 실행해 SK/Light/Dark, KR/EN, 모바일 넘침, 키보드 조회, 집계 범위 변경, 그룹 페이지 이동, 누락 및 오류 표시와 늦은 응답 차단을 확인했습니다. 브라우저 오류와 외부 요청은 없었으며 스크린샷 8장을 저장했습니다.
- 합성 508건에서 SQL 8회로 집계했습니다. 동시 테스트 부하에서 약 2~3.7초가 측정됐으며 운영 환경의 처리 시간 보장은 아닙니다.
- 기존 Starlette/AnyIO deprecation 경고와 프런트엔드의 큰 번들 경고는 남아 있습니다. 운영 DB 및 실제 모델을 사용한 검증, 서비스 재배포와 Git 업로드는 수행하지 않았습니다.
