# 역할 간 중복 근거 정리와 대표 응답

작성일: 2026-11-25. 시작 commit: `dca2cc2` (`Deploy current changes to main`).

## 목적과 범위

Primary와 Verifier가 같은 발췌에서 같은 논점을 설명하는데도 최종 근거에 반복되는 문제를 보완합니다. 새 정리 버전은 `evidence-display-editor-v3`, 저장된 표시 계획은 `evidence-display-plan-v2`, 관리자 표시 조회는 `evidence-display-view-v2`, 최종 응답 구성은 `core-evidence-v2`입니다. 공개 결과의 schema_version은 `waf-analysis-v3` 그대로입니다.

이번에는 원문 분할이나 파서, Primary/Verifier의 지침/출력 계약/독립성 및 최종 판정 정책을 바꾸지 않습니다. `confidence_score`와 별도의 확실성 등급은 묶기나 대표 선택의 조건으로 사용하지 않습니다. 실제 동작과 성립 조건, 반대 해석 및 관련 원문의 기여가 다른 경우는 여전히 별도 논점입니다.

## 처리 순서

1. 원본 결과와 관련 원문 관계를 기존 엄격한 저장 계약으로 검증합니다.
2. 동일 필드/발췌/확인된 실제 위치, 같은 supports와 같은 필수 관련 원문의 기여를 가진 번호를 정리 후보로 만듭니다. 위치가 없거나 서로 다른 위치를 같은 것으로 추정하지 않습니다.
3. 양 역할의 판단 조건 번호/소속 차이를 병합 금지 이유로 쓰지 않습니다. root와 role별 판단 조건 문장은 모두 정리 입력과 원문 해시에 연결합니다. 같은 역할만 포함한 후보에는 기존 판단 조건 소속 경계도 유지합니다.
4. 기존 근거 정리 호출 1회가 같은 관찰과 보안 의미를 반복하는지를 판단합니다. 대표 하나가 의미를 포괄하지 못하거나 실제 조건이 다르면 별도로 남깁니다. 새 설명/발췌/판정/심각도/필드는 생성하지 않습니다.
5. 서버는 각 묶음에서 실제 정책 판정 근거를 우선 보존하고, 그 범위에서 정리 모델이 추천한 기존 대표를 선택합니다. 정책에 사용되지 않은 설명을 새 정책 근거인 것처럼 바꾸지 않습니다.
6. 내부의 `원본 ID → 대표 ID` 대응표로 최종 응답 사본의 판단 조건 참조를 정리하고 중복 번호를 제거합니다. 필수 관련 근거는 대응표와 원래 관계를 따라 빠짐없이 포함합니다.
7. 원본/계획/대응표에 연결된 명시적 응답 타입을 검증하고 API에 반환합니다. UI, 보고서, PDF 및 Excel은 같은 선택 목록을 사용합니다.

같은 논점이 하나면 하나만 반환하고 숫자를 채우려고 구성원을 다시 추가하지 않습니다. 실제로 다른 논점이나 반대 근거가 여러 개면 여러 개 남습니다.

## 출처와 참조의 의미

선택된 개별 근거의 ID, 설명, 발췌, supports, source_spans와 origins는 원본 그대로입니다. 다른 모델의 origins를 합쳐 대표 문장의 작성자로 만들지 않습니다. 판단 조건의 문장과 missing_condition_ko 및 작성 역할도 원래대로입니다.

응답에서만 판단 조건은 동등한 대표를 참조할 수 있습니다. 예를 들어 Primary의 e1과 Verifier의 e2가 같은 논점이고 e1이 실제 정책 근거로 선택되면, 양쪽 판단 조건의 참조가 e1이 될 수 있습니다. Verifier 판단 조건의 작성 역할은 verifier이고 e1의 작성 출처는 primary 그대로입니다. 이는 Verifier가 Primary 문장을 작성했다는 뜻이 아닙니다.

역할별 evidence_ids는 선택된 근거 중 실제 해당 역할이 작성/기여한 번호의 교집합입니다. 따라서 Verifier 실행과 판정/판단 조건은 남지만 최종 대표가 Primary 항목뿐이면 verifier.output.evidence_ids는 빈 배열일 수 있습니다. 이 배열을 채우려고 가짜 작성 출처를 추가하지 않습니다.

API v3의 필드 구조가 같다는 것과 참조 의미까지 이전과 같다는 것은 다릅니다. 예전의 ‘판단 조건과 모든 참조 근거의 작성 역할 일치’ 조건은 최종 대표 응답에 한해 위의 대응표 검증으로 바뀝니다. 클라이언트가 이 이전 의미 규칙까지 별도로 검사한다면 함께 갱신해야 합니다. 기존 `X-Evidence-View` 헤더는 새 응답에 `core-v2`, 기존 응답에 `core-v1`을 반환합니다. result_version=v2 호환 응답도 검증된 typed 응답에서 명시적으로 변환하며 원본 계약을 느슨하게 읽지 않습니다.

## 저장 검증과 응답 검증

`AnalysisResultV3`, 원본 `AnalysisDetail`과 관리자 원본 조회의 저장 검증은 변경하지 않습니다. `CoreAnalysisResultV3`와 `CoreAnalysisDetail`은 응답에만 사용합니다. 원본을 엄격하게 검증한 뒤 유효한 계획과 대응표로 응답을 직접 구성하고, 완성된 응답 전체를 내부 증명 객체에 연결합니다.

검증되지 않은 사전, 변조된 모델 사본, 깊은 하위 값이 변경된 객체와 검증 없이 생성한 객체는 typed 응답을 가장할 수 없습니다. HTTP 응답 재검증에서도 확인하며 원본용 strict 검증을 전역으로 완화하거나 historical dict 분기로 우회하지 않습니다. 원문 해시/계획/대응표는 출처와 연결의 무결성을 검사할 뿐, 두 문장이 의미적으로 동등하다는 사실을 코드로 증명하는 것은 아닙니다. 의미 판단의 품질은 모델 평가 대상입니다.

## 실패와 진단

정리 비활성, 이전 버전, 실패 또는 훼손된 계획에 새 대응표를 적용하지 않습니다. 새 응답 구성에 문제가 있으면 기존 보수적 선택 경로로 복귀합니다. 선택 단계에서 추가 모델 호출이나 분석 재실행을 하지 않고, 정리 오류가 완료된 분석의 판정이나 성공 상태를 덮어쓰지 않습니다. 이 경로에서는 표현이 비슷한 중복이 남을 수 있습니다.

기존 정리 작업의 metadata에는 source_count/group_count 외에 returned_count, aliased_count, issue_reference_reduction, required_dependency_count와 projection_fallback을 기록합니다. 건수와 고정 상태만 남기며 원문, 해석 문장이나 원본 번호를 진단 로그에 출력하지 않습니다. 건수 계산 자체가 실패해도 정리 작업이나 분석을 실패시키지 않습니다. 새 페이지나 DB migration은 필요하지 않습니다.

일반 분석의 완료와 운영 승격 자격은 구분합니다. 새 버전은 대표 응답 검증의 실패/미확인 상태로 공식 평가와 승격을 통과하지 않습니다. 최종 응답 검사 상태를 확인할 수 없으면 먼저 이를 해소해야 하며, 암호화 자료를 검증하는 승격 검사에서는 실제 응답 구성도 다시 확인합니다. 진단값을 계산하지 못했다는 이유로 이미 완료한 분석을 실패로 바꾸거나 모델을 자동 재호출하지는 않습니다. 과거 정리 v1/v2에는 새 진단 필드를 요구하지 않습니다.

## 버전 보존과 적용

새 `app.worker_entrypoint_v233`은 이전 worker_runtime_v232의 분석 실행과 모델 검증을 재사용하고, 근거 정리 작업의 스케줄러만 새 facade로 연결합니다. Primary/Verifier의 prompt_version과 fixed_rules_version은 v2.32 그대로입니다. 이름 때문에 v2.33 판정 지침이 생긴 것으로 해석하지 않습니다.

기존 v2.32 실행의 177개 파일, 공통 지침과 정리 v1/v2 파일은 원래 해시를 보존합니다. 새 정리 artifact에는 정리 지침/계획/작업/응답 계약/선택기와 정리용 새 실행 파일을 고정합니다. 후보 구성 해시는 새 정리 버전을 포함하고, Production은 공식 테스트/승인 Ground Truth 평가/관리자 검토와 승격을 거친 버전만 선택합니다. 과거 승인, 대기 작업과 실패 재실행은 원래 정리 버전과 암호화 스냅샷을 유지합니다. 이전 계획을 새 의미로 소급해서 해석하지 않습니다.

최종 정리 artifact는 기존 고정 파일을 포함한 14개이며 SHA256은 `ae30d7cf17ef364fb3d7e9072ba5be14e05a000f2db29b0eb48c8b7d8d06bf82`입니다. 기존 177개 실행 파일 해시는 `11c5bd23b63ae871ed743295accfeb7b7f63a4aaa8c4eef9c7cec0a0b22e6c3f`, Primary/Verifier 지침 파일 해시는 `521e280c06b2ffbca6fd62175054858f4095bb872d76030af2bff58b7673ddaf`로 시작 상태와 같습니다. 정리용 지침만 1,018→1,078자로 바뀌며 기존 한 번의 호출과 1,024 출력 토큰 및 입력 예산은 유지합니다. 실제 토큰 수와 지연 효과를 측정한 것은 아닙니다.

이번 작업은 운영 데이터 조회/전송, 실제 LLM 호출, Production 설정 변경, Docker 재배포와 Git 업로드를 포함하지 않습니다. 새 패키지/운영 서비스 의존성도 없습니다.

## 검증

합성 데이터와 모의 provider 응답으로 다음을 확인합니다.

- 양 역할이 각자의 판단 조건을 갖는 같은 논점 4개가 대표 1개로 반환되고 필수 참조는 대표를 가리킴.
- 대표의 실제 작성 출처, 판단 조건 문장/작성 역할, 판정/심각도/요약 및 저장 원본 불변.
- 확신도 차이는 묶기 조건이 아니며 실제 다른 동작/조건/분류와 의존 원문의 기여 차이는 유지.
- 잘못된 번호/묶음, 원문 위치/해시 불일치, 변경된 typed 객체는 거부되거나 보수적 경로로 복귀.
- API POST/GET/by-event의 v3/v2 응답과 UI/보고서/PDF/Excel의 최종 근거 목록 일치.
- 과거 정리 버전과 177개 고정 실행 파일, 승인된 운영 구성 및 재실행 보존.
