# v2.38: 분류가 다른 근거의 연결 허용

## 범위

v2.36의 단일 근거 목록과 `related_evidence_ids`, 최대 5개 제한을 유지합니다. 연결된 근거의 `supports`에 `attack_request`와 `normal_request`가 함께 있다는 이유만으로 전체 출력을 거절하지 않습니다. 새 필드나 필수 LLM 단계, 출력 한도와 재시도 상한 변경은 없습니다.

`related_evidence_ids`는 해석에 실제로 필요한 원문 기여, 비교 또는 제약 정황입니다. 같은 주제라는 이유만으로 연결하지 않습니다. 반대 정황도 종합 해석에 필요할 수 있으며 분류 혼합만으로 `interpretation_conflict=true`, 추가 Verifier 또는 보류를 강제하지 않습니다.

## 설명과 최종 응답

Primary와 독립 Verifier가 각자 대표 근거의 `interpretation_ko`에 결합한 보안 의미와 판단 이유를 작성합니다. 기존 근거 정리 호출은 같은 분류와 실제 원문 및 필수 출처를 가진 중복 해석에서 기존 대표 설명을 선택합니다. 새 문장을 생성하거나 공격/정상 근거를 하나로 병합하지 않습니다.

최종 API는 선택된 대표 설명과 필요한 관련 원문, 중요한 반대 근거를 보존합니다. 화면, Markdown, PDF와 Excel도 같은 핵심 응답을 사용합니다. `waf-analysis-v3`의 필드와 타입은 바뀌지 않습니다. 관리자 전용 관계 기록과 표시 계획의 내부 버전만 달라집니다.

## 유지하는 검증

- 원문 후보와 실제 발췌, 위치 및 역할별 출처를 확인합니다.
- 없는 번호, 자기 참조와 모호한 참조를 허용하지 않습니다. 유효한 순환은 제한된 탐색으로 처리합니다.
- 필수 출처를 사용할 수 없으면 이에 의존한 해석도 사용할 수 없습니다. 다른 독립 근거와 중요한 반대 정황은 보존합니다.
- 시그니처와 등록 설명은 `context`로만 인용하며 확정 판정에는 같은 방향의 실제 요청 내용 근거가 필요합니다.
- 필요한 Verifier 실패와 두 역할의 최종 판정 불일치는 기존 보류 정책을 유지합니다.
- 관측만 있는 문장을 자동으로 공격/정상으로 분류하거나 서버가 분류를 뒤집지 않습니다.

## 버전과 적용

새 지침은 `waf-judgment-v2.38` / `waf-system-v2.38`, 실행 구현은 `evidence-pipeline-v18`, 관계는 `evidence-relations-v2`입니다. 입력은 기존 `agent-input-v4`와 `evidence-selection-v5`를 사용합니다. 근거 정리는 `evidence-display-editor-v4`, 표시 계획은 `evidence-display-plan-v3`, 읽기 뷰는 `evidence-display-view-v3`입니다. 실행 명령은 `app.worker_entrypoint_v238`입니다.

v2.36과 철회한 v2.37을 포함한 기존 237개 고정 실행 파일은 변경하지 않습니다. 이전 실행과 실패 재실행, 대기 작업은 당시 지침과 엔진으로 처리하고 과거 관계도 기존 규칙으로 읽습니다. 저장된 Test 프로필과 정책 ID는 변경하지 않지만 새 Test 접수는 새 후보 지침을 고정합니다. 비교하려면 기존 실패 항목 재실행이 아니라 새 테스트를 만드세요.

승인된 Production은 코드 배포로 자동 변경하지 않습니다. 승인된 Ground Truth 공식 테스트, 운영 반영 검토와 관리자 승격을 거칩니다. DB migration과 신규 운영 의존성은 없습니다. 이번 작업은 서비스 재배포나 Git 게시를 포함하지 않습니다.

## 검증과 한계

합성 입력으로 직접/간접/순환 혼합, 원문 누락과 의존 해석 제외, 최초 1회 출력 수락, Verifier 조건 유지, API와 내보내기의 근거 보존 및 과거 버전 해시를 검증합니다. 새 관계를 읽어도 반대 방향의 설명을 병합하지 않는지 frontend 회귀와 build로 확인합니다.

방향 혼합 검증 때문에 발생하던 재시도를 줄이는 변경입니다. 모델의 의미적 정확성이나 `length/max_tokens`, 다른 JSON 오류를 자동으로 해결하지 않습니다. 실제 Gemma의 성공률, 보류율과 처리시간 효과는 운영 데이터 및 유료 모델을 호출하지 않은 오프라인 검증만으로 보장할 수 없습니다.
