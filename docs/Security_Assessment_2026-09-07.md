# WAF AI Analysis Console 보안 점검 결과

점검일: 2026-09-07 · 대상 버전: 0.1.0 · 상태: 점검 및 보완조치 제안, 미조치

## 1. 결론

**현재 상태로 운영망에 공개하거나 실제 사내 로그를 추가 수집하는 것은 권고하지 않는다.** 관리자 비밀번호·세션 서명키·데이터 암호화키가 공개된 개발용 기본값과 같음을 현재 API 컨테이너에서 확인했다. 기본 서명키를 이용한 관리자 세션 생성은 격리된 합성 환경에서 재현했다. 실제 서비스에 위조 세션을 보내거나 데이터를 복호화하지는 않았다.

현재 공개 포트는 호스트 loopback인 `127.0.0.1:18000`과 `127.0.0.1:18080`이다. 인터넷에 직접 노출됐다는 뜻은 아니지만, 로컬 접근자나 향후 프록시·운영망 공개를 통해 접근하는 주체에 대해서는 문제가 남는다. 침해사고 발생 여부를 조사한 보고서는 아니다.

확인된 주요 문제 8건은 **CRITICAL 1건 / HIGH 3건 / MEDIUM 4건**으로 정리했다. 별도 운영 보강·조건부 항목은 이 건수에 포함하지 않았다. 등급은 이 프로젝트의 영향과 공격 전제에 대한 평가이며, 주통기 항목 중요도나 CVSS 점수와 동일하지 않다.

| ID | 위험도 | 확인된 문제 | 우선 보완조치 |
| --- | --- | --- | --- |
| F-01 | CRITICAL | 개발용 기본 비밀번호·세션 서명키 사용, 운영 기동 시 차단 없음 | 관리자 비밀번호와 세션키 교체, 기본값 기동 거부 |
| F-02 | HIGH | 개발용 기본 데이터 암호화키 사용, 안전한 키 전환 기능 부재 | 백업·복구 확인 후 버전별 키 처리와 재암호화 |
| F-03 | HIGH | 로그아웃·비밀번호 변경 후 복사된 세션 재사용 | 서버측 세션 폐기, 유휴·절대 만료 분리 |

| F-06 | MEDIUM | 인증 성공·실패·로그아웃의 애플리케이션 감사 누락 | 비밀값 없는 인증 감사와 탐지 |

| F-08 | MEDIUM | 전체 이벤트·파일 행 수·접수량·큐 상한 부족 | 입력 예산과 source별 접수 제한, 큐 backpressure |

## 2. 기준과 점검 범위

### 실제 수행한 범위

- 필수 문서와 관련 설계·코드 읽기. 안내된 `docs/WAF_AI_Analysis_Architecture_v0.1.md` 대신 실제 존재하는 루트의 동명 설계서를 확인했다.
- FastAPI 인증·권한·파일 접수·LLM 입력/출력·암호화·감사, React 보고서·키 표시, Nginx/Docker 설정 검토.
- 현재 프로젝트 컨테이너의 공개 포트·권한·자원 제한·패키지 버전·파일 모드 읽기.
- 실제 설정과 공개 기본값의 일치 여부만 출력. 비밀번호·키·쿠키·환경변수 원문은 출력하지 않음.
- 공개 페이지의 소수 GET 요청과 HTTP 헤더 확인. 운영 인증/변경 API는 호출하지 않음.
- 네트워크 없는 일회성 컨테이너, 합성 데이터 및 메모리 DB로 재현. 실제 LLM 호출·유료 검증·운영 DB 변경·대량 공격은 수행하지 않음.

이는 **프로젝트 범위의 1차 기술 점검**이다. 기반시설 전체의 공식 취약점 분석·평가 완료, 법적 적합성 또는 무취약성을 보증하지 않는다. GPU 운영서버·네트워크 장비·호스트 전체·실제 로그의 보관 및 반출 실태는 별도 확인 대상이다.

## 3. 주요 문제와 보완조치

### F-01. 개발용 기본 인증 비밀값 사용 — CRITICAL

**근거:** [config.py:14–20](../backend/app/config.py), [auth.py:11–20](../backend/app/api/auth.py), [security.py:22–30](../backend/app/security.py), [main.py:70–76](../backend/app/main.py), [docker-compose.yml:7–11](../docker-compose.yml).

실제 API 설정 검사에서 `default_admin_password=true`, `default_session_secret=true`였다. `environment=production`이어도 기본값을 거부하는 검증이 없다. 합성 환경에서는 공개 기본값으로 로그인할 수 있었고, 공개 서명키로 생성한 쿠키가 관리자 권한으로 인정됐다.

**영향/전제:** API에 도달할 수 있는 주체가 관리자 권한을 얻어 원문·Agent 이력을 조회하거나 프롬프트·공급자·서비스 키 설정을 변경할 수 있다. 현재 loopback 제한은 외부 도달 가능성을 줄이지만 인증 결함 자체를 제거하지 않는다. 코드 실행이나 실제 침해를 확인한 것은 아니다.

**보완:** 승인 후 관리자 비밀번호와 세션 서명키를 각각 충분한 난수로 교체한다. 세션키 교체는 기존 세션을 일괄 만료시킨다. 누락·공개 기본값·부적합 키이면 운영 API와 worker 기동을 거부하도록 한다. 공용 Compose의 기본 비밀값 fallback과 기본 전체 인터페이스 포트 공개도 안전한 배포 기준으로 변경한다.

**재점검:** 기본값 운영 기동 실패, 이전 비밀번호/서명키의 인증 거부, 새 자격증명 정상 동작. 실제 비밀값을 로그·테스트 결과에 출력하지 않는다.

### F-02. 공개된 데이터 암호화키와 키 전환 공백 — HIGH

**근거:** [config.py:20–21](../backend/app/config.py), [crypto.py:5–16](../backend/app/services/crypto.py), [models.py:104–105,165–167](../backend/app/models.py). 실제 API 설정에서 `default_encryption_key=true`였다.

**영향/전제:** DB 또는 백업을 확보하면 원문, Agent 입출력, 프롬프트 스냅샷 및 암호화된 공급자 API 키를 공개된 개발용 기본 암호화키로 복호화할 수 있다. DB 접근 자체를 원격으로 얻을 수 있다고 검증한 것은 아니다. SHA-256으로 저장한 서비스 API 키를 역산할 수 있다는 의미도 아니다.

버전 컬럼은 있지만 복호화 서비스는 현재 설정의 Fernet 키 하나만 사용한다. **환경변수의 암호화키만 즉시 바꾸면 기존 데이터와 공급자 키를 읽지 못한다.**

**보완 순서:** 보호된 일관성 백업과 복구 시험 → 구·신 키의 버전별 복호화/신규 쓰기 정책 → 기존 암호문 재암호화와 검증 → 새 키 전환. 기존 백업에 남은 암호문·평문 복사본 및 옛 키도 보호·보유·폐기 절차에 포함한다. 노출 범위에 따라 공급자 API 키 재발급도 별도 검토한다. 무단 삭제나 단순 키 덮어쓰기는 하지 않는다.

**재점검:** 원문·단계 입출력·프롬프트·공급자 키 각각의 구/신 데이터 읽기, 건수와 안전한 무결성 비교, 재시작·복구 시험. 이 작업은 데이터 이전 설계와 작업 시간 합의가 필요하다.

### F-03. 로그아웃 뒤에도 세션을 폐기하지 못함 — HIGH

**근거:** [auth.py:18–25](../backend/app/api/auth.py), [security.py:24](../backend/app/security.py), [main.py:70](../backend/app/main.py). 세션 ID와 폐기 상태를 서버에서 관리하지 않고 서명된 쿠키의 관리자 플래그를 신뢰한다.

합성 시험에서 로그아웃 후 브라우저 쿠키는 삭제됐지만 미리 복사한 쿠키로 인증이 다시 성공했다. 관리자 비밀번호를 변경한 뒤에도 같았다. 설정된 8시간은 최초 로그인 이후의 절대 만료가 아니라 응답으로 갱신되는 유효기간이다.

**영향/전제:** 쿠키가 먼저 탈취되었거나 기본 서명키 문제로 만들어진 경우 관리자 접근을 종료하기 어렵다. 기본키를 안전하게 바꾸어도 이 결함은 별도로 남는다.

**보완:** 불투명한 세션 ID와 서버측 폐기 상태, 로그아웃·비밀번호 변경 시 무효화, 유휴 시간과 절대 수명 분리. 긴급 전체 만료에는 서명키 교체를 사용할 수 있으나 개별 세션 폐기를 대체하지 않는다. 서버 세션 저장이 필요하면 DB 스키마 변경을 먼저 합의한다.

**재점검:** 로그아웃 직전 복사본, 비밀번호 변경 이전 세션, 절대 수명을 넘겨 계속 갱신한 세션이 모두 거부되는지 확인한다.

### F-04. 암호화한 원문의 일부가 결과에 평문으로 복제됨 — HIGH

**근거:** [worker.py:755–798](../backend/app/worker.py), [models.py:106,121–122](../backend/app/models.py), [analysis.py:66–76](../backend/app/services/analysis.py).

원문과 단계 출력은 암호화하지만 최종 결과 및 Primary/Verifier의 구조화 응답 전체를 `result_json`에 평문 저장한다. 원문 발췌와 모델 설명이 포함되며 `summary_ko`, `extra_fields`도 평문이다. 임의의 안전한 암호화키와 합성 Cookie를 사용한 모의 Agent 시험에서도 같은 발췌가 평문 결과에 남았다.

**영향/전제:** 민감 정보가 발췌·설명·추가 필드에 포함되면 DB/백업 읽기 권한만으로 원문 일부를 볼 수 있다. 실제 저장된 150건의 민감 정보 존재 여부는 읽어 확인하지 않았다. HIGH는 비마스킹 사내 로그를 다루는 용도의 기밀성 영향을 고려한 등급이다.

자기 source의 ingest 키가 결과의 발췌를 받는 것은 현재 문서화된 계약이다. 같은 키의 원문 API 접근은 403으로 차단됐다. 따라서 이 문제를 **서비스 키 권한 우회로 분류하지 않는다.**

**보완:** 마스킹 정책 변경 대신 민감 결과 본문·발췌·진단 출력과 원문을 포함할 수 있는 추가 필드를 암호화한다. 검색·필터에 필요한 허용 메타데이터만 분리한다. 과거 DB/WAL/백업 복사본 처리도 필요하다. API 반환 범위 변경이 필요하면 연동 계약과 별도로 합의한다.

**재점검:** 합성 민감 표식이 암호화 대상으로 지정한 평문 컬럼에 남지 않는지, 목록·검색·상세·보고서가 유지되는지 확인한다. F-02의 키 교체만으로 해결되지 않는다.

### F-05. 로그인 반복 시도 제한 없음 — MEDIUM

**근거:** [auth.py:11–20](../backend/app/api/auth.py). 합성 환경에서 실패 30회 모두 401이고, 직후 정상 로그인은 성공했다. 지연·429·잠금 상태가 없다. 현재 프로젝트 Nginx에도 로그인 속도 제한이 없다.

**영향/전제:** 로그인 경로 접근자가 추측 공격을 지속할 수 있다. 운영 상위 프록시의 별도 방어 여부는 미확인이다.

**보완:** 계정과 접속원 조합의 속도 제한, 점진적 지연, 짧은 잠금과 복구 절차를 둔다. 무기한 잠금으로 정상 관리자를 막는 역방향 서비스 거부도 고려한다. 서비스 키 접수 제한과 관리자 로그인 제한은 구분한다.

**재점검:** 임계치 이후 제한, 시간 경과 후 해제, 정상 관리자 복구, 신뢰 프록시 설정을 포함한 접속원 판별을 확인한다.

### F-06. 인증 감사 누락 — MEDIUM

**근거:** [auth.py:11–25](../backend/app/api/auth.py), [security.py:32–45](../backend/app/security.py), [models.py:221](../backend/app/models.py). 합성 로그인 성공·실패 30회·로그아웃 이후 인증 감사 레코드는 0건이었다.

현재 원문 열람과 설정 변경 감사는 있다. 일반 HTTP 접근 로그까지 없다는 뜻은 아니다. 다만 인증 사건을 조사할 접속원, 결과, 요청 상관 ID 등의 구조화 기록이 부족하다.

**보완:** 로그인 성공/실패, 로그아웃/세션 폐기, 권한 거부, 키 인증 실패를 안전하게 기록한다. 비밀번호·키·쿠키·payload·모델 본문은 넣지 않는다. 프록시 전달 IP는 신뢰 경계 검증 후 사용한다. 중앙 전송·보관·위변조 방지·경보·시간 동기화는 운영 담당자와 정한다.

**재점검:** 각 보안 사건의 기록과 연관 분석, 경보 동작, 합성 비밀 표식이 로그에 없는지 확인한다.

### F-07. 인증 전 업로드 처리 및 Starlette 취약점 — MEDIUM

**근거:** [analyses.py:309–340](../backend/app/api/analyses.py), [main.py:70](../backend/app/main.py), [nginx.conf:4](../frontend/nginx.conf). 실제 패키지는 FastAPI `0.115.8`, Starlette `0.45.3`, python-multipart `0.0.20`이다.

`UploadFile`을 만들기 위한 multipart 파싱이 인증 의존성 및 함수 내부 10 MiB 검사보다 먼저 수행된다. 합성 시험에서 업로드 한도를 1 KiB로 설정했어도 무인증 2 MiB 파일을 파싱하고 임시 디스크로 전환한 뒤 401을 반환했다. 인증 우회는 아니며 인증 전 자원 사용 문제다.

실제 Starlette 버전은 **CVE-2025-54121** 영향 범위다. 큰 파일의 디스크 전환에서 이벤트 루프가 일시적으로 차단될 수 있다. 공급자가 명시한 수정 버전은 `0.47.2`, CVSS는 5.3이다. 운영 장애 규모를 재현한 것은 아니다. [Starlette 공식 보안 공지](https://github.com/Kludex/starlette/security/advisories/GHSA-2c2j-9gv5-cj73).

**보완:** FastAPI와 호환되는 패치된 Starlette 조합으로 갱신한다. 특정 버전만 강제 설치하지 말고 의존성 호환성과 다른 공지도 함께 확인한다. ASGI 수신 누적 바이트를 파싱 전에 제한하고, multipart 처리 전 인증이 가능한 구조 및 연결·동시성 제한을 검토한다. Content-Length만 신뢰해서는 안 된다.

Nginx의 `client_max_body_size 11m`은 실제 방어다. 다만 API 직접 포트에는 그 프록시 제한이 적용되지 않으며, 11 MiB 이하에서도 spool 전환은 발생할 수 있다. 운영에서는 프록시 경유만 허용하는 방안도 병행한다.

**재점검:** 무인증·초과 크기·길이 미제공/잘못된 길이·분할 수신에 대해 파싱 이전 제한이 동작하는지, 정상 150건 업로드는 유지되는지 격리 환경에서 확인한다.

### F-08. 입력·접수량·큐 자원 한도 부족 — MEDIUM

**근거:** [schemas.py:21–63](../backend/app/schemas.py), [analysis.py:93–126](../backend/app/services/analysis.py), [analyses.py:347–368](../backend/app/api/analyses.py), [uploads.py:28–39](../backend/app/services/uploads.py).

payload는 제한하지만 signature와 확장 메타데이터를 포함한 이벤트 전체 크기·깊이, 파일 행 수, source별 접수량, pending 큐 상한은 별도로 제한하지 않는다. 합성 시험에서 payload 한도 1 KiB 조건에 signature/metadata 각 16 KiB를 넣은 33,052바이트 이벤트가 접수됐다. 10 MiB 파일 제한과 모델 입력 예산은 있지만 접수·저장·큐 예산을 대신하지 않는다.

**영향/전제:** 유효한 ingest 권한의 과도한 요청이나 수집기 오류가 메모리·DB·큐 및 외부 LLM 비용을 늘릴 수 있다. 실제 장애나 과금 증가는 시험하지 않았다.

**보완:** 전체 직렬화 크기·중첩 깊이·항목 수·필드 길이·업로드 행 수를 제한한다. source/키별 속도·일일 한도, 전역 큐 상한과 429/재시도 안내, 비용 예산을 분리한다. 합성 150건 선택 기능의 명시적 승인도 유지한다.

작은 비정상 파일에서도 예외 누락을 확인했다. 깊이 10,000의 JSON 20,001바이트는 `RecursionError`, 긴 CSV 필드는 `csv.Error`로 500이 된다. Unicode 로그인 자격증명도 [auth.py:14–15](../backend/app/api/auth.py)의 문자열 비교에서 500이 된다. 이들은 개별 LOW 오류 처리 문제이며 서비스 전체 중단 증거는 아니다. 파싱 전 한도와 비밀값 없는 413/422/401 응답으로 정리한다.

**재점검:** 경계값 입력, 정상/초과 파일, source별 제한과 큐 회복, 중복 접수 시 불필요한 비용/작업 증가가 없는지 검증한다.

## 4. 운영 보강 및 조건부 항목

다음은 설정 공백 또는 조건부 위험이며, 모두 공격 성공으로 확인된 것은 아니다.

| 항목 | 현재 관찰과 판단 | 보완 및 재점검 |
| --- | --- | --- |
| HTTP·Secure 쿠키 | 현재 loopback HTTP, `session_https_only=false`. 운영 중요 정보 전송에는 SN 기준 보완 필요 | 관리망/TLS 종료점·신뢰 프록시 확정 후 HTTPS와 Secure 쿠키. HTTPS 정착 후 HSTS 검토. 로컬 HTTP에서 Secure만 켜 로그인 장애를 만들지 않음 |
| 같은 site의 다른 origin | SameSite=strict·HttpOnly는 있음. Origin/CSRF 토큰 검사는 없음. 임의 Origin 요청 수용만 합성 확인했으며 브라우저 공격은 미재현 | 변경 API의 Origin 및 CSRF 방어, 같은 호스트의 다른 포트/형제 도메인에서 파일 접수·본문 없는 POST 시험. 일반 외부 사이트 CSRF가 성공한다고 단정하지 않음 |
| 프로세스·컨테이너 권한 | API 실행 UID 0, 세 백엔드 컨테이너에 사용자 지정 없음. 전체 컨테이너 rootfs 쓰기 가능, cap_drop 및 no-new-privileges 설정 없음 | 비root 실행·최소 capability·권한 상승 방지·읽기 전용 rootfs, 필요한 `/data`와 임시 경로만 쓰기 허용. SQLite WAL/마이그레이션 권한을 함께 검증. Nginx master와 worker 권한은 구분 |
| 컨테이너 자원·로그 | 컨테이너별 memory/CPU/PID 상한 없음. json-file 로그에 회전 옵션 없음 | 실측 후 CPU/메모리/PID·임시 공간 제한, 로그 회전·디스크 경보. 부하 시 다른 서비스 영향 확인. 무조건 작은 제한 적용은 피함 |
| DB 파일 권한 | `/data` 0755, DB/WAL/SHM 0644, root 소유. 해당 볼륨에 접근할 수 있는 다른 사용자에 대한 읽기 제한 부족 | 서비스 전용 UID/GID, 디렉터리 0700 또는 필요한 공유 그룹 0750, 파일 0600/0640 검토. 상위 호스트 경로/마운트 권한까지 확인. 모든 호스트 사용자가 읽을 수 있다고 단정하지 않음 |
| egress 네트워크 | 애플리케이션 allowlist는 있음. Docker bridge는 internal=false. 호스트 방화벽의 실제 목적지 제한은 미검증 | 등록 vLLM 및 승인 OpenAI 통신 정책을 네트워크 계층에서도 구현·시험. bridge 설정만으로 방화벽 부재를 확정하지 않음 |
| 헤더·캐시 | 공개 페이지 응답에 CSP/frame 제한/nosniff 등이 없고 `Server: nginx/1.27.5`를 노출. no-store는 서비스 키 API에 있고 일반 원문·Agent·결과 API에는 없음 | 서버 버전 노출 최소화, CSP Report-Only 검증 후 적용, frame 제한·nosniff·Referrer-Policy, 민감 응답 no-store 및 로그아웃 후 화면 정리. WEB-16은 서버 정보 노출에만 대응하며 CSP/캐시는 추가 점검. 실제 XSS/캐시 유출로 확정하지 않음 |
| Swagger 외부 자산 | `/docs` 비인증 공개, 관리 origin에서 jsDelivr의 Swagger JS/CSS 사용. 외부 favicon도 있음 | 문서 페이지를 제거할 필요는 없음. 접근 범위를 정하고 검토한 버전의 자산을 내부 제공, CSP 적용. 기능 공개와 관리자 API 인증 우회를 혼동하지 않음 |
| 개발용 Vite | `6.1.0`, dev script가 `--host 0.0.0.0`. 개발 서버가 접근 가능하게 실행될 때 알려진 파일 읽기 취약점 영향 | 지원되는 보안 수정 버전으로 갱신하고 loopback 기본값. 현 Docker 최종 이미지는 Nginx 정적 배포이므로 운영 취약점 건수에서 제외 |
| 이미지·의존성 관리 | 가변 이미지 태그 및 일부 오래된 고정 패키지 사용 | SBOM/잠금·digest·정기 재빌드·보안 공지 검토. 버전만으로 도달 불가능한 모듈 취약점을 확정하지 않음 |

Docker 최소권한·자원 분리는 가이드의 Docker 항목으로 위장하지 않고 [Docker 보안 문서](https://docs.docker.com/engine/security/)와 [자원 제한 문서](https://docs.docker.com/engine/containers/resource_constraints/)를 보조 기준으로 사용했다. `privileged=false`이고 Docker 소켓 마운트는 없었다. `security_opt`가 비어 있다고 기본 seccomp까지 없다는 뜻은 아니다.

Vite 개발 서버는 CVE-2026-39363의 영향 버전이다. 해당 결함의 수정 버전은 6.4.2/7.3.2/8.0.5이며, 실제 업그레이드 버전 선정 시 다른 공지도 확인해야 한다. [Vite 공식 공지](https://github.com/vitejs/vite/security/advisories/GHSA-p9ff-h696-f583). 실제 Nginx 1.27.5의 각 취약점은 HTTP/3·MP4·mail·SSL upstream 등 설정 전제를 확인해야 하므로 이번에는 특정 공격 가능성을 확정하지 않았다. [Nginx 공식 공지](https://nginx.org/en/security_advisories.html).

## 5. 확인된 보호조치와 미검증 범위

확인된 보호조치:

- 서비스 키는 256비트 난수와 SHA-256 단방향 저장, 일회 표시, no-store, source/scope 제한, 요청별 폐기 상태 확인을 사용한다. 사용자가 선택한 무기한 키 정책 자체를 취약점으로 세지 않았다.
- 환경변수 기반의 기존 배포 키 인증 경로는 제거되어 있다.
- 관리자 전용 원문·Agent 조회와 열람 감사, 서비스별 분석 조회·리뷰 범위 제한이 있다.
- 보고서·원문·디코딩 문자열을 React 텍스트로 표시하고 모델이 제시한 HTML·이미지·링크를 실행하지 않는다. API 키를 localStorage에 저장하지 않으며 테마 설정만 저장한다.
- vLLM 개별 내부 IP/포트 등록과 호출 직전 재검사, OpenAI 공식 HTTPS 주소/승인/TLS 검사, redirect·환경 프록시 차단이 있다.
- 디코더는 코드·JNDI·네트워크 조회를 실행하지 않고 처리량·깊이를 제한한다. 참고 답안 분리, 모델 입력 예산, 출력 계약과 근거 문자열 검증도 있다.
- 비공개 배포 폴더는 0700, 현재 compose/rollback 파일은 0600이었다. 프로젝트 루트 `.env`는 존재하지 않았다. 이 사실은 기본키 문제를 해결한 것으로 보지 않는다.

별도 확인이 필요한 범위:

- GPU 운영서버의 OS 계정/SSH/PAM, 패치, 방화벽, 시간 동기화, Docker daemon 접근권한과 커널 격리.
- vLLM 및 중간 프록시의 인증·TLS·payload/쿠키/모델 본문 로깅, 방화벽의 실제 차단 결과.
- OpenAI 실제 사내 데이터 반출 승인, 조직 정책과 보관 설정. 프로필 체크박스를 사내 승인 자체로 보지 않음.
- 외부 공격자가 프롬프트 인젝션으로 판정을 왜곡할 수 있는 정도. 스키마·근거 대조는 의미적 정확성이나 인젝션 저항성을 보장하지 않음.
- 정기 백업·복구, 암호화키 회전, 감사로그 중앙 보관·위변조 방지, 실제 운영 부하와 비용 제한.
- 전 의존성/기반 OS 패키지의 포괄적 CVE 스캔, 실제 브라우저 공격 및 침해 흔적 조사. 이번에 확인하지 않은 취약점을 없다고 판정하지 않음.

## 7. 권고하는 조치 순서

1. **즉시 승인 후:** loopback 제한을 유지하면서 관리자 비밀번호·세션키를 교체하고 기본값 기동 차단을 적용한다. 기존 세션 거부까지 확인한다. 데이터 암호화키는 이 단계에서 덮어쓰지 않는다.
2. **데이터 보호 설계 합의 후:** 키 전환·복구 시험과 평문 파생결과 암호화를 진행한다. DB 변경과 기존 백업 처리 범위를 먼저 설명한다.
3. **운영망 공개 전:** 서버측 세션 폐기, 로그인 제한·인증 감사, multipart 패치·수신 제한, TLS/CSRF/캐시, 비root·파일 권한·자원 한도를 검증한다.
4. **GPU 환경에서:** 네트워크 차단과 upstream 로깅, 합성 인젝션 평가, 운영 부하·비용·복구 시험을 수행한다. 실제 사내 로그 외부 전송은 별도 승인 없이 시험하지 않는다.

가장 작은 다음 단계는 **관리자 비밀번호·세션 서명키의 안전한 교체와 기존 세션 거부 확인**이다. 다른 기능을 추가하거나 데이터 암호화키를 즉시 변경할 필요는 없다. 본 점검에서는 어떠한 보완조치도 자동 적용하지 않았다.
