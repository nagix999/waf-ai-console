# 요청 입력 검사 v1

2026-09-11. [직전 150건 평가](evaluations/Context_Judgment_GPT54Mini_150_2026-09-10.md)에서 확인한 본문 누락·구조 문제를 정상 판정의 근거로 사용하는 문제에 대한 제한적 보완이다. **코드·오프라인 검증 범위이며 새 Docker 배포·지침 활성화·유료 LLM 평가는 하지 않았다.**

## 변경 내용

`request-integrity-v1`이 기존 HTTP 파서 결과와 원문을 로컬에서 검사한다. 원문을 복구·디코딩하거나 외부 자료를 조회하지 않는다. `generic-http-v3`의 `success` / `partial` / `failed` 의미와 원문 위치는 그대로 유지하며, 검사 결과는 별도로 기록한다.

| 검사 | 처리 |
|---|---|
| 서로 다른 Content-Length, 잘못된 길이 값 | 경계 정보 문제로 기록 |
| Transfer-Encoding과 Content-Length 동시 존재 | 경계 정보 충돌로 기록 |
| 길이를 선언했으나 본문이 없음 | 수집본의 본문 부재로 기록 |
| ASCII 본문이 선언한 길이보다 짧음 | 수집본의 길이 부족으로 기록 |
| 지원하는 chunked 형식의 종료·데이터 누락 | 수집본의 종료 구조 문제로 기록 |
| JSON 본문의 닫히지 않은 문자열·컨테이너 | 구조가 닫히지 않은 사실만 기록; 수집 손실로 단정하지 않음 |
| JSON 객체의 같은 키 반복 | 참고 관찰만 제공; 값 충돌·공격·보류로 자동 해석하지 않음 |
| 선언한 길이·chunked 끝 이후 추가 내용 | 참고 관찰만 제공; 파이프라이닝·수집 장식을 공격으로 단정하지 않음 |

동일한 길이 값의 반복과 같은 값의 쉼표 목록은 충돌로 처리하지 않는다. 길이는 원래 전송 바이트 기준이므로 Unicode 본문이나 Content-Encoding이 적용된 본문을 문자 수로 비교하지 않는다. WAF 수집 문자열은 네트워크 원본 바이트가 아니므로 ASCII 비교 결과도 수집본에 대한 관찰이다. HTTP 규칙은 [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)과 [§8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8)을 참고했다.

## 판정 반영 범위

새 공통 지침 `waf-system-v2.9` / `waf-judgment-v2.9`로 고정된 실행에만 적용한다. Production과 Test의 지침과 검사 규칙은 같다. 기존 편집 지침, 모델·출력 계약·원문 후보 선택·기존 Verifier 조건은 유지한다.

정상 판정(`false_positive`)의 원문 근거가 **확인된 누락·경계·JSON 미완결 구간과 겹칠 때**만 `input_integrity_requires_review` 조건으로 독립 Verifier를 요청한다. Primary의 출력은 수정하거나 Verifier에게 전달하지 않는다. 두 역할은 같은 실제 입력과 검사 결과를 받는다.

기존 결합을 마친 최종 정상 판정에도 같은 근거 구간 문제가 남으면 최종 결과를 `inconclusive` / `UNKNOWN`으로 제한하고 튜닝 제안을 비활성화한다. 기존 심각도 일관성·보류 신뢰도 상한을 따른다. 유효 원문 근거와 각 역할의 원래 판정·해석은 보존하며, 최종 요약과 마지막 추가 확인 사항에 수집본·길이 정보·실제 입력 형식을 확인하도록 안내한다. 모델 둘의 의견이 같아도 이 최종 제한은 적용될 수 있다.

관찰만으로 새 공격 판정을 생성하거나 공격 판정을 자동으로 보류시키지 않는다. 다른 온전한 구간에 근거를 둔 판정은 이 검사 때문에 바꾸지 않는다. JSON 중복 키·추가 바이트·업무 조건 미상·파싱 실패·검사 한도 초과 자체도 자동 보류 사유가 아니다. 공격 성공이나 HTTP 성공 응답을 판정의 필수 조건으로 요구하지 않는다.

이는 원문 위치를 이용한 보수적인 제한이지, 모델 해석의 의미를 검증한 것은 아니다. 같은 짧은 발췌가 여러 위치에 반복되고 `payload` 전체를 출처로 사용한 경우에는 영향을 받는 위치와 겹칠 수 있어 보수적으로 제한될 수 있다. 특정 문항·경로·시그니처·참고 답안에 맞춘 예외는 없다.

## 입력 예산·검사 한계

- 전체 원문 262,144자, 헤더 구간 32,768자를 넘으면 검사하지 않는다. 잘라낸 앞부분을 원문의 끝으로 간주하지 않는다.
- HTTP/1.0·1.1 요청이고 기존 파서가 `success`인 경우만 지원한다. `partial`/`failed`, 문자형 줄바꿈·포장된 로그·HTTP/2 덤프를 임의 재파싱하지 않는다.
- 길이 값 목록 32개 / 개별 128자, JSON 본문 65,536자 / 중첩 64단계로 제한한다. 매우 큰 길이 숫자는 임의 정밀도 연산 없이 현재 최대 수집 길이보다 큰 값으로 비교한다.
- chunked는 ASCII·CRLF, chunk 최대 1,024개, trailer 최대 32줄의 단순 형식만 검사한다. chunk 확장·미지원 전송 코딩·해석 불가 구문은 미지원으로 남긴다. 압축 해제와 전송 코딩 복원은 하지 않는다.
- 일반 텍스트·문서 안의 중괄호를 JSON으로 취급하지 않는다. JSON Content-Type의 객체·배열을 대상으로 하며, 구문 검사와 중복 키 관찰도 완전한 JSON/서버 처리 검증은 아니다.

검사 상태는 `not_checked`, `no_issue_observed`, `issues_observed`다. **미검사·문제 미발견은 완전한 요청이나 정상 요청의 증명이 아니다.** 부분 미지원과 한도는 `limitations`의 고정 코드로 남긴다.

모델 입력의 `request_integrity`는 최대 3,072자 또는 전체 문자 예산의 1/8 안에 들어간다. 검사 근거가 된 원문 구간이 전부 실제 제출된 경우에만 해당 관찰을 통째로 제공한다. 원문 또는 예산 때문에 관찰을 생략하면 `omitted_issues=true`이며 생략한 관찰은 서버 판정 제한에도 사용하지 않는다. 이로 인해 더 많은 원문이 생략될 가능성은 기존 `input_truncated`와 함께 확인해야 한다. 기존 문자 예산은 정확한 모델 tokenizer 한도 보장이 아니다.

OpenAI Docs의 [프롬프트 안내](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4)를 참고해 새 관찰의 해석·한계와 반대 조건만 공통 지침에 추가했다. 기본 Primary는 3,692→3,905자로 213자 늘었고 새 출력 필드는 요구하지 않는다. 문자 수를 실제 토큰 수나 품질 향상률로 표시하지 않는다.

## 이력·조회·호환성

parser 단계의 암호화된 출력에 검사 전체와 원문 위치를, agent_input 단계와 두 역할의 암호화 이력에 실제 제출한 검사 결과를 기록한다. 일반 metadata와 최종 `diagnostics.request_integrity`에는 버전·고정 사유 코드·생략 여부·최종 제한 여부만 남기며 필드 값·Cookie·예외 본문은 넣지 않는다. 새 전처리 버전은 `agent.preprocessors`에 추가하고 `agent.tools=[]`는 유지한다.

`diagnostics.input_signals`의 `input_integrity_observed`는 관찰 신호이고, `inconclusive_reasons`의 `input_integrity_limited`는 이 제한이 최종 정상 판정을 보류로 변경한 경우에만 기록한다. 모델이 먼저 보류하거나 기존 Verifier 결합으로 보류한 것을 새 제한의 효과로 세지 않는다. 설정 → Agent 설정 → 처리 현황에서도 두 건수를 구분한다. 과거 응답에 새 카운터가 없으면 값을 0으로 추정하지 않는다.

기존 v2.6은 이전 인용 계약, v2.7·v2.8은 이전 후보 선택 계약과 기존 입력을 유지하며 새 검사·판정 제한을 받지 않는다. 재실행·재선점 시 당시 고정 지침에 따라 적용한다. 기존 분석·필드 정의·답안·지침·모델 설정은 재작성하지 않는다. DB 마이그레이션·새 운영 의존성·모델별 전환은 없다.

## 검증

전체 백엔드 **1,757항목 통과**(611.06초), 관련 회귀 267항목 통과, 7개 문제 유형 × 3개 판정의 추가 제한 검사 21조합 통과를 확인했다. 프런트엔드 **29개 테스트 파일 통과**, Node 24.11.1에서 UI 빌드도 통과했다(98개 모듈, 8.47초). 백엔드에는 기존 Starlette/AnyIO 폐기 예정 경고 1건이 있다. 중단 전 전체 테스트의 종료 결과는 회수하지 못해 동일 Python 3.12.12 환경을 복구한 뒤 전체를 다시 검증했고, 종료 결과를 별도 XML로 보존했다. 모의 LLM과 임시 DB를 사용하며 실제 LLM 품질 검증과 구분한다. [집계·파일 해시·검증 소스 기록](evaluations/Request_Integrity_Offline_150_2026-09-11.json)을 함께 제공한다.

Medium을 포함한 기존 150건에는 참고 답안을 검사 로직에 전달하지 않고 구조 검사·입력 예산·원문 위치 검증을 적용했다. 기존 파일과 답안은 변경하지 않았다. 문항별 오프라인 예산 검사는 32,768 context / 출력 3,072 / 기본 예약 4,096과 후보 선택을 사용했으며, 실제 배포 프로필의 편집 지침·교정 예약·tokenizer 검증을 대신하지 않는다. worker 통합 검사는 실제 예약 계산과 두 역할의 동일 입력을 별도로 확인한다.

| 묶음 | 검사 미지원·한도 초과 | 관찰 없음 | 관찰 있음 |
|---|---:|---:|---:|
| 파싱 난이도 50건 | 41 | 8 | 1 |
| Hard 50건 | 0 | 44 | 6 |
| Medium 50건 | 0 | 49 | 1 |

관찰이 있는 8문항에서 9개 관찰이 나왔다. 정상 판정 제한 대상이 될 수 있는 코드가 나온 문항은 6건이며 모두 기존 참고 답안이 보류였다. **실제 모델의 새 판정·근거를 생성하거나 6건을 실제로 보류로 바꿨다는 뜻은 아니다.** 제한 적용에는 실제 제출 범위와 정상 판정의 근거 위치 조건이 추가로 필요하다. 파싱 난이도에서 41건은 새 검사가 지원하지 못하며 기존 파서·LLM 처리를 유지한다.

Medium의 소유권·업무 승인·서버 처리 정책 같은 미제공 환경 조건은 이 구조 검사로 해결하지 못한다. 기존 과탐·공격 보류와 Verifier의 의미 해석 문제도 별도 과제로 남는다. 실제 gpt-5.4-mini / Gemma4 재평가, 새 지침의 품질·지연·토큰 검증과 Docker 배포는 후속 단계다.
