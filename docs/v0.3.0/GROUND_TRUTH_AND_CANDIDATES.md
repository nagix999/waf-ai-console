# v0.3.0 기반 작업: 답안 승인과 테스트 구성 고정

2026-09-17. **개발 중인 기능 계약이며 v0.3.0 완료·배포 보고서가 아니다.** 실제 운영 DB·모델·지침·스키마·서비스 컨테이너는 변경하지 않는다.

## 1. Ground Truth 검토

데이터셋 문항의 답안(정탐/오탐/보류)과 검토 상태는 별도다.

| API 값 | 화면 | 의미 |
| --- | --- | --- |
| draft | 미검토 | 작성·가져오기·수정 직후. 답안은 없어도 됨 |
| reviewed | 검토 완료 | 입력과 답안을 확인함. 답안 필수 |
| approved | 승인됨 | 검토 완료된 답안을 공식 평가용으로 승인함. 답안 필수 |

상태는 미검토 → 검토 완료 → 승인됨 순서로 변경한다. 검토 완료·승인됨에서 미검토로 되돌릴 수 있다. 한 관리자가 검토와 승인을 모두 수행할 수 있지만 단계별 행위자와 시각은 보존한다.

- 항목 입력·답안·설명 수정은 항상 **새 미검토 revision**을 만든다.
- 상태 변경도 문항 revision과 데이터셋 revision을 새로 만들고 감사 기록을 남긴다. 기존 항목 행을 수정하지 않는다.
- 상태만 변경할 때 이벤트·스키마·답안 메모의 암호문과 암호화 키 버전은 그대로 복사한다.
- 과거 승인 버전, 이미 실행한 테스트의 membership·답안·평가는 바꾸지 않는다.
- 분석 결과의 참고 답안을 가져와도 미검토다. 동일 입력 재가져오기는 중복 처리이며 승인 상태를 자동 변경하지 않는다.
- 출처 종류, 원본 분석 연결, 모델 노출 여부, 가져온 답안의 ID·출처·작성자를 보존한다. 원본이 삭제되어도 사본은 유지한다. 과거 항목에 없던 출처 정보는 추측하여 채우지 않는다.
- 내부 전용 데이터는 수정·검토·승인으로 외부 모델 사용이 허용되지 않는다.

### 관리자 API

`POST /api/v1/validation-datasets/{dataset_id}/items/{item_id}/reviews`

```json
{
  "expected_revision": 7,
  "review_status": "reviewed"
}
```

`expected_revision`은 **데이터셋**의 현재 revision이다. 성공 시 `item`과 새 `revision`을 반환한다. 동일 상태 요청은 버전을 추가하지 않는다. 오래된 revision은 409, 답안 없는 검토 완료는 422, 미검토에서 바로 승인은 409다. 항목 생성·수정 API에 `review_status`를 끼워 넣는 요청은 거부한다.

`GET /api/v1/validation-datasets/{dataset_id}?review_status=approved&limit=50&offset=0`

- `total`: 선택한 데이터셋 버전 전체 문항 수
- `filtered_total`: 검토 상태 필터에 맞는 문항 수. 페이지 수 계산에 사용
- `review_counts`: 선택한 버전의 draft/reviewed/approved 개수
- `revision` 지정 조회는 당시 membership과 상태를 반환
- 항목 상세 `history`에는 revision별 검토 상태·기록자·시각 포함

현재 데이터 관리 화면에 상태 표시·필터·확인 후 검토/승인·과거 버전 읽기 전용을 연결했다. 미저장 수정이 있으면 승인 버튼을 사용할 수 없다.

## 2. 테스트 후보 구성 API

`POST /api/v1/test-runs`와 `POST /api/v1/validation-datasets/{id}/runs`의 최상위에 다음 선택 항목을 추가했다.

```json
{
  "candidate_configuration": {
    "primary_profile_id": "프로필 UUID",
    "verifier_profile_id": null,
    "evidence_editor_enabled": false,
    "evidence_editor_profile_id": null,
    "prompt_policy_version_id": "저장 지침 버전 UUID",
    "input_schema_version_id": "저장 스키마 버전 UUID"
  }
}
```

`POST /api/v1/test-runs/uploads`에서는 같은 객체를 JSON 문자열로 만든 multipart `candidate_configuration` 필드로 전송한다. 이벤트·CSV/JSON의 문항 내부에는 넣지 않는다.

- 지정하지 않으면 기존 Test 역할과 공통 활성 지침·스키마를 사용한다. 생략한 기존 요청의 재접수 키 의미도 유지한다.
- 직접 지정할 때 Primary·지침·스키마 ID가 필수다. Verifier가 null이면 Primary와 동일하다. 근거 정리를 켜고 프로필이 null이면 Primary와 동일하다.
- 비활성 저장 지침·스키마도 테스트할 수 있다. 저장 버전이 실제로 존재해야 한다.
- 모든 역할의 활성 상태·현재 설정으로 전체 검증 통과·내부 대상 허용·외부 전송 승인을 확인한다. Primary/Verifier는 선택 지침과 교정 요청을 담을 입력 공간도 확인한다.
- 내부 전용 데이터셋은 세 역할 모두 내부 vLLM이어야 한다.
- 명시적 후보는 moduagent 모드에서만 접수한다. stub으로 바꿔 실행한 뒤 실제 모델 평가인 것처럼 표시하지 않는다.
- 같은 재접수 키로 다른 후보 구성을 요청하면 409다. 동일 요청은 처음 접수한 실행을 반환한다.
- 후보 선택은 운영 역할, Test 기본 역할, 지침 활성 버전, 스키마 활성 버전, 동시 처리 설정을 변경하지 않는다.

### 저장과 실행

기존 TestRun의 암호화된 전체 지침·입력 스키마·근거 정리 지침을 재사용한다. 새 `configuration_snapshot_json`은 역할 프로필 ID와 지문, 지침·고정 규칙·스키마의 버전/지문, 근거 정리 활성 상태, Verifier 기준값만 보관한다. 원문·답안·필드 설명·API Key·지침 본문은 넣지 않는다.

`configuration_hash`는 이 정보의 정규화된 JSON에 대한 SHA-256이다. 테스트명이나 이벤트 내용이 달라도 같은 구성이면 같다. 실행 전 저장된 구성과 암호화 스냅샷의 정합성을 확인한다. 실행 시 선택된 모델에 대한 권한·설정 변경 검사도 유지한다. 새 TestRun 응답은 `configuration_snapshot`, `configuration_hash`를 제공한다.

과거 실행이나 stub에는 후보 구성 지문을 소급 생성하지 않는다. 과거 평가를 공식 평가로 승격한 것으로 간주하지 않는다.

## 3. DB 변경과 되돌리기

- `0019_ground_truth_review`: 문항 검토 상태 및 상태/답안 DB 제약, 원본 답안 출처 필드 추가. 기존 문항은 draft로 유지하며 내용·암호문·답안·membership은 변경하지 않는다.
- `0020_test_candidate_config`: TestRun의 nullable 구성 스냅샷·지문 추가. 기존 실행의 새 필드는 null로 유지한다.
- 새 설치의 현재 metadata와 기존 설치에서의 증분 이전을 모두 지원한다.
- 검토 이력·출처 정보 또는 후보 구성 기록이 생긴 후에는 해당 migration downgrade를 거부한다. 데이터 의미를 지우는 대신 **업그레이드 전 DB와 대응 암호화 키 백업**을 복구해야 한다.
- 이 작업에서는 가상 DB로만 upgrade/downgrade를 검증한다. 운영 DB에는 적용하지 않는다.

## 4. 아직 남은 범위

후속 작업에서 후보 선택 UI, approved만 고정하는 공식 평가, 결과 스냅샷, 동일 기준 비교를 추가했다. [공식 평가 계약](OFFICIAL_EVALUATIONS.md)에 API·화면·DB 변경을 정리했다. 승인했다고 기존 평가를 공식 평가로 표시하지 않는다.

다음 작업은 관리자 승인에 따른 운영 구성 일괄 승격이다. 승격 과정에서 기존 운영 기준 스냅샷·스키마 변경 비교·명시적 승인·동시 변경 차단·실패 시 전체 rollback을 구현한다. 기존 운영 직접 변경 API 제한도 이때 서버와 화면 모두 적용한다.

5개 메뉴·KR/EN·3개 테마·전체 세부 화면 정리·실제 worker 상태 기반 Runtime은 그다음이다. 버전 번호 변경·운영 이전·재배포·실제 LLM 평가·GitHub 게시·릴리스 태그는 수행하지 않았다.

## 5. 기반 작업 당시 검증 결과

실제 사내 로그 대신 가상 입력·프로필과 일회성 SQLite를 사용했다. 백엔드 검증 컨테이너는 네트워크를 차단하고 소스/테스트만 읽기 전용으로 연결했다. 모델 실행 테스트는 가짜 응답으로 검증했으며 외부 전송·유료 호출은 없다.

- 후보 구성·기존 Test 역할·Agent 역할·지침 스냅샷: 최종 **101개 통과**. 개별 항목에 정상 암호문이지만 다른 지침/스키마를 연결한 경우에도 호출 전에 차단함을 포함한다.
- 운영 키의 분석 삭제/사본 보존·실패 재실행·입력 스키마·테스트 비교: **105개 통과**.
- Ground Truth·후보 구성·마이그레이션·근거 정리 등의 확장 회귀: 112개 중 111개 통과 후 문서 경로 누락 1개 확인. 코드 변경 없이 검증 컨테이너에 문서 원본 경로를 연결하고 해당 스키마 통합 파일 **11개 전부 통과**. 위 검증 그룹 간 중복 항목이 있으므로 합계를 별도 전체 테스트 수로 표시하지 않는다.
- 프런트엔드 `node --test src/*.test.mjs`: **42개 테스트 파일 통과**.
- `npm run build`: 통과. 기존 500 kB 이상 번들 경고는 남아 있으며 전체 UI 전환 시 코드 분할 검토 대상이다.
- `node scripts/ground-truth-smoke.mjs`: 검토/승인 분리, 확인 절차, 이중 클릭 방지, 상태 필터, 과거 버전 읽기 전용, 미저장 편집 차단, 승인본 수정→미검토, 동시 수정 충돌, 390px 대화상자 확인. 실제 API/LLM 호출 0회. 이미 설치된 개발용 브라우저만 사용했고 운영 Chromium 의존성을 추가하지 않았다.
- 변경 파일의 공백 오류 검사 통과. 전체 백엔드 테스트 및 새 전체 화면의 KR/EN·3테마 시각 회귀는 아직 실행하지 않았다.
