# 판정 근거와 보류 설명 개선

후속 검증: 사용자 승인으로 gpt-5.4-mini 파싱/Hard/Medium 각 50건을 모두 실행했다. v2.8 대비 답안 일치 119→120건, 실패 0건, 근거 구분 기록 150건, 보류 쟁점 18/19건이다. 미탐 증가와 설명의 의미 오류가 남아 품질 개선을 보증하지 않는다. [실제 비교 결과](evaluations/Analyst_Assessment_GPT54Mini_150_2026-09-14.md)를 기준으로 남은 확인과 후속 우선순위를 판단한다. 아래 미검증 설명은 최초 구현 당시의 상태다.

작업 범위: 합의한 1~3단계(설명 누락 방지 → 근거 구분·판단 쟁점 기록 → 화면·보고서 반영). 최초 작업은 코드와 오프라인 검증 범위다. 이후 사용자 요청으로 [Docker 재배포와 화면 확인](Deployment_Analyst_Evidence_2026-09-14.md)을 완료했다. 실제 LLM 호출·Git 작업은 하지 않았다.

## 분석가에게 보이는 내용

화면 순서는 판정 요약 → 세부 분석 → 판정 근거 → 기타 정보 → 추가 확인 사항이다. 보류에서는 요약 안에 기록된 보류 이유와 ‘판단이 필요한 부분’, 관련 근거 번호를 함께 표시한다. 실제 미확인 조건이 기록된 경우에만 ‘아직 확인되지 않은 조건’을 추가한다.

| 표시 | 의미 |
| --- | --- |
| 정탐 근거 | 해당 해석이 공격 시도를 뒷받침함 |
| 오탐 근거 | 해당 해석이 정상 요청을 뒷받침함 |
| 참고 내용 | 어느 쪽의 근거로도 분류하지 않은 관찰 |
| 구분 미기록 | 분류를 기록하지 않았거나 지원하지 않는 값 |
| 로그 발췌 | 서버가 원문과 대조한 문자열 |
| 판단 이유 | 발췌에 대한 모델의 해석. 출처 대조가 해석의 정확성까지 보증하지 않음 |

정탐·오탐 근거는 데스크톱에서 나란히, 좁은 화면에서 세로로 표시한다. 동일한 출처·발췌를 다른 방향으로 해석하면 양쪽을 모두 남기고 같은 발췌의 근거 번호를 안내한다. 근거 개수로 최종 판정을 정하지 않는다. 한쪽에 근거가 없다고 반대 판정이 확정되는 것도 아니다.

실행 오류·원문 대조 오류가 보류 원인이면 그 원인을 먼저 설명하고 업무 쟁점을 보류 원인으로 표시하지 않는다. 보류의 세부 분석에는 확정된 공격·정상 결론이 아니라는 안내를 유지한다. `NONE`은 ‘해당 없음’, `UNKNOWN`은 ‘미확정’, 기술정보의 점수는 ‘판정 점수’로 표시한다. 점수는 모델 자기평가에 결합 정책을 적용한 참고값이지 실제 정탐 확률이 아니다.

Markdown 원본·보고서 보기·PDF·Excel에 같은 근거 분류와 판단 쟁점을 반영한다. PDF/Excel은 기존처럼 단건 상세 중심이며 HTTP 전체 원문과 Agent 입출력을 추가로 조회하지 않는다. 원문 발췌에 민감정보가 있을 수 있으므로 기존 다운로드 권한·감사·용량 제한을 유지한다.

## 새 실행의 계약

공통 시스템 지침은 `waf-system-v2.10`, 프롬프트는 `waf-judgment-v2.10/policy-N`이다. Test와 Production은 동일한 공통 지침을 쓴다. 저장된 관리자 편집 지침·역할별 모델 배정을 자동 변경하지 않는다.

새 메타데이터의 설명을 추가하면서 중복 문구와 신규 설치용 기본 편집 지침을 줄였다. 코드 기본 템플릿의 Primary 지침은 3,949자로 기존 3,950자 검사를 유지한다. 실제 실행은 저장된 편집 지침을 결합하므로 이 길이와 다를 수 있다. 문자 수는 모델 토큰 수나 성능 측정값이 아니다.

모델 내부 출력에 다음만 추가한다.

- 근거별 `supports`: `true_positive` / `false_positive` / `context`. 전체 판정에서 추정하지 않는다.
- `decision_issue`: `{point_ko, evidence_indexes, missing_condition_ko}` 또는 null. 핵심 구분점은 400자, 관련 근거 번호는 0~4의 최대 5개, 실제 미확인 조건은 최대 500자 또는 null이다. 확정 판정의 누락 조건은 서버에서도 null로 제한한다. 근거가 없는 쟁점은 만들지 않는다.

구조 오류 교정은 기존 횟수 제한 안에서 새 스키마의 필드·고정 오류 코드를 전달한다. 원문 인용 교정에서는 `source_id`만 바꾸며 분류·해석·판정을 다시 작성하지 않는다. 쟁점은 근거 인덱스로 연결되어 교정된 출처를 따라간다.

서버는 두 역할의 마지막 성공한 호출에서 원문 대조를 통과한 근거만 모아 `result.analyst_assessment`에 기록한다.

```json
{
  "version": "analyst-assessment-v1",
  "evidence": [{
    "evidence_id": "e1",
    "field": "payload.body",
    "excerpt": "code_verifier=fixture",
    "interpretation_ko": "인증 검증에 사용하는 요청 값입니다.",
    "supports": "false_positive",
    "origins": [{"role": "primary", "index": 0, "source_id": "c1"}]
  }],
  "decision_issues": [{
    "point_ko": "이 값이 인증 데이터인지 구문으로 해석되는지 구분해야 합니다.",
    "evidence_ids": ["e1"],
    "missing_condition_ko": "해당 필드의 허용 형식은 제공되지 않았습니다.",
    "origins": ["primary"]
  }],
  "omitted_issue_count": 0
}
```

예시는 가상 데이터이며 판단의 정답 예시가 아니다. 근거는 역할별 최대 5개, 합쳐 최대 10개다. 출처·발췌·해석·방향이 완전히 같은 경우만 합치고 역할·근거 번호는 추적 정보로 보존한다. 반대 방향이나 다른 해석을 문장 유사도로 제거하지 않는다. 실패한 호출, 거부된 발췌, 연결할 근거가 없는 쟁점은 화면용 기록에 넣지 않는다. 쟁점 연결 실패 건수는 `omitted_issue_count`에 기록한다. 이것만으로 새 보류를 만들지 않는다.

교정 전후의 원래 구조화 출력과 쟁점 정보는 기존 암호화 단계 이력에 남기며, 원문·해석을 로그나 단계 메타데이터에 추가하지 않는다. 최종 판정은 기존 `result.verdict`를 사용한다. 화면용 근거 분류가 별도의 판정이나 분석가 승인이라는 의미는 아니다.

## 유지하는 경계

- Primary → 조건부 독립 Verifier → 서버 최종 결합 구조와 보류 정책을 유지한다. Verifier에 Primary 출력이나 새 쟁점 정보를 전달하지 않는다.
- 기존 최종 `result.evidence` 최대 5개와 입력 검사 정책은 그대로다. 화면용 최대 10개 기록을 판정 정책의 입력으로 다시 넣지 않는다. 외부 소비자는 전체 분석가 근거를 표시하려면 새 확장 필드를 사용한다.
- 새 DB 마이그레이션, 운영 패키지, 추가 LLM 단계, 외부 평판 조회를 추가하지 않는다.
- 기존 결과는 재작성·재분류하지 않는다. 확장 필드가 없으면 기존 근거와 ‘구분이 기록되지 않았다’는 안내를 표시한다.
- v2.6~v2.9로 고정된 기존 접수·재실행은 당시 입력/출력 계약과 암호화 지침을 유지한다. 새 배포가 기존 대기 작업에 v2.10 출력을 강제하지 않는다.
- 이전의 내부 절차 안내는 완전히 일치하는 짧은 고정 문구만 표시에서 제외한다. `primary`, `verifier`, ‘불일치’ 등이 문장에 포함됐다는 이유로 내용을 삭제하지 않는다. `code_verifier`·`primary_email`·실제 비교 설명을 보존한다.

## 검증과 남은 확인

가상 입력과 가짜 HTTP 응답으로 다음을 검증한다: 양쪽 근거 10개 보존, 정확한 중복만 병합, 출처 교정 후 방향·쟁점 연결 유지, 실패/거부 근거 제외, 잘못된 쟁점 연결로 판정이 바뀌지 않음, 이전 지침 호환, moduagent의 vLLM/OpenAI 전송 스키마와 오류 교정, 웹/서버 공통 표시 사례, PDF/Excel 생성, 모바일 배치와 HTML 비실행.

2026-09-14 수행 결과:

- 네트워크 없는 임시 컨테이너의 전체 백엔드 실행: 1,807개 통과, 기본 지침 길이 제한 1개 실패. 제한을 완화하지 않고 문구를 줄인 후 해당 검사·고정 지침·접수·API 문서·새 계약을 포함한 168개 재검증이 전부 통과했다. 수정 후 전체 묶음을 한 번 더 실행한 것은 아니다.
- 새 근거·표시·보류 설명·출력 스키마 관련 별도 검증: 75개 통과. 실제 provider 요청은 가짜 HTTP 응답으로 대체했다.
- 프런트엔드 전체 32개 테스트 파일 통과. UI/보고서·기존 결과 호환·문서·탐색 회귀 포함.
- 실제 브라우저 14개 사례 통과: 데스크톱 밝은 화면과 모바일 어두운 화면, 양쪽 근거·보류·오류·오탐·보고서. API는 모두 가상 응답으로 대체했으며 외부 요청·실제 LLM 호출은 0회다.
- Vite 빌드 성공. 단일 JS 묶음 500 kB 초과 경고와 테스트 라이브러리의 기존 deprecated API 경고는 남아 있다. 이 작업에서 패키지 교체나 코드 분할을 추가하지 않았다.

실제 Gemma4/gpt-5.4-mini의 새 필드 작성률·해석 정확성·출력 실패율·토큰/시간은 아직 측정하지 않았다. 코드 테스트 통과를 보류율 또는 정확도 개선으로 해석하지 않는다. 다음 검증에서는 먼저 제한된 가상 사례로 새 계약의 작성 품질을 확인하고, 보류 감소와 함께 과탐·미탐·부적절한 확정이 늘지 않았는지 비교해야 한다. 기존 운영 로그를 외부 모델에 전송하지 않는다.
