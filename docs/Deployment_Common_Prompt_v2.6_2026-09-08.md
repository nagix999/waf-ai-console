## 배포 절차와 보존

기존 비공개 Compose를 복제하고 `services.*.image`만 변경했다. 새 이미지를 먼저 검증한 뒤 네 서비스를 중지했고, 대기·진행 중 분석/모델 검증이 없는 상태에서 SQLite backup API로 일관성 백업을 생성했다. 관리용 임시 컨테이너는 포트를 공개하지 않았으며, 새 이미지의 FastAPI TestClient를 통해 실제 관리자 인증·버전 생성(201)·revision 검증 활성화(200)·감사 기록을 수행했다. 별도의 SQL로 정책 본문이나 활성 선택을 강제 수정하지 않았다.

활성화 전에 API의 DB 경로가 백업 대상과 동일한지와 Production·Test 양쪽 프로필의 보수적 입력 예산을 확인했다. 두 용도에 지정된 프로필에서 입력 문자 예산 74,181자로 기존 최소 조건을 통과했으며 이는 실제 tokenizer 한도 검증이 아니다. 지침 적용이 끝나기 전 외부 접수·worker를 재개하지 않았다.

백업과 실제 DB를 활성 직후·재기동/HTTP 점검 후 대조했다. 기존 테이블·열과 모든 기존 행을 보존했고 다음 차이만 허용했다: 정책 버전 1개 추가, 공통 활성 상태·revision 변경, 정상 감사 이력 추가. DB는 `0012_input_schemas`를 유지하며 추가 마이그레이션은 없다.

## 빌드·점검 범위

의존성과 패키지 버전 목록을 이전 이미지와 동일하게 유지했다. 첫 오프라인 빌드는 런타임에 setuptools가 없어 실패했으며 서비스를 중지하기 전이었다. 로컬 setuptools 80.9.0 캐시를 별도 빌더 단계에서만 사용해 wheel을 만들고, 최종 이미지에는 `--no-deps --no-index`로 앱 wheel만 설치했다. 새 운영 의존성이나 외부 다운로드는 없다. 웹의 이전 해시 자산은 새 이미지의 정적 파일 레이어에서만 교체했고 이전 실행 이미지는 보존했다.

소스·배포 자료 83개와 새 모듈 import, 공통 지침 버전을 네트워크·운영 DB 없는 컨테이너에서 확인했다. 현재 소스·웹 산출물 manifest SHA-256은 `2fd1e8be8ee60a67b39e5807e1e8ad17c292d64aa1617b79aad4126567b0896d`이다. 과거 Git 커밋을 이번 변경 코드의 revision으로 표시하지 않는다.

실제 배포 HTTP 점검 **37개 통과**: 직접/프록시 health, HTML/JS/CSS의 현재 빌드 바이트 일치, 관리자 로그인·로그아웃, 미인증 401, 공통 시스템·활성 정책 본문/지문/revision, Production 문서·OpenAPI와 필드 정보 `history_only`, 기존 두 테스트의 읽기 전용 비교·동일 분모·페이지 조회를 확인했다. 초기 점검 스크립트가 UI fetch의 `cache: no-store`를 서버 응답 헤더로 잘못 기대한 부분은 실제 계약에 맞게 교정하고 재실행했다. 앱 코드는 이 점검 때문에 추가 변경하지 않았다.

앞선 코드 회귀(Backend 1,318개, Frontend 277개, 모의 브라우저 12개)는 [개발 검증 기록](Prompt_Optimization_and_Comparison_v0.2.0.md)을 따른다. 이번 배포에서 전체 회귀를 다시 실행한 것은 아니다. 실제 vLLM/OpenAI 추론·정확도·응답 속도, 새 분석 접수·150건 검증, 실제 배포 화면의 클릭 검증은 수행하지 않았다. 지침의 품질 상태는 계속 `not_evaluated`다.

## 로컬 복구 자료

현재 구성은 `.local-deploy/common-prompt-20260908-KtTSLB/compose.json`이다. 같은 폴더에 이전 구성·컨테이너 비공개 기준값, 소스 manifest, 단계별 보존·활성·HTTP 검사 결과가 있다. 인증·암호화 설정이 포함된 파일은 출력·공유·커밋하지 않는다. 상위 폴더 700, 비공개 구성·검사 파일·백업은 600 권한이다.

백업은 `pre-prompt-v26.db`, **0012**, 36,802,560 bytes이며 지침 활성 전 자료다. 이전 0011→0012 마이그레이션 백업과 구분한다. 기본 Compose 단독 실행, volume 삭제, DB downgrade·백업 덮어쓰기를 하지 않는다.

작성 지침 복귀는 관리자 API로 이전 버전을 활성화하는 별도 이력 변경이며 DB 복원이 아니다. 시스템 지침 v2.6의 복귀에는 코드 이미지도 별도로 고려해야 한다. 이미 접수된 작업은 당시 스냅샷을 계속 사용한다. 문제가 생기면 신규 접수·writer를 멈추고 현재 DB도 백업한 뒤 호환성·새 데이터 보존을 검토하며, 별도 승인 없이 이전 DB를 덮어쓰지 않는다.
