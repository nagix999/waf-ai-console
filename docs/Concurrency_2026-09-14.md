# 분석 동시 처리

아래는 구현 당시 코드·오프라인 검증 기록이다. [2026-09-14 로컬 배포](Deployment_Evidence_Editor_2026-09-14.md)에서 동시 처리 설정을 반영했으며 상한은 기존 기본값 1을 유지한다. 실제 GPU 처리량 검증이나 설정 증가는 하지 않았다.

## 설정

설정 → Agent 설정 → **동시 처리**에서 다음 값을 저장한다.

- 프로덕션 / 테스트 동시 분석 수: 각각 1~32건, 기본 1.
- 서버별 동시 호출 수: 주소·포트별 1~64회, 기본 1. 같은 서버의 여러 모델·프로필은 합산한다.

동시에 10건을 처리하려면 해당 용도의 분석 수와 사용하는 서버의 호출 상한을 모두 조정해야 한다. GPU 메모리·입력 길이·지연을 검증하지 않고 10을 권장 기본값으로 삼지는 않는다. vLLM 서버나 worker 컨테이너를 추가할 필요는 없다.

값을 높이면 이미 대기 중인 분석에도 다음 선점·호출부터 적용한다. 값을 낮춰도 진행 중인 작업·전송한 요청은 취소하지 않으며 완료 후 여유가 생겨야 다음 요청을 시작한다. 저장은 설정·감사 이력만 기록하지만 실행 중 worker가 대기 작업을 더 빨리 처리할 수 있고 OpenAI 비용 발생 속도도 달라질 수 있다.

모델 배정·프롬프트·판정 정책·기존 실행 스냅샷은 바꾸지 않는다. 동시 처리 상한은 재실행에도 현재 운영 설정을 적용하는 자원 제한이며 모델 선택을 바꾸는 설정이 아니다.

## 실행 범위

기존 동기 SQLAlchemy 파이프라인을 제한된 작업 풀에서 실행한다. 분석마다 별도 Session·소유권·갱신 처리를 갖는다. 한 worker 프로세스가 여러 분석을 실행하며, DB 전체의 유효한 작업 소유권을 집계해 여러 worker도 같은 용도별 상한을 지킨다. 테스트 대량 업로드가 프로덕션의 **분석 슬롯**을 차지하지 않게 선점 순서를 번갈아 처리한다. LLM 서버 슬롯은 공유하므로 운영 요청의 지연시간이나 엄격한 우선순위까지 보장하지 않는다.

일반 단건 테스트·배치 파일·운영 분석이 대상이다. 별도 model-test worker의 150건 후보 모델 검증은 기존의 문항별 순차 처리·재개 계약을 유지한다. 다만 후보 문항·연결 검증의 HTTP 요청도 같은 서버 상한에 포함한다. `test_concurrency`는 여전히 **연결 전체 검증 시 보내는 동시 요청 수**이며 일반 분석 수가 아니다. 서버 상한이 이 값보다 작으면 `concurrency_limit_below_test`로 검증을 중단한다. 두 설정 중 변경할 값을 관리자가 직접 선택한다. 검증 중에도 다른 요청·상한 변경에 따른 대기가 생길 수 있으므로 p95는 순수 GPU 처리시간이나 해당 동시성의 처리량 보장이 아니다.

각 분석의 Primary → 조건부 Verifier → 서버 판정 순서는 유지한다. Primary·Verifier·원문 인용 교정·출력 재시도는 같은 공통 호출 진입점을 사용한다. 후속 근거 정리 LLM도 이 진입점을 사용해야 하며 이 변경 자체가 근거 정리 역할을 활성화하지는 않는다.

## 호출 제한과 복구

`llm_call_slots`에는 무작위 슬롯 ID·서버 주소 키·만료 시각만 임시로 저장한다. payload·키·프롬프트는 넣지 않는다. 읽기에서 빈자리가 보이면 짧은 SQLite 쓰기 트랜잭션에서 상한을 다시 확인하고 예약한다. DB 쓰기 잠금을 유지한 채 모델 응답을 기다리지 않는다.

LLM 단계의 호출 슬롯은 순차 네트워크·출력 재시도가 끝날 때까지 보수적으로 유지한다. 슬롯 대기는 모델 실행 제한 시간 밖에서 처리하고, 대기 중에도 모델·외부 전송·작업 소유권 검사를 반복한다. 원문 인용 교정은 새 슬롯을 얻는다. 성공·예외·취소 시 반환하며 전체 로컬 실행 제한 시간보다 30초 뒤에 만료한다. worker가 강제 종료되면 만료 후 빈자리를 복구한다. 원격 vLLM/OpenAI가 연결 종료를 즉시 취소하는지는 보장할 수 없어, **물리적인 GPU 내부 실행 수의 절대 상한이 아니라 이 앱의 호출 예약 상한**이다.

새 단계 telemetry의 `concurrency.wait_ms`는 해당 호출 슬롯 대기 시간이다. 단계 전체 시간에는 이 대기가 포함된다. 재시도 등 전체 시간·토큰 합산 시 기존 시도별 이력과 중복 합산하지 않는다.

분석은 처리·호출 대기 중에도 lease를 갱신한다. 결과 쓰기와 새 호출에 소유권 검사를 적용해 재선점 후 이전 worker의 결과 덮어쓰기를 막는다. SIGTERM/SIGINT는 새 선점을 중단하고 진행 중인 작업을 마칠 때까지 기다린다. Compose의 종료 유예 시간을 넘겨 강제 종료되면 기존 lease 만료 복구를 따르며, 이미 보낸 모델 요청의 중복 과금을 완전히 배제하지는 못한다.

주소 키는 URL의 host·port로 구성하고 HTTP 기본 80/HTTPS 기본 443, IPv6 표기를 정규화한다. 경로·모델명·프로필 별칭을 바꿔 상한을 우회하지 않는다. 다른 IP나 프록시 주소가 실제로 같은 GPU를 가리키는지는 자동으로 알 수 없다. 별도 DB를 사용하는 다른 WAF 설치나 다른 앱의 vLLM 요청은 이 상한에 포함되지 않는다.

## API와 배포

- 관리자 전용 `GET /api/v1/admin/agent-settings/concurrency`: 설정·등록 서버·조회 시 처리 중 수.
- 관리자 전용 `PUT /api/v1/admin/agent-settings/concurrency`: `expected_state_token`, `production`, `test`, `servers[{server_key,max_calls}]`. 서버 목록은 등록 프로필에서 가져온 전체 목록이어야 하며 중복·임의 서버·잘못된 범위·오래된 상태 토큰은 거부한다.
- 기존 관리자 Origin/CSRF·감사 기록 정책을 유지한다. 프로필·모델 배정 API는 변경하지 않는다.

**Alembic `0015_concurrency`**로 `concurrency_configuration`, `llm_call_slots` 테이블을 추가한다. 기존 분석·Agent 설정·모델·검증 이력은 보존하고 새 패키지는 없다. 설정 변경 이력 또는 호출 슬롯이 남아 있는 downgrade는 거부한다.

배포 전 SQLite 일관성 백업과 암호화 키 복구 가능 여부를 확인한다. 모든 기존 worker·model-tester를 중지하고 마이그레이션 후 API와 모든 worker를 같은 코드 버전으로 교체한다. 구버전 worker가 함께 실행되면 새 상한을 우회하므로 혼용하지 않는다. 이번 개발에서 운영 DB 마이그레이션이나 재배포는 하지 않았다.

실제 Gemma4의 적정 동시 요청 수·처리량·GPU 메모리·429/timeout·장시간 장애 복구는 별도 운영 환경 검증이 필요하다.

## 검증 기록

- 전체 백엔드 회귀 1,922항목을 실행했다. 발견한 마이그레이션 중복 생성·공유 제한 미사용 경로의 요청 권한 검사 회귀를 수정하고 영향 범위 194항목을 재검증해 통과했다. 최종 코드로 전체 묶음을 다시 실행한 결과와 혼동하지 않는다.
- 추가 동시 처리 전용 19항목 통과: 단일 worker의 10건 파이프라인, 분리 프로세스 간 공통 상한, 실제 ModuAgent 직렬화와 모의 HTTP·연결 검증의 상한 공유, 대기 중 권한 해제, timeout/취소/만료 슬롯 반환, 소유권 상실 후 쓰기 차단, 실행 중 상한 변경과 종료 시 대기 작업 보존.
- 프런트엔드 전체 34개 테스트 파일·Vite 빌드 통과. 데스크톱/모바일 브라우저에서 설정 입력·범위 검사·초안 유지·확인/취소·저장·변경 충돌·새로고침과 가로 넘침을 점검했다. 브라우저는 임시 loopback 서버와 가짜 API만 사용했다.
- 기존 경고: Starlette의 AnyIO 별칭 deprecation, Vite의 500 kB 초과 번들 안내. 새 운영 패키지는 추가하지 않았다.
- 기존 가상환경의 Python이 삭제된 `/tmp` 경로를 가리켜 테스트용 Python 3.12.12를 별도 임시 경로에 준비하고 기존 고정 의존성을 재사용했다. FastAPI 테스트 클라이언트의 로컬 스레드 통신을 위해 sandbox 밖에서 테스트했으며 실제 서비스·모델 호출은 하지 않았다.
