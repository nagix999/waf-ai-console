# LLM 응답 교정 재시도

## 확인한 원인

사용자 보고: 내부 데이터 1,319건 중 완료 1,283건, 실패 36건(실행 성공률 약 97.27%). 실제 로그를 개발 환경으로 가져오거나 외부 모델로 전송하지 않았다.

ModuAgent 0.6.2의 `model output incomplete`는 `model_output_incomplete` 코드다. 모델의 종료 사유가 `length`, `max_tokens`, `timeout`이면 **스키마를 검사하기 전에** 발생한다. 따라서 이 메시지만으로 JSON 스키마 변환 오류라고 단정할 수 없다. `output_validation_failed`는 별도의 출력 검증 오류다. 기존 실행기는 후자만 한 번 교정했고 전자는 즉시 실패했다. 실제 36건의 세부 원인이 모두 같다는 의미는 아니다.

## 변경 내용

기존 Primary → 조건부 독립 Verifier → 서버 최종 판정 구조를 유지한다. 양 역할과 Production/Test에 같은 정책을 적용한다.

| 오류 | 처리 |
| --- | --- |
| JSON/필수 필드/타입/범위/판정 계약 위반 | 검증기가 만든 필드 경로·오류 유형·계약 설명으로 전체 JSON을 다시 작성 |
| vLLM `length`, `max_tokens` / OpenAI `length` | 출력 한도와 중단 원인을 알리고 중복 설명을 줄여 완전한 JSON 재작성 |
| vLLM 응답의 `timeout` | 생성 시간 초과를 알리고 짧고 완전한 JSON 재작성 |
| 인증/허용 대상/프로필 변경, 거절, 콘텐츠 차단, 알 수 없는 종료 사유 | 교정 재시도하지 않음 |
| 통신 timeout/연결 실패/HTTP 408·5xx | 기존 통신 재시도 1회 유지; 소진 후 출력 교정으로 다시 반복하지 않음 |

- Primary/Verifier 역할별 **최초 1회 + 교정 최대 3회 = 총 4회**. 형식 오류와 응답 중단이 번갈아 발생해도 합쳐서 4회다. 성공하면 즉시 종료한다.
- 기본 한도는 `backend/app/agent/executor.py`의 `OUTPUT_VALIDATION_MAX_ATTEMPTS=4`다. 별도 설정 UI/DB 필드는 추가하지 않는다. 내부 호출자는 1~4회로 낮출 수 있다.
- 교정 단계가 진행되면 요약·해석의 중복과 수식어를 더 줄이도록 안내한다. 이전 응답 전체를 누적하거나 깨진 JSON을 이어 붙이지 않는다.
- 필수 필드·최소 길이·서로 다른 핵심 근거·필요한 확인사항은 유지하도록 지시한다. 짧게 만들기 위해 판정·심각도·신뢰도를 바꾸거나 보류를 선택하지 않도록 한다. 실제 설명 품질 보존은 별도 확인이 필요하다.
- 같은 역할의 고정 입력·지침·모델·스키마·출력 한도를 사용한다. 기본 지침은 바꾸지 않고 교정 지시만 붙인다. 출력 토큰/문맥 길이를 자동으로 늘리거나 입력 원문을 추가로 잘라내지 않는다.
- Primary 출력·교정 이력은 Verifier에 전달하지 않는다. 이전 모델 출력/오류의 임의 본문도 system 지침으로 넣지 않는다.
- 원문 출처 검증과 최종 판정 정책은 완화하지 않는다. 끝내 복구하지 못한 Primary는 실패, Verifier는 기존처럼 최종 보류다. 실행 성공률을 높이려고 실패를 완료로 바꾸지 않는다.
- 별도 원문 인용 교정은 기존 1회, 선택적 근거 정리는 기존 1회를 유지한다. 이 단계들에서 새 교정 루프를 시작하지 않는다.

## 시간·동시 처리·보안

통신 재시도는 교정과 별도다. 각 교정 시도 안에 통신 시도가 최대 2회이므로 Primary/Verifier 한 역할의 구조화 출력 단계는 최대 8회 HTTP 요청이다. 별도 인용 교정이 필요하면 기존 한도가 더해진다. 정상 첫 응답은 추가 호출 없이 끝난다. 교정된 문항은 시간·모델 비용이 늘어난다.

기존 서버별 동시 처리 슬롯 하나를 교정 동안 공유하며 실제 요청 직전에 허용 대상·프로필·작업 소유권을 다시 검사한다. 운영 실행의 슬롯 제한 시간은 `프로필 timeout × 2 × 교정 총 시도 수 + 5초`이며, 슬롯 만료보다 먼저 종료된다. 각 ModuAgent 실행에도 기존 `timeout × 2` 제한이 있다. 대기 시간은 모델 응답 시간과 분리한다. 작업 취소/소유권 상실 시 새 HTTP 전송을 계속하지 않는다. 이미 전송한 원격 GPU 작업의 취소까지 보장하지는 않는다.

`output_validation_retry`의 기존 필드를 유지하고 `version=structured-output-repair-v2`, `stop_reason`, 시도별 `retry_kind`, `provider_finish_reason`, `duration_ms`, `max_output_tokens`를 추가한다. 원시 provider 본문·미완성 출력·private reasoning은 저장하지 않는다. 검증 오류에는 허용된 필드명·오류 유형만 남긴다.

미완료 응답 때문에 framework 사용량 집계가 비어 있으면 provider의 숫자 카운터만 사용한다. 없는 수치는 null이며 임의로 0이나 계산값을 채우지 않는다. 최상위 usage는 마지막 시도이고 전체 사용량은 시도별 usage를 합산한다. 둘을 중복 합산하지 않는다. 통신 실패에서 사용량을 받지 못한 호출까지 과금 사용량을 완전히 측정하는 것은 아니다.

설정의 실패 집계에는 `model_output_incomplete`도 `output_incomplete`로 분류한다. 길이와 시간 중단을 함께 포함하므로 화면 문구는 “응답 생성 중단”이다. 과거 저장 결과/진단은 다시 쓰지 않는다.

OpenAI의 `length`와 거절을 별도로 처리하는 기준은 [공식 구조화 출력 안내](https://developers.openai.com/api/docs/guides/structured-outputs)를 확인했다. OpenAI 전용 옵션·승인·공식 대상 제한을 유지한다. vLLM에는 OpenAI 옵션을 추가하지 않는다.

## 검증과 적용

외부 통신을 차단한 임시 컨테이너에서 실제 ModuAgent와 HTTP 모의 응답으로 검증했다. 관련 백엔드 검사 356개가 통과했다(최초 354개 통과, 샘플 경로 누락 2개는 읽기 전용 경로 연결 후 재검사 통과). 프런트엔드 테스트 파일 41개도 통과했다. 응답 중단/JSON 오류 복구·혼합 오류 총 한도·거절/HTTP 오류 중단·허용 대상 해제·취소·동시 처리 슬롯·사용량 중복 합산 방지·기존 근거/판정 정책을 확인했다.

운영 DB/실행 컨테이너는 변경하지 않았다. 내부 원문 전송·유료 호출·실제 GPU 평가·재배포·Git 업로드는 하지 않았다. 새로운 DB 마이그레이션·운영 의존성은 없다.

운영 재검증 순서:

1. 배포 후 기존 실패 36건을 같은 모델·출력 한도로 재실행한다. 이전 실패 이력을 지우거나 덮어쓰지 않는다.
2. 복구 여부와 시도별 원인을 확인하고, 복구된 분석의 원문 근거·판정·설명이 유효한지 분석가가 확인한다.
3. 같은 1,319건 기준으로 미해결 실패가 **13건 이하**여야 실패율 1% 미만이다. 기존 36건 중 최소 23건 복구가 필요하다. 실패 문항만 다시 실행한 수치는 원래 모집단의 재실행 포함 누적 복구율이며, 새 배치의 성공률과 구분한다.
4. 새 전체 배치에서 실행 성공률, 교정 발생률·복구율, 추가 호출 수, 처리시간, 참고 답안 일치/미탐/보류를 함께 확인한다. 성공률 개선을 정확도 개선으로 해석하지 않는다.

같은 `length` 오류가 반복되면 교정 횟수만 늘리지 말고 프로필 출력 한도와 vLLM 문맥/생성 설정을 확인한다. 현재 입력 예산은 문자 기반 추정이므로 실제 tokenizer와 긴 운영 데이터에서 남는 토큰을 보장하지 않는다. 이 변경만으로 99% 실행 성공을 보장할 수 없다.
