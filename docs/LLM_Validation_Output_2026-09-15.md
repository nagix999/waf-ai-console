# LLM 연결·기능 검증의 출력 한도와 실패 원인 표시

현재 코드의 출력 상한·고정 JSON 검증·응답 상태 기록은 [2026-09-16 후속 변경](LLM_Validation_JSON_2026-09-16.md)을 따릅니다. 아래 256토큰 안내와 검증 수치는 당시 기록입니다.

2026-09-15 코드·오프라인 검증 결과입니다. 실행 중 Docker 서비스와 운영서버에는 아직 반영하지 않았습니다. 실제 Gemma/vLLM 호출은 하지 않았습니다. GitHub 게시 대상은 기존 `nagix999/waf-ai-console`의 `main`이며, 앱 버전 0.2.0과 기존 태그는 유지합니다.

## 배경과 확인 범위

운영 Gemma 전체 검증에서 동시 요청 수를 1로 설정했는데도 `vllm_output_incomplete`가 발생했다는 보고를 받았습니다.

기존 코드에서는 동시 요청과 긴 입력 검증에 `max_tokens=8`을 고정해서 보냈습니다. 이 값은 프로필의 실제 분석용 출력 한도와 별개였습니다. 서버가 `finish_reason=length`를 반환하면 `vllm_output_incomplete`로 처리하면서도, 화면에는 응답 중단과 거절을 구분하지 못하는 공통 메시지를 표시했습니다.

따라서 동시 요청 수를 줄이는 것만으로 출력 길이 부족을 해결할 수는 없습니다. 8토큰 제한은 코드에서 확인한 문제이며, 해당 운영 응답의 사용량·서버 설정은 직접 확인하지 못했으므로 운영 장애의 유일한 원인이라고 단정하지 않습니다.

## 변경 내용

- vLLM 연결·기능 검증의 생성 요청은 `min(256, 프로필의 max_output_tokens)`를 사용합니다. 기존 동시 요청·긴 입력의 8토큰 제한과 나머지 짧은 검증의 64토큰 제한을 교체했습니다.
- `temperature=0`, `enable_thinking=false`, 내부 연결 허용 검사와 서버별 동시 호출 상한을 유지합니다.
- OpenAI 요청의 출력 한도는 기존대로 프로필 설정을 사용합니다. 공급자별 요청 옵션은 섞지 않습니다.
- 요청별 출력 한도, 입력·출력·전체 사용량, 종료 사유, 거절 여부, HTTP 상태, 오류 코드를 기록합니다. 응답이 없거나 올바른 사용량이 없으면 `null`로 기록하고 화면에는 ‘미기록’으로 표시합니다. 실제 0은 0으로 유지합니다.
- 동시 요청 중 하나가 실패해도 이미 제출한 나머지 요청의 처리가 끝난 뒤 기록을 저장합니다. 실패를 통과로 바꾸거나 자동 재요청하지 않습니다.
- 잘린 출력, 거절, 비정상 종료, 빈 응답은 계속 실패입니다. 기능 검증이 실패하면 선택한 150건 판정 평가도 시작하지 않습니다.

검증의 출력 **상한**을 늘린 것이므로 매번 256토큰을 생성하도록 강제하지는 않습니다. 다만 모델이 길게 답하면 기존보다 처리 시간이 늘어날 수 있습니다.

## 화면과 이력

설정 → LLM 공급자 → 검증 결과 → **확인 내용**에서 실패 원인과 요청별 토큰·종료 사유를 표로 봅니다. **기술 기록**을 누르면 기존 JSON 트리와 JSON 텍스트 보기를 사용할 수 있습니다. 모바일에서는 표 안의 긴 문구를 줄바꿈합니다.

기존 검증 기록은 수정하지 않습니다. 과거 기록도 오류 코드가 있으면 알기 쉬운 설명을 표시하지만, 저장되지 않은 토큰 한도·사용량을 현재 프로필 설정으로 추정하지 않습니다.

저장 위치는 기존 `VLLMTestRun.checks_json` 항목의 `response_diagnostics`입니다. 기존 관리자 검증 조회 API의 `checks`에도 같은 필드가 반환됩니다. DB 컬럼·마이그레이션이나 운영 패키지 추가는 없습니다.

기록은 고정된 오류 코드·종료 사유와 유효한 숫자만 허용합니다. 응답 원문, 거절 문구, 추론 텍스트, 요청 메시지, API Key, 공급자의 임의 오류 본문은 추가 기록에 넣지 않습니다.

## 유지하는 설정

실제 WAF 분석의 출력 한도, Primary·Verifier·근거 정리 모델 배정, 공통 지침, 판정 정책, 동시 처리 설정을 바꾸지 않습니다. 기존 프로필의 검증 상태와 설정 식별값도 변경하지 않습니다. 새 진단 정보는 사용자가 새로 실행한 검증부터 저장됩니다.

## 검증 결과

- 관련 백엔드 회귀 테스트 **214개 통과**: 공급자별 옵션, 1건 동시 요청의 출력 한도, 각 단계의 잘림·거절 차단, 혼합 성공/실패 동시 요청 정리, 사용량 누락, 민감한 응답 정보 제외, 내부 연결 제한, 프로필 지정 조건, 검증 이력 저장·관리자 API 반환, 실패 후 데이터셋 평가 차단.
- 프런트엔드 **37개 테스트 파일 통과**, 배포용 빌드 성공.
- 예시 기록만 주입한 브라우저 점검: 상세 창, 요청별 상태, 기술 JSON 보기, 모바일·다크 모드, 키보드 닫기, 기존 기록 호환성 확인. 실제 API·모델 요청은 하지 않았습니다.
- 백엔드 전체 테스트를 재실행한 결과는 아닙니다. 기존 Starlette/AnyIO 폐기 예정 경고와 프런트엔드 단일 번들 크기 경고는 남아 있습니다.

## 배포 후 가장 작은 운영 확인

1. 기존 Gemma 프로필의 검증 동시 요청 수는 1로 유지합니다.
2. 전체 검증에서 **연결·기능 검증만** 선택합니다. 먼저 150건 판정 평가 없이 기능 검증을 확인합니다.
3. 동시 요청과 긴 입력의 새 기록에서 실제 요청 한도가 256토큰인지, 정상 종료했는지 확인합니다. 프로필 한도가 더 작다면 그 값을 사용합니다.
4. 여전히 실패하면 해당 항목의 종료 사유·사용량·HTTP 상태·오류 코드를 확인합니다. 원문이나 API Key를 공유할 필요는 없습니다.

`length`가 계속되면 서버의 문맥 길이, 채팅 템플릿·종료 처리, 사고 모드 비활성화 적용 여부 등을 확인한 뒤 검증용 상한을 재검토해야 합니다. 프로필의 분석용 출력 한도를 256보다 크게 높이는 것만으로 이번 **검증용 256토큰 상한**이 더 커지지는 않습니다. 256토큰이 모든 모델·서버 구성에 충분하다는 점은 아직 실모델로 검증하지 않았습니다.
