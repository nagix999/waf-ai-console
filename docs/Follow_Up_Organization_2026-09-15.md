# 추가 확인사항 정리와 Test API 사용 안내

2026-09-15 구현. 코드·오프라인 검증 범위이며 Docker 재배포, 실제 모델 호출, Git 게시와 운영 설정 변경은 하지 않았다.

## 변경 범위

기존 선택적 근거 정리 단계에서 추가 확인사항도 함께 정리한다. 별도 LLM 단계나 모델 설정을 추가하지 않으며, Agent 설정의 기존 모델 배정을 사용한다. 화면 이름은 **근거·확인사항 정리**, 모델 선택은 **정리 모델**이다. 이 옵션을 사용하지 않는 실행에는 적용하지 않는다.

Primary → 조건부 독립 Verifier → 서버 최종 판정 순서는 유지한다. Verifier에 Primary 결과를 전달하지 않고 최종 판정 뒤에 표시용 정리만 수행한다. 판정·심각도·원래 근거·역할별 분석·확인사항을 덮어쓰지 않는다. 분석 상세와 Markdown·PDF·Excel의 추가 확인사항에 같은 대표 선택 결과를 적용한다. Agent 실행 이력의 원본 JSON은 그대로다.

## 묶는 기준과 한계

- 기존 최종 `analyst_guidance.checks`의 최대 5개 항목이 대상이다. 역할별 원본을 새로 합쳐 상한을 늘리거나 기존에 생략된 확인사항을 복구하지 않는다.
- 서버는 `source_ko`가 정확히 같은 항목만 묶기 후보로 허용한다. 자료명이 다르면 유사하게 보이더라도 병합하지 않는다.
- 모델에는 자료가 같다는 이유만으로 묶지 말고 실제 확인 작업·대상·처리 경로·판단 조건까지 같을 때만 묶도록 지시한다. 요청 수신과 실제 실행, 공격 판단 조건과 피해 확인, 다른 필드·설정·시간 범위는 구분한다. 불명확하면 각각 남긴다.
- 모델은 번호로 그룹과 기존 대표 항목만 선택한다. 새 문장을 작성하거나 확인 자료·조건을 보충하지 않는다. 서버는 번호 중복·누락·다른 자료의 병합·그룹 밖 대표·추가 설명 필드를 거부한다.
- 표시 매핑은 원래 목록 전체와 연결한다. 원본이 달라졌거나 매핑이 불완전하면 화면과 다운로드 모두 원래 목록으로 돌아간다. 최종 판정이 정탐·오탐이고 원래 확인사항이 비어 있으면 과거 권고로 채우지 않는다.

**같은 자료 안에서 두 문장이 실제로 같은 작업을 뜻하는지는 모델 판단이다.** 서버의 구조 검증만으로 의미가 다른 항목의 잘못된 병합까지 입증하거나 완전히 방지하지 못한다. 실제 Gemma와 운영 자료에서 정리 품질은 별도 검증해야 한다. 자료명 표현이 다른 중복은 의도적으로 남을 수 있다.

## 호출·버전·보존

- 새로 고정되는 정리 지침은 `result-editor-v2`다. Test는 접수 시, Production은 최초 실행 시작 시 고정한다. 운영·테스트의 정리 지침은 동일하다.
- 이미 고정된 `evidence-editor-v1`은 이전 근거 정리 계약만 사용한다. 기존 실행과 해당 스냅샷을 사용하는 실패 재실행에는 확장 지침을 소급하지 않는다.
- 기존 근거 표시 매핑 계약 `evidence-editor-v1`은 유지하고, 확인사항 표시 매핑 `follow-up-editor-v1`을 별도로 저장한다. 단계명은 기존 `llm_evidence_editor`를 유지하되 이력 화면은 실제 지침 버전에 맞춰 표시한다.
- 근거·확인사항을 **한 번의 호출**에 함께 넣는다. 확인사항에만 후보가 있어도 실행할 수 있으므로, 기존 옵션이 켜져 있다면 이전에는 건너뛰던 분석에서 추가 시간·비용이 발생할 수 있다.
- 공통 동시 처리 슬롯과 기존 제한을 유지한다. 출력 최대 1,024토큰(프로필 한도 이하), 모델 응답 최대 30초(프로필 제한 이하), 대기 포함 최대 90초, 자동 재시도 없음. 입력은 기존 16,000바이트 및 컨텍스트 예산 검사를 사용한다.
- 입력 한도 초과·정리 실패·잘못된 매핑은 원본 표시로 복구한다. 분석 자체를 실패로 바꾸거나 판정을 보류로 바꾸지 않는다. 작업 소유권을 잃으면 기존 규칙대로 중단한다.
- 상세 입출력은 암호화된 단계 이력에 기록하고 일반 메타데이터에는 버전·상태·항목 수만 추가한다. 실제 호출 오류 원문을 결과나 메타데이터에 복사하지 않는다.

DB 변경과 새 운영 의존성은 없다. 활성화 여부, 모델·공통 판정 지침·API 키·기존 분석 기록은 변경하지 않았다.

## Test API의 테스트명

`test_run_id`는 사용자가 정한 이름이 아니라 **이미 생성한 테스트의 서버 ID**다.

1. Test 키로 `POST /api/v1/test-sessions`에 `{"name":"Gemma 검증 1차","idempotency_key":"gemma-check-20260915-01"}`를 보낸다.
2. 응답의 `id`를 `POST /api/v1/analyses?wait_seconds=60&test_run_id=<반환된 id>`에 넣고 이벤트 JSON을 전송한다.
3. 접수가 끝나면 `POST /api/v1/test-sessions/<id>/close`로 닫는다. 진행 중 분석은 계속 처리된다.
4. `GET /api/v1/test-sessions/<id>`에서 저장한 테스트명·결과·지표를 확인한다.

`wait_seconds`는 응답 대기 시간뿐이며 이름이나 실행 제한 시간이 아니다. 등록되지 않은 임의 ID는 404, 36자 초과는 422다. 생략하면 자동 테스트를 만들며 자동 생성 이름과 실행 ID도 별개다. 관리자 쿠키와 키를 함께 보내면 관리자 세션이 우선하므로 Test API는 쿠키 없는 클라이언트로 확인한다.

접수 동작은 변경하지 않았고, 저장소·온라인 API 정의서와 Swagger의 설명을 보강했다. 운영에서 임의 ID가 접수됐다는 현상은 원격 서버의 버전·실제 요청을 확인하지 않아 재현 여부를 확정하지 않았다. 전체 예제는 [운영 API 정의서의 Test API 키 사용](Production_API_v0.1.md#test-api-키-사용)을 따른다.

## 검증

합성 입력, 격리된 테스트 DB, 가짜 모델 응답과 차단된 네트워크만 사용했다. 실제 모델의 정리 품질·지연·토큰 사용량과 운영 데이터는 미검증이다.

- 백엔드: 관련 회귀 269개와 마지막에 추가한 Swagger 설명 검사 1개, 총 270개 통과. 근거·확인사항 정리, v1/v2 스냅샷, 모델 배정·실패 재실행, 판정 안내, PDF·Excel, Test API·자료 접근 분리, 가짜 vLLM/OpenAI 전송, 동시 처리·공통 지침·API 문서를 포함한다. 실제 서비스에 연결하지 않은 `--network none` 임시 컨테이너에서 실행했다.
- 프런트엔드: 전체 38개 테스트 파일 통과. 대표 선택·원본 변경 감지·불완전 매핑 복구·빈 목록 보존·화면과 Markdown 일치·단계 버전별 이름을 확인했다.
- 브라우저: 가상 자료만 사용해 12개 확인 통과. 추가 확인사항 3→2개 표시, 다른 작업 보존, 보고서·Markdown의 동일 대표 선택, Agent 원본 JSON 보존, 잘못된 매핑의 3개 원본 복구와 375px 화면의 가로 넘침을 확인했다. 페이지 오류 0건, 네트워크 요청 0건이다.
- UI 빌드 통과. 기존 Vite의 500kB 초과 번들 경고와 백엔드 Starlette/AnyIO 사용 중단 예고 경고는 남아 있다. 이 작업에서 의존성 변경이나 번들 구조 개편은 하지 않았다.

검증의 대표 선택 응답은 사람이 정한 가짜 응답이다. 테스트 통과를 실제 모델의 중복 제거 정확도 개선으로 해석하지 않는다. 다음 실제 검증에서는 같은 자료의 유사 문장과 다른 작업·조건을 함께 넣고, 잘못 묶은 항목과 남은 중복을 따로 검수해야 한다.
