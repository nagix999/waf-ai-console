## 결론

Docker 재배포 후 같은 `gpt-5.4-mini`로 150건을 접수했다. **파싱 50건·Hard 50건·Medium 42건이 완료됐으며, Medium 8건은 OpenAI HTTP 429로 실패했다.** 사용자 요청에 따라 추가 호출·재실행 없이 완료된 **142건만 같은 이전 문항과 비교**했다. 150건 전체 평가를 완료했다는 뜻은 아니다.

참고 답안 일치는 **114/142 → 116/142건(80.28% → 81.69%)**이다. 미탐은 1→0건, 공격 답안의 보류는 4→0건으로 줄었지만 **정상 요청의 과탐이 0→5건으로 늘었다.** 보류 설명의 빈칸은 줄었으나 판정 품질이 전반적으로 개선됐다고 결론내리거나 운영 자동화 범위를 넓히는 것은 권고하지 않는다.

최종 보류 15건과 답안 불일치 26건의 합집합 37건, 각 묶음에서 event_id 순으로 고른 일치 공격·정상 각 1건씩 6건, 총 **43개 고유 문항의 저장된 요약·판단 쟁점·확인 항목**을 검토했다. 검토자는 Codex이며 독립된 사람 분석가 검수나 실제 사용자 사용성 시험은 아니다.

‘공격 시도와 성공을 구분하라’는 지침 이후 구문만 보고 공격 의도를 확정하는 설명이 나타났다. 그러나 v2.11 지침과 v2.12 입력 검사를 함께 적용한 단일 비교이므로 이를 특정 문장 하나의 인과 효과로 단정하지 않는다. 정상/공격 짝 문항으로 경계를 다시 검수해야 한다.

설명의 정확성도 별도 문제다. URL 수집 사례는 예시 주소를 내부 자산으로 단정했다. `192.0.2.0/24`는 문서 예시용 범위이며 실제 사내 자산이라는 근거가 아니다. [RFC 5737](https://www.rfc-editor.org/rfc/rfc5737.html#section-3) 테스트 표식·회사명·Cookie를 정상 근거로 사용하는 문장, Host 등 주변 정보의 반복, 내부 진단 용어도 남았다. 구조화된 `missing_condition`은 비어 있는데 쟁점 문장에는 자료 부족을 적어 안내가 어색해지는 경우도 있다.

## 보류 안내는 별도로 효과 확인

- 이번 보류 **15건 모두** 관련 근거와 판단 쟁점·확인 항목이 표시됐다. 미확인 조건이 있는데 확인 항목이 없는 경우는 0건이다. 조건 기록은 9건이며, 나머지는 실제 기록에 따라 근거 해석 검토나 입력 상태 확인을 안내한다.
- 모델 재평가의 영향과 분리하기 위해 **이전 v2.10의 동일 보류 19건**을 그대로 조회했다. 구체적 확인 항목 표시가 **8→19건**, 쟁점 표시가 **18→19건**으로 늘었다. 모델 호출은 0회였고 저장 결과 해시는 변하지 않았다.
- 이 19건은 실제 Excel의 모든 시트와 웹의 확인 문구가 일치함을 대조했다. UI·백엔드 표시 로직도 같은 결과를 냈다. 조회가 사람의 검토 완료를 의미하거나 안내의 실무적 유용성을 증명하지는 않는다.
- 새 완료 결과 142건에 근거 구분이 기록됐다. 근거 924개는 정탐 281·오탐 265·참고 378개, 판단 쟁점 205개는 모두 근거에 연결됐다. 원문 연결이 맞아도 그 해석이 맞다는 뜻은 아니다.

## Verifier·입력 검사·호출량

Primary 일치는 114건, 최종 일치는 116건으로 개선 4·악화 2건이다. 이 중 **3건은 두 역할의 정상 결론을 서버 입력 검사로 보류한 사례**다(본문 없음 1·서로 다른 Content-Length 2). 나머지 Verifier 결합만의 일치 변화는 개선 1·악화 2, 순감 1건이다. 최종 순증 2건을 모두 Verifier의 효용으로 표현하지 않는다.

Verifier는 118건에서 실행됐다. 정상이었던 요청을 공격으로 해석한 경우 두 역할이 같은 오류를 내기도 했고, 확신이 높아 Verifier가 실행되지 않은 과탐도 있었다. 이번 결과만으로 Verifier 제거·새 오케스트레이터 추가·실행 조건 변경을 결정하지 않았다.

이번 완료분은 역할 단계 260개와 출력 계약 교정 1회로 총 261회다. 파싱 019의 Verifier가 정탐 판정과 맞지 않는 심각도를 제출해 기존 재시도에서 회복했다. 원문 근거 거부·근거 인용 교정은 0건이다. 원문 후보 생략은 4개 역할 단계에 기록됐다.

실패분까지 포함하면 모델 단계 268개·기록된 논리적 호출 269회다. HTTP 429 실패 8개 단계의 사용량은 미기록이며 **0토큰으로 단정하지 않는다.** 위 사용량은 공급자 청구 금액이나 전송 계층 재시도까지 확정한 수치가 아니다. 429만 저장돼 있으므로 크레딧 고갈과 일시적인 호출 한도를 구분해 확정할 수는 없다. 추가 진단용 모델 호출·분석 재실행은 하지 않았다.

첫 처리 시작부터 마지막 실패 종료까지 한국 시각 **14:26:35~14:56:58, 약 30분 24초**다. 처리 시간 평균은 큐 대기를 제외한다. 테스트별 접수→완료 시간은 대기가 겹치므로 더하지 않는다. 공급자 부하가 통제되지 않았고 평가 중 격리된 오프라인 테스트도 실행했으므로 속도 변화의 원인을 코드에만 돌리지 않는다.

## 다음 가장 작은 보완

1. **새 과탐 5건과 대응 공격 문항의 판단 경계를 먼저 검수한다.** GraphQL 별칭·파일명·표시용 경로·엔터티/이스케이프된 코드가 실제 실행·조작 구문으로 쓰이는지 구분한다. 정상 맥락이 없다는 사실만으로 악의를 확정하지 않도록 짧은 기준을 합의한다.
2. 판정 성능과 표시 효과를 분리한다. 확인 안내의 보완은 유지하되, 지침 변화와 입력 검사 효과를 개별 비교할 후속 평가를 설계한다. 실패 8건을 재실행하려면 사용 한도 확인과 별도 실행 합의가 필요하다.
3. 별도 18건의 참고 답안·확인 조건을 사람이 검수한 뒤, 테스트 표식 의존과 과도한 확정 여부를 평가한다. Gemma4·실제 운영 로그는 승인된 GPU 환경에서 별도로 검증한다.

이 결과는 반복 사용한 가상 개발 문항과 AI 작성 참고 답안의 일치도다. 독립적인 운영 정확도·Gemma4 성능·분석가 사용성을 입증하지 않는다. 과제별 지표와 사례 검토를 함께 보고 별도 평가 자료를 유지하는 방법은 [OpenAI의 평가 권고](https://developers.openai.com/api/docs/guides/evaluation-best-practices)를 참고했다.
