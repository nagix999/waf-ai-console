3. **같은 관찰이 다시 쓰인 문장으로 반복된다.** 원문·방향이 같아도 설명 문장이 다르면 양 역할의 근거가 따로 남는다. 참고 내용은 398/995개(40.0%)이며 일반 Host·WAF 조치·시그니처 설명이 핵심을 길게 만든다. 반대 해석을 삭제하지 않으면서 대표 설명과 부가 관찰을 구분할 필요가 있다.
4. **구체적인 문장이 반드시 정확하지는 않다.** CDATA 경계를 설명하는 요약, 태그 시작·종료 표기, SQL 주석 용어, 한국어가 아닌 단어·내부 진단명이 남은 문장을 확인했다. 올바른 최종 판정도 설명 검수를 면제하지 않는다.
5. **보류 답안 자체도 검수가 필요하다.** CL+TE 뒤의 추가 요청처럼 공격 시도로 읽을 수 있는 사례까지 실제 성공 자료 부족을 이유로 보류 답안으로 정했는지 확인해야 한다. 반대로 소유권·허용 기능이 쟁점인 요청은 그 정책 없이 정상/공격을 확정하면 안 된다. 이번에는 기존 답안을 바꾸지 않고 비교했다.

## 후속 작업 권고

1. **미탐과 과도한 확정부터 보완한다.** 이번 SVG 미탐, JSON 안의 공격 구문, 정상 파일명, 권한·허용 기능 미상 사례를 짝지어 판단 기준과 답안을 먼저 검수한다. 공통 지침은 ‘입력 위치·구문·업무 의미’, ‘시도와 성공’, ‘시그니처 일치와 요청 전체 공격성’을 짧고 분명하게 구분하도록 보완한다. 개별 문항 ID나 테스트 표식으로 정답을 맞추는 규칙은 넣지 않는다.
2. **부분 로그의 입력 검사 빈틈을 좁힌다.** 버전이 없어도 확인 가능한 본문 누락·길이 선언과, 확인할 수 없는 수집 상태를 구분한다. `partial` 전체를 보류로 바꾸지 않고 정상 확정의 근거가 부족한 경우만 제한하도록 설계를 합의한다.
3. **보류 설명과 확인 안내의 빈틈을 메운다.** 양 역할의 확정 이후 서버 보류에도 기록된 사실로 판단 쟁점을 보여 준다. 누락 조건이 있으면 확인할 자료를 연결하고, 자료 부족이 아니면 근거 해석 검토로 안내한다. 새로운 사실을 만들어 내거나 추가 자료가 무조건 필요하다고 표현하지 않는다. 중복·주변 설명과 부정확한 어휘도 함께 줄인다.
4. **그다음 같은 150건 + 별도 검수 문항으로 확인한다.** 기존 파일은 기준선으로 보존하고, 테스트 표식이 없는 새 평가셋은 별도 버전으로 만든다. 미탐·과탐·부적절한 보류/확정과 설명 유용성을 함께 통과 조건으로 삼는다. 유료 재평가와 Gemma4 검증은 별도 승인·GPU 환경에서 진행한다.

이번 요청에서는 평가와 비교만 수행했으며 위 보완을 구현하지 않았다. 원문 바로가기·분석가 확인 작업 관리·Verifier 실행 조건 조정은 이 결과를 반영해 후속 설계를 정하는 편이 좋다. 오케스트레이션 LLM은 계속 뒤로 둔다.
