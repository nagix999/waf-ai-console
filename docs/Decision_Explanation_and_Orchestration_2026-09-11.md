# 보류 설명 개선과 오케스트레이션 검토

작성: 2026-09-11. 화면·보고서 표시 개선은 구현, 추가 LLM·조사 도구·판정 정책 변경은 미구현이다. 이번 작업으로 배포하거나 모델을 호출하지 않았다.

## 구현한 범위

저장된 최종 결과의 `diagnostics.inconclusive_reasons`를 읽어 보류 구분·설명·다음 행동을 표시한다. 웹 상세, Markdown 보고서, PDF와 Excel에 같은 기준을 적용한다. 추가 확인 사항은 마지막에 유지한다. 새 API 필드·DB·패키지·프롬프트·Agent 단계는 없다.

| 기록된 상태 | 표시 | 다음 행동 |
|---|---|---|
| 필수 분석 절차 실패 | 자동 분석 미완료 | 서비스 담당자가 실행 오류 확인 |
| 원문 인용 검증으로 판정 제한 | 근거 확인 실패 | 원문 직접 검토 및 대조 오류 확인 |
| 인용 교정 뒤 판단 재검토 필요 | 근거 재검토 필요 | 원문과 해석의 연결 재검토 |
| 입력 검사에서 실제로 정상 판정을 제한 | 요청 구조 확인 필요 | 수집 기록·요청 형식 대조 |
| 결과 결합에서 판정을 확정하지 못함 | 판단 미확정 | 원문과 해석 재검토; 자료 부족으로 단정하지 않음 |
| 모델의 보류 또는 과거 상세 사유 없음 | 보류 이유 | 기록된 최종 설명 유지; 없으면 미기록 안내 |

우선순위는 실행 실패 → 근거 검증/교정 → 실제 입력 제한 → 결합 미확정 → 모델 보류/미기록이다. 복수 사유 중 대표 사유를 표시하며 전체 진단 정보는 기존 이벤트·실행 정보에서 보존한다.

`parse_status=partial/failed`, 입력 생략, Verifier 실행 조건, 일부 인용 거절만으로 최종 보류 원인을 추정하지 않는다. 입력 구조 문제는 `input_integrity_limited`와 실제 강등 메타데이터가 함께 있을 때만 원인으로 표시한다. 구조 문제를 수집 손실이나 공격으로 단정하지 않는다.

과거 결과는 다시 저장하지 않는다. 원래 결과 JSON·원문·Agent 이력·판정·점수·Label은 그대로이며, 표시 시 해석 버전만 달라진다. 과거의 명시적인 Verifier 실패 메타데이터와 정확히 일치하는 서버 근거 거절 문구는 제한적으로 지원한다. 임의 자연어 오류에서 원인을 추출하지 않는다.

공통 기본 확인 항목은 기존 서버가 만든 자료/내용/목적 세 문장이 정확히 같은 경우에만 숨긴다. 실제 요청별 확인은 보존하고, 명시적인 빈 목록을 다른 항목으로 채우지 않는다. 공통 WAF 정책 주의문만 있는 빈 카드는 숨기며 구체적인 위험·제안은 보존한다. 오탐의 유형은 `탐지 유형`, 보류는 `검토한 유형`으로 표시한다.

보류의 세부 분석에는 확정되지 않은 자동 분석 해석이라는 안내를 붙인다. 원문이나 해석을 새로 쓰거나 불리한 근거를 삭제하지 않는다. 서로 다른 해석을 의미상 정리한 보고서는 아직 아니다.

## 검토 근거와 남는 한계

2026-09-10 GPT-5.4-mini 기존 150건 중 보류 15건을 이전 읽기 전용 검토에서 확인했다. 두 모델 모두 보류 3건은 구체적인 최종 요약이 남았고, 한쪽 보류 5건과 서로 반대 확정 7건은 최종 요약이 공통 문장이었다. 기본 확인 안내는 12건이었다. 상세는 [기존 평가 기록](evaluations/Context_Judgment_GPT54Mini_150_2026-09-10.md)을 따른다.

이 개선으로 12건의 사건별 보류 설명이 새로 생기는 것은 아니다. 특히 개별 모델은 확정했으나 최종 정책에서 보류된 경우, 화면은 기록된 결합 미확정 상태를 설명할 뿐 없는 업무 정보 부족 사유를 만들어내지 않는다. 한쪽 모델의 설명을 그대로 최종 사실로 승격하지 않는다. 의미 해석을 정리하는 별도 처리는 후속 범위다.

보류 15건 중 8건은 참고 답안도 보류였다. 보류를 모두 없애는 것은 목표가 아니다. 반대로 전체 150건에서 참고 답안이 보류인 22건을 확정한 사례도 있었다. 참고 답안은 검토가 필요한 테스트 기대값이지 검증된 운영 정답은 아니다. 화면 이해도·의미 정확도·과도한 확정을 함께 봐야 한다. Gemma4 운영 데이터와 실제 분석가 사용성은 이번에 검증하지 않았다.

## 오케스트레이션 LLM을 추가한다면

권고는 **코드가 통제하고 LLM이 제한된 조사 계획을 제안하는 방식**이다. 최종 출력 담당자가 제한된 기능을 도구로 호출하는 manager 패턴은 [OpenAI 공식 오케스트레이션 설명](https://developers.openai.com/api/docs/guides/agents/orchestration)에도 제시되어 있다. 이 패턴을 현재 WAF 시스템에 적용하는 아래 설계는 프로젝트에 맞춘 제안이지, 효용이 검증된 결과는 아니다. ModuAgent와 vLLM/OpenAI 공급자 경계를 유지하며 SDK 교체를 전제로 하지 않는다.

| 선택지 | 기대 효과 | 비용·위험 | 판단 |
|---|---|---|---|
| 현재 코드 흐름 유지 | 예측 가능한 실행·기존 원인 표시 | 사건별 추가 조사는 못함 | 이번 구현 |
| 보고서 작성 LLM만 추가 | 중복·상충 설명과 문장 정리 | 같은 자료를 재해석하며 잘못된 이유를 그럴듯하게 만들 수 있음 | 필요 시 별도 비교 실험 |
| 조사 계획 LLM + 제한된 도구 | 무엇을 확인할지 선택하고 새 사실을 확보할 여지 | 도구 권한·출처·실행 예산·재검증 필요 | 다음 후보 |
| 전권 오케스트레이터 | 유연한 분기·재시도·판정 변경 | 무한 조사, 자의적 확정, 외부 전송, 검증 독립성 훼손 | 현재는 권하지 않음 |

### 맡길 일과 맡기지 않을 일

- 맡길 후보: 원문을 다시 볼 위치 선택, 정상/공격을 구분할 질문 제안, 허용된 조회 도구 선택, 확인된 도구 결과와 남은 조건 정리.
- 맡기지 않음: WAF 차단/허용 변경, 모델·프로필 자동 전환, 허용 목록 외 네트워크 요청, 코드/페이로드 실행, 비밀값 조회, 실패 은폐, 기존 판정·이력 덮어쓰기.
- Primary와 Verifier의 독립성 유지: 서로의 결과를 전달하지 않는다. 조사 계획에 결론이 섞였다면 후속 독립 검증 입력으로 재사용하지 않는다. 검증에는 원문과 출처가 확인된 중립적인 도구 결과만 전달한다.
- 첫 시험에서는 조사 계획과 보고서를 별도 평가하고 기존 최종 판정을 바꾸지 않는다. 보류를 뒤집는 재판정 단계는 별도 설계·합의 대상이다.

현재 도구는 HTTP 구조 확인·디코딩·근거 위치 확인·입력 검사 같은 로컬 전처리 중심이다. 자산·업무 규격·요청 처리 로그를 조회하는 조사 도구가 없으므로 LLM만 추가하면 새 정보 없이 세 번째 의견을 만들 가능성이 있다. 처음에는 원문 위치 확인처럼 좁은 읽기 전용 도구 하나로 시작하고, 내부 자료 조회는 접근 권한·대상·자료 보관 범위를 합의한 뒤 추가한다.

### 제안하는 제한

```text
기존 분석 완료
  → 코드가 조사 대상 여부 확인
  → 계획 LLM: 확인할 질문·원문 위치·허용 도구 제안
  → 코드: 권한·대상·입력·시간·호출 한도 검사
  → 읽기 전용 도구 실행
  → 근거가 있는 조사 결과만 별도 기록
  → 기존 판정은 유지, 추가 결과는 별도 평가
```

첫 시험의 예산 후보는 계획 LLM 1회, 도구 최대 2회, 필요 시 정리 LLM 1회다. 반복 실패 시 중단하고 원래 보류와 실행 실패를 보존한다. 전체 판정/다른 역할 결과/전체 프롬프트를 무조건 붙이지 않고, 필요한 원문 후보와 제한된 구조화 정보를 전달한다. 이는 Gemma4에 적합한 길이나 품질을 보장하지 않으므로 실제 입력·출력 토큰, 초과·잘림과 도구 선택 정확도를 따로 측정한다.

로그 안의 지시가 도구 호출 권한이 되지 않도록 도구명·대상·인자를 서버에서 검증한다. 자유로운 URL·SQL·명령어를 실행 인자로 허용하지 않는다. 비신뢰 입력 분리·구조화된 단계 간 전달·권한 검사는 [공식 Agent 안전 지침](https://developers.openai.com/api/docs/guides/agent-builder-safety)을 참고했다. 구조화 출력만으로 프롬프트 주입이나 잘못된 의미 해석을 완전히 막는 것은 아니다.

### 도입 여부를 판단할 검증

1. 기존 보류만 고르지 말고 명확한 공격·정상, 적절한 보류, 잘못된 확정, 악성 지시가 포함된 입력을 함께 비교한다. 원문·참고 답안·모델·지침 버전을 고정하고 새로운 독립 문항도 포함한다.
2. 기존 코드 흐름 / 보고서 정리만 추가 / 제한된 조사 계획+도구를 비교한다. 새 사실 확보 없이 설명만 달라진 효과와 실제 판정 개선을 구분한다.
3. 측정: 보류 이유의 원문 근거 여부, 허구의 확인 조건, 도구 선택·인자 정확도, 불필요한 조회, 분석가가 이유·다음 행동을 찾는 정확도와 시간, 토큰·p95 지연·오류율.
4. 재판정을 시험할 때는 과탐·미탐·적절한 보류·잘못된 확정을 함께 보고, 보류율 감소만으로 성공이라 하지 않는다. 모델 채점만 사용하지 않고 사람이 표본을 독립 검토한다.

[공식 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)은 다중 Agent 도입을 평가 결과에 따라 결정하고 도구 선택·인자와 각 단계의 비결정성을 평가할 것을 권한다. 현재 비용·정확도·속도 개선 수치는 실험하지 않았으므로 제시하지 않는다. 유료 모델 호출과 실제 사내 자료 전송은 별도 승인 후 진행한다.

## 검증

- 프런트엔드 전체 31개 테스트 파일 통과, Vite 빌드 통과.
- 관련 백엔드 108개 테스트 통과. 기존 Starlette/AnyIO 폐기 예정 경고 1건.
- 동일한 25개 테스트 입력으로 브라우저/Python 원인 분류를 검증한다. 과거·미완료·잘못된 메타데이터·미래 코드·입력 신호 오인·근거 교정 재검토를 포함한다.
- PDF·Excel 생성과 원본 결과 불변성, 구체적인 확인 항목 보존, 내부 역할 출력 미노출을 검증했다.
- 실제 React 앱에서 원문 부족 설명·판단 미확정·근거 확인 실패·분석 미완료·오탐 5종 × 데스크톱/모바일 다크 10개 화면 및 보고서 전환을 검증했다. 모든 API는 테스트 응답이며 실제 API·LLM 호출은 0회다.
- 재현: `cd frontend && node scripts/decision-explanation-smoke.mjs` (기존 Playwright/Chromium 필요; 새 패키지를 설치하지 않음).
- JS 약 511 kB의 기존 500 kB 번들 경고가 남아 있다. Docker 재배포, 실제 분석가 사용성 평가, Gemma4 품질 평가 및 오케스트레이션 구현은 수행하지 않았다.
