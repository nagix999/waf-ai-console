# 테스트 실패 항목 재실행과 평가 반영

## 화면과 처리 방식

테스트 상세의 **실패 항목 모두 재실행** 버튼으로 해당 테스트 전체의 실행 실패 항목을 다시 접수한다. 현재 페이지·난이도·상태 필터와 관계없이 대상을 확인한다. 확인창에서 재실행 가능 건수, 제외 사유, 당시 모델·지침 재사용, 모델 호출·비용 및 해당 시 외부 전송 안내를 확인해야 접수한다.

이미 완료되었거나 대기/처리 중인 항목은 재실행하지 않는다. 입력 검증에서 거부된 행은 분석 자체가 없으므로 파일/입력을 고쳐 접수해야 한다. 모델·지침을 복원할 수 없거나 프로필이 변경·비활성화·검증 취소된 항목은 제외하고 이유를 표시한다. 모델 프로필의 자격 검증용 150건 실행은 기존대로 LLM 설정에서 새 검증을 시작한다. 이 버튼으로 모델 검증 통과 상태를 바꾸지 않는다.

재실행 접수 후 전체 문항·최신 답안 보기로 돌아가고 완료될 때까지 기존 5초 조회로 상태·결과·평가를 갱신한다. 행에는 재실행 횟수를 표시하고 최신 분석 상세를 연다. 개별 분석 상세의 기존 재실행 버튼에도 동일한 결과 연결 규칙을 적용한다.

## 기존에 결과가 반영되지 않던 원인

재실행은 새 `Analysis`로 만들었지만 `TestRunItem`은 최초 분석에만 연결되어 있었다. 테스트 집계는 그 최초 실패를 계속 조회했고 새 분석에는 참고 답안 연결도 없었다.

이제 기존 `retry_of_analysis_id` 연결을 조회해 문항별 최신 실행을 선택한다. 이전에 개별 재실행해 둔 항목도 같은 방식으로 표시한다. `TestRunItem.analysis_id`와 최초 분석·실패 이력·답안은 바꾸지 않는다. 새 DB 컬럼이나 운영 패키지는 없다.

- 테스트 목록·상세의 진행/완료/실패 건수, 문항 목록·필터·평가·실행 비교는 최신 실행을 사용한다.
- 재실행 대기 중에는 대기, 성공하면 완료, 다시 실패하면 실패로 표시한다. 실패를 성공이나 보류로 바꾸지 않는다.
- 한 문항은 하나로 집계한다. 파일 중복 행·재실행 횟수가 평가 분모를 늘리지 않는다.
- 테스트 분석 검색도 기본적으로 최신 실행만 보여 준다. `include_retries=true`는 최초 실패와 재실행 이력을 함께 보여 준다. Production의 기존 원본 집계 규칙은 바꾸지 않는다.
- 테스트 시작 시각은 최초 실행을 포함한 가장 이른 시작, 종료는 현재 문항들이 끝난 시각이다. 전체 경과에는 재실행까지 기다린 기간도 포함될 수 있다.
- 실행 비교의 시간·토큰은 선택된 최신 분석 기준이다. 이전 실패 분석의 비용이 빠진다는 안내를 표시하고 전체 과금액으로 해석하지 않는다.

## 답안·평가 기록 보존

새 재실행에 직접 입력한 참고 답안이 있으면 우선한다. 없으면 가장 가까운 이전 실행의 최신 답안을 비교에만 사용한다. Label을 복사하거나 모델 입력에 추가하지 않는다. 재실행 항목에서 답안을 수정하면 새 답안 이력을 생성하며 원본 답안은 그대로 남는다.

| 보기 | 분석 결과 | 참고 답안 |
| --- | --- | --- |
| 최신 답안 | 문항별 최신 실행 | 해당 실행의 답안, 없으면 이전 실행의 답안 |
| 접수 당시 답안 | 문항별 최신 실행 | `TestRunItem.label_id`에 고정된 초기 답안 |
| 새로 저장한 평가 | 저장 시점까지의 문항별 최신 실행 | 저장 당시 선택한 Label ID |
| 이 기능 이전에 저장한 평가 | 기존처럼 최초 분석 | 기존에 저장한 Label ID |

새 평가 저장은 모든 현재 문항이 끝나고 API 테스트 접수가 닫혀 있어야 가능하다. 새 저장 계약은 같은 트랜잭션의 `rescore_test_with_retries_v1` 감사 기록으로 구분한다. 기록 시각 이후 만들어진 재실행은 그 평가에 포함하지 않는다. 기존 `rescore_test` 평가에 이미 존재하던 재실행을 소급 반영하지 않는다. 감사 이력은 보존해야 하며 새 DB 마이그레이션 없이 기존 저장 구조를 사용한다.

## 관리자 API

- `GET /api/v1/test-runs/{run_id}/retry-eligibility`: 전체 실패 수, 재실행 가능한 분석 ID/건수, 제외 사유별 건수, 외부 호출 여부. 이 조회는 모델을 호출하지 않는다.
- `POST /api/v1/test-runs/{run_id}/retry-failed`: 미리 확인한 `analysis_ids`(1~5,000개), `idempotency_key`, `cost_acknowledged=true`를 받는다. 접수/제외 건수와 새 분석 ID들을 반환한다.
- 다른 테스트의 ID나 중복 ID는 거부한다. 접수 시 권한·상태·원본 설정을 다시 검사한다. 상태가 바뀐 항목은 제외하며 현재 설정으로 자동 대체하지 않는다.
- 같은 요청의 재전송은 기존 접수 결과만 반환한다. 재실행이 다시 실패하거나 차단된 프로필이 복구되었더라도 같은 요청 키로 추가 실행을 만들지 않는다. 새 재실행에는 새 확인과 요청 키가 필요하다.
- SQLite 쓰기 잠금과 기존 부모별 자식 하나 제약으로 겹친 요청을 막는다. 신규 분석들과 일괄 접수 감사 기록은 함께 커밋한다.
- 기존 관리자 세션·Origin/CSRF 보호를 적용하고 서비스 API 키는 허용하지 않는다. Test 키로 원래 접수한 테스트 역시 관리자 화면에서 재실행한다. 키 귀속·용도·`internal_only`·암호화 원문·입력 스키마·모델/지침 스냅샷은 기존 재실행 계약대로 유지한다.
- 실제 LLM 호출은 기존 비동기 worker 및 서버별 동시 처리 상한을 따른다. 버튼을 눌렀다고 vLLM 서버/worker를 추가로 띄우거나 호출 상한을 늘리지 않는다.

## 검증 범위

인공 데이터와 격리 DB/모의 모델로 재실행 체인, 이전 개별 재실행 연결, 성공 후 3×3 행렬·점수 갱신, 검색/페이지/난이도 필터, 중복 행 제외, 최초 답안/저장 평가 보존, 개별 답안 수정, 중복·겹친 접수, 권한·비용 확인, 프로필 변경 차단 및 고정 설정으로 worker 실행을 확인한다.

브라우저 테스트는 네트워크를 차단하고 모의 데이터만 사용한다. 실제 버튼·확인 체크·36건 전체 접수·중복 클릭 차단·필터 초기화·자동 조회/지표 갱신·최신 상세 이동·저장 평가 보기·모바일 확인창을 확인한다. 기존 개발용 브라우저만 사용하며 운영 이미지에 브라우저를 설치하지 않는다.

검증 결과:

- 백엔드 테스트·평가 회귀 검사 178개 통과, 추가 API·worker 검사 174개 통과. 최종 재실행·근거 정리 프로필 관련 검사 55개 통과. 실행 묶음 간 중복이 있으므로 합산 건수가 아니다.
- 프런트엔드 테스트 파일 42개 및 운영 빌드 통과. 빌드의 500kB 초과 JS 청크 안내는 남아 있다.
- 브라우저 모의 시나리오 8개 통과. 실제 API·LLM 호출은 0회다.

운영 데이터의 재실행, 실제 Gemma/유료 API 호출, Docker 재배포·Git 업로드는 이 변경 작업에 포함하지 않는다. 적용하려면 API/worker/frontend를 같은 코드로 재배포해야 한다.
