# 공통 프롬프트 경량화와 테스트 실행 비교

기준일: 2026-09-08. **Test와 Production은 동일한 공통 시스템 지침과 활성 프롬프트 버전**을 사용한다. 용도별 차이는 검증·지정한 LLM 모델이다. 테스트 전용 프롬프트 선택이나 provider별 시스템 템플릿 분기는 제공하지 않는다.

후속 배포: 아래 코드 개발·오프라인 검증 이후 사용자가 별도로 활성화·재배포를 승인했다. 새 작성 지침 v2와 시스템 규칙 v2.6을 현재 로컬 서비스에 적용했으며 [실제 배포 기록](Deployment_Common_Prompt_v2.6_2026-09-08.md)을 따른다. 실제 LLM 품질 재평가는 하지 않았다.

## 공통 지침 v2.6

코드의 시스템 지침은 `waf-system-v2.6`, 조합한 지침은 `waf-judgment-v2.6/policy-N`으로 기록한다. 반복 설명과 예시를 압축하고 원문 근거·디코딩 경고·판정 기준·보고서 작성 역할을 정리했다.

| 문자 수 기준 | 이전 v2.5 | v2.6 |
| --- | ---: | ---: |
| 공통 시스템 규칙 | 4,136 | 2,681 |
| 신규 설치 기본 편집 지침 | 696 | 359 |
| 기본 지침을 조합한 Primary 전체 | 5,018 | 3,226 |

기본 조합은 문자 수 **35.7%**, UTF-8 바이트 수는 10,209 → 6,637로 **35.0%** 감소했다. 정확한 모델 토큰 수·출력 토큰 감소율·지연시간이나 정확도 개선율이 아니다. 기존 DB의 편집 지침은 보존하므로 실제 조합 길이는 저장된 버전에 따라 다르다.

핵심 변경과 유지 조건:

- 시그니처가 다르거나 공격 성공·취약 제품이 미확인이라는 이유만으로 정상 요청으로 판단하지 않는다.
- 정탐은 공격 시도와 영향의 성립 조건을 구분하고, 오탐에는 정상으로 볼 구체적 맥락이 필요하다. 서버 규칙에 따라 의미가 갈리는데 해당 조건이 없으면 보류한다.
- 프롬프트만 짧게 하며 판정 근거를 부실하게 줄이지 않는다. 관찰·의미·판정 연결을 필요한 만큼 설명한다.
- 비신뢰 입력, 원문 정확 발췌, 심각도 계약, 보류/확정 후 추가 확인 구분, JNDI 미실행·조건부 디코딩 경고를 유지한다.
- Primary와 Verifier의 역할 지침은 서로 다르지만 양쪽 서비스 용도에서 동일하게 사용한다. Verifier에 Primary 결론을 전달하지 않는다.
- 판정 결합·출력 계약·근거 검증·Retry·모델 선택·필드 정보의 `history_only`는 변경하지 않는다. 모델별 추론 옵션과 입력 예산 예약량도 변경하지 않는다.

Gemma 4는 system 역할을 지원한다. 이전 Gemma의 사용자 메시지에 지침을 합치는 방식이나 특수 제어 토큰을 이 앱에 추가하지 않았다. [Google의 Gemma 4 공식 형식](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)을 확인했지만, 이 문서는 이번 WAF 프롬프트의 품질 향상이나 긴 지침에 대한 취약성을 입증하지 않는다.

## 버전과 적용 범위

**설정 → 프롬프트**의 활성 버전 하나를 새 Production·Test 접수 모두 사용한다. 저장·복제와 활성 적용은 별개이며 버전은 불변이다. 적용한 시점 이후의 새 접수만 바뀐다.

이미 접수된 테스트·Production·대기 작업은 암호화된 전체 Primary/Verifier 지침과 당시 버전을 유지한다. 현재 코드나 활성 버전이 바뀌었다고 과거 이력을 다시 쓰지 않는다. 재선점·출력 교정에서도 같은 스냅샷을 사용한다. 따라서 서로 다른 접수 시점의 과거 실행 버전은 다를 수 있지만, 용도 때문에 다른 프롬프트를 선택하지 않는다.

새 기본 편집 지침은 최초 초기화에만 사용한다. **기존에 저장·활성화한 지침을 코드 배포가 자동으로 덮어쓰지 않는다.** 기존 환경에서 편집 지침까지 바꾸려면 [간결 지침 원문](prompts/compact_policy_v1.md)을 검토해 새 버전으로 저장하고, 양쪽 새 접수에 영향을 주는 공통 적용을 별도로 결정한다. 공통 시스템 규칙 v2.6은 같은 새 코드로 API와 worker를 배포한 뒤의 새 접수에 반영된다.

테스트 JSON·multipart로 `prompt_policy_version_id`, `fixed_rules_version`, `prompt_template`을 지정하는 기능은 제공하지 않는다. 조회 응답의 `prompt_policy_version_id`는 실제 접수한 버전의 읽기 전용 정보다. Production 입력 계약과 예약 필드 목록은 그대로다.

## 결과 비교 사용법

**분석 결과 → 테스트 → 실행 상세 → 다른 테스트와 비교**에서 비교할 기존 실행을 이름으로 찾는다. 두 실행은 저장된 결과만 읽으며, 이 화면은 새 분석 접수·프롬프트 적용·LLM 호출을 하지 않는다.

기준 실행과 동일 이벤트·참고 답안으로 새 테스트를 만들려면 테스트명을 지정하고 같은 파일을 새 접수 키로 업로드한다. 새 테스트는 그때의 공통 활성 프롬프트와 Test 모델을 사용한다. 시작 버튼은 실제 모델 호출·외부 전송·비용이 발생할 수 있으므로 조회와 구분한다. 같은 접수 키·같은 내용의 재전송은 원래 실행을 반환한다.

## 비교 대상과 해석

`GET /api/v1/test-runs/{candidate_id}/comparison?baseline_id={baseline_id}`는 관리자 전용 읽기 API다. `limit`(1~200, 기본 25), `offset`, `changes_only`를 지원한다. 비교는 해당 두 실행 전체를 대상으로 하며, 실행 상세의 난이도·유형 필터와 독립적이다. 페이지·변경 문항 필터는 비교 요약의 분모를 바꾸지 않는다.

- 파일의 중복 행은 독립 표본으로 늘리지 않고, 각 실행에서 접수된 문항끼리 Event ID로 대응시킨다.
- Event ID뿐 아니라 **정규화 이벤트 지문**이 같아야 한다. 지문 누락·내용 변경·한쪽에만 있는 문항은 별도로 제외한다. 원문을 복호화하거나 응답에 넣지 않는다.
- 각 문항의 **접수 당시 답안**과 출처 구분·AI 열람 여부를 대조한다. 사후 최신 Label로 과거 평가 기준을 바꾸지 않는다.
- 양측이 실제 판정 평가에 적격인 공통 쌍만 같은 분모로 집계한다. 실패·미완료·stub·출처 불명·답안 오염·답안 없음은 오답으로 만들지 않는다.
- `improved`는 기준의 답안 불일치가 후보에서 일치로, `regressed`는 그 반대로 바뀐 경우다. 둘 다 불일치인 판정 변화까지 개선으로 판단하지 않는다. 근거 설명의 의미적 타당성을 자동 채점하지 않는다.
- 이진 미탐·과탐과 확정 판정 기준 Accuracy/Precision/Recall/F1은 기존 [공통 평가 기준](Test_Runs_and_Evaluation_v0.1.md)을 따른다. 보류·커버리지와 기대 보류 답안의 일치 여부를 함께 확인한다.

모델 설정·Verifier 임계값·입력 스키마·시스템 규칙이 다르거나 확인할 수 없으면 경고한다. 같은 이벤트라도 실행별 `source_system`과 프롬프트의 입력 예산·절단 범위 때문에 실제 직렬화 입력은 달라질 수 있다. 모델의 비결정성이나 코드·파서 변경까지 통제한 실험이라는 보장도 없다. 따라서 두 실행의 차이를 **프롬프트만의 인과 효과**로 단정하지 않는다.

## 시간과 토큰

성능 비교의 범위는 품질 비교가 가능한 **동일 문항 쌍**이다. 처리 시간은 최초 선점부터 완료까지로 큐 접수 대기와 구분하며, 선점 이후 복구 대기는 포함할 수 있다. LLM 단계 시간은 기록된 논리 단계의 실측 시간이고 내부 재시도·검증 시간을 포함한다.

토큰은 기록된 Primary/Verifier 단계의 허용된 숫자 카운터만 합산한다. 한 단계의 교정 시도 중 해당 카운터가 하나라도 누락되면 그 카운터의 단계 전체를 미측정으로 제외하며, 완전 계측 단계 합계와 결측 단계 수를 반환한다. 교정 시도별 사용량이 있으면 그 목록을 사용하고 최상위 마지막 시도 사용량을 중복 합산하지 않는다. 미측정·이전 문자열형·유효하지 않은 값은 미측정으로 표시한다. 측정값 합계와 결측 건수를 함께 보며, 비교에서 제외된 실패 문항의 호출 비용이나 전체 네트워크 재시도 비용까지 계측한 청구액으로 해석하지 않는다. 모델별 가격·달러 금액은 자동 추정하지 않는다.


## 기존 기준선과 다음 검증

기존 [gpt-5.4-mini 30건 결과](evaluations/Verifier_GPT54Mini_30_2026-09-08.md)와 JSON 기록을 그대로 보존한다. 실행 ID는 `3decdd13-e135-4314-8c85-d4a6cd85c849`이다. 아직 새 v2.6 지침으로 재실행하지 않았다.

다음 실제 검증은 공통 지침 적용 범위·Test 모델 설정·합성 문항·비용을 확인한 뒤 별도로 합의한다. 이전 30건은 개선에 사용한 개발 표본이며 나머지 120건도 같은 합성군이므로 독립 운영 검증셋으로 표시하지 않는다. 사람의 답안·근거 검수와 함께 미탐·과탐·보류·근거 정확성·시간·토큰을 확인한다. 평가와 사람의 검수를 함께 쓰는 원칙은 [OpenAI Docs의 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 참고했다. 외부 Evals 서비스는 연결하지 않는다.

## DB·배포와 검증 경계

기존 `0012_input_schemas`까지의 TestRun·Analysis·프롬프트·Label·AgentStep 구조를 재사용한다. 새 DB 마이그레이션이나 운영 패키지는 없다. 새로운 조사 Agent·도구·자동 승격은 포함하지 않는다.

개발 검증은 합성 데이터·메모리/임시 SQLite·모의 Agent와 HTTP 응답으로 수행한다. 실제 LLM 품질·외부 전송·과금, 실행 중인 Docker 반영, 운영 부하는 별도 검증 대상이다. 이번 작업은 공통 코드와 테스트만 변경하며 운영 프롬프트 활성화·DB·Docker 재배포·GitHub 게시는 수행하지 않는다.

### 오프라인 회귀 결과 — 2026-09-08

- Backend 전체 수집 1,318개. `test_[a-l]*.py`와 `test_[m-z]*.py`로 분할 실행하고, 변경된 지침 문구 검사와 샘플 디렉터리 미마운트 항목을 `test_analyst_guidance.py`·`test_upload_expected_labels.py` 85개 재실행으로 확인했다. 최종 범위는 1,318개 모두 통과이며 남은 건너뜀은 없다. 격리된 테스트 이미지에서 네트워크 없이 실행했고 `/samples`에는 합성 데이터만 읽기 전용으로 마운트했다.
- 공통 프롬프트 접수 회귀 20개는 용도별 다른 모델에서도 같은 역할 지침 사용, 활성 변경 전 작업 보존, 멱등 재전송, 테스트별 지침 선택 거부와 손상 시 안전한 실패를 확인한다. 지침 경계 21개와 비교 API 19개도 전체 범위에 포함한다.
- Frontend는 Node 24의 `node --test --test-isolation=none src/*.test.mjs`로 277개 통과했고 Vite production build도 통과했다. 빌드 성공은 실행 중인 UI 재배포를 의미하지 않는다.
- 기존 뒤로/앞으로 탐색 브라우저 회귀 9개와 `frontend/scripts/prompt-comparison-smoke.mjs`의 공통 접수·파일 업로드·비교/탐색 3개가 통과했다. 요청에 테스트별 지침 선택값이 없는지, 통신 재전송 키와 비교 조건이 유지되는지 확인했다. 390px 화면에서 페이지 가로 넘침 없이 표 내부 스크롤이 동작한다. API는 모두 모의 응답이며 실제 API 요청·LLM 호출은 없다.

Backend에는 기존 Starlette/AnyIO 사용 중단 예정 경고 1종이 남아 있다. 위 검증은 프롬프트 의미 준수·정확도·Gemma tokenizer 한도나 운영 지연시간을 입증하지 않는다.
