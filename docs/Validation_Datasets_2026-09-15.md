# 검증 데이터 관리

2026-09-15 후속 요청으로 로컬 Docker 재배포와 실제 서비스 조회·화면 점검을 완료했다. DB는 `0017_validation_data`이며 기존 데이터·현재 모델·지침·키를 유지한다. 아래 오프라인 검증과 미배포 설명은 구현 당시 기록이다. 최신 적용·백업·검증 범위는 [배포 기록](Deployment_Validation_Data_2026-09-15.md)을 따른다.

## 합의한 범위

- 데이터셋과 문항을 관리하고 분석 결과를 복사한다. 원본 분석은 변경하지 않는다.
- 문항 입력 전체를 편집할 수 있다. 입력이 같으면 이벤트 ID가 달라도 중복으로 처리한다. 답안이 다르면 충돌로 알리고 덮어쓰지 않는다.
- 문항과 데이터셋 구성은 버전으로 보존한다. 삭제는 목록에서 숨기는 방식이며 이전 테스트는 보존한다.
- 답안이 없는 문항도 판정을 실행한다. 답안 없음과 보류 답안을 구분하며 답안 없는 문항은 점수에서 제외한다.
- 참고 답안과 메모는 개별/일괄 등록하며 변경 이력을 보존한다. LLM에는 전달하지 않는다.
- 테스트 당시 답안은 유지한다. 수정 답안으로 재평가하면 LLM 호출 없이 별도 평가 버전을 만든다.
- 운영에서 복사한 문항은 수정 후에도 내부 vLLM 전용이다. Primary, Verifier, 근거 정리 및 재실행에 적용한다.
- API 키의 용도는 발급 시 고정한다. Test 키는 Test 모델·동시 처리 설정을 사용하며 Production 결과에 접근하지 못한다.
- Test API 요청은 선택적으로 테스트 실행에 묶는다. 실행을 닫으면 새로운 항목을 받지 않는다.
- 보고서의 본문 폭을 넓히고 정탐 근거·오탐 근거·참고 내용을 구분한다.

## 저장 및 보안

0017 마이그레이션으로 데이터셋, 변경 불가능한 문항 버전과 구성 버전, 재평가 기록을 추가한다. API 키 용도와 분석의 내부 전송 제한을 저장한다. 기존 키는 Production으로 유지한다. 참고 답안의 보류도 허용한다.

문항 입력 전체와 메모는 기존 암호화 서비스를 사용한다. 원문 조회는 관리자 권한과 감사 기록을 적용한다. 데이터셋의 삭제·수정으로 원본 분석, 접수된 테스트의 입력·답안·모델 설정이 바뀌지 않는다. 운영 데이터 재사용은 서비스 기능에 한정하며 실제 사내 로그를 개발 테스트나 fixture에 넣지 않는다.

## 검증 범위

새 기능의 오프라인 테스트와 프런트엔드 빌드를 수행한다. 실제 LLM 호출, 운영 DB 변경, Docker 재배포, GitHub 게시는 별도 요청 범위다.

2026-09-15 검증 완료:

- 전체 백엔드 1,968건 실행: 1,961건 통과. 기존 Production 키가 Test 결과까지 조회한다고 가정한 5건과 0008 DB를 최신 ORM으로 검사하던 2건을 새 계약·해당 당시 스키마에 맞게 조정했다.
- 관련 API·기능·마이그레이션 172건 재검증 및 보류 집계·권한 분리 29건 추가 검증 모두 통과. 전체 실행과 후속 검증을 테스트 ID별 최신 결과로 합치면 1,971개 케이스가 통과했다. 최종 전체 재실행 한 번으로 얻은 수치는 아니다.
- 프런트엔드 36개 테스트 파일 통과, Vite 빌드 통과. 기존 500KB 초과 번들 경고는 남아 있다.
- 가상 API를 사용하는 Chromium 점검: 데이터셋 생성·문항 편집·뒤로 가기·일괄 답안·데이터셋 복사/실행·Test 키 발급·모바일 배치 통과. 실제 백엔드와 브라우저를 함께 구동한 통합 검증은 아니며 백엔드 API는 별도 테스트로 확인했다.
- 실제 이전 DB 구조를 만든 임시 DB에서 0017 업그레이드·반복 적용·원문/키/답안 보존·FK 검사를 통과했다. 실제 서비스 DB에는 적용하지 않았다.

실제 vLLM 동시 처리·장시간 대량 테스트·운영 로그의 모델 판정 품질·실환경 백업 복구는 이번에 검증하지 않았다. 운영에서 가져온 문항의 OpenAI 접수 차단과 세 역할의 전송 직전 차단은 외부 호출 없는 테스트로 확인했다.

브라우저 검증 스크립트: `scripts/verify_validation_data_ui.mjs`. 프런트엔드를 빌드한 후 설치된 Playwright 드라이버 경로, Chromium 실행 파일 경로, 결과 디렉터리를 차례로 인자로 전달한다. 신규 운영 의존성은 없다.

## 사용 흐름

1. 데이터 관리에서 데이터셋을 만든다. 문항을 직접 입력하거나 분석 결과의 현재 페이지에서 항목을 선택해 데이터셋에 추가한다.
2. 동일 입력은 event_id만 제외하고 비교한다. 답안이 다르거나 기존 문항보다 더 엄격한 전송 제한이 필요하면 충돌로 알리고 추가하지 않는다. 중복 가져오기 자체가 기존 문항의 답안·메모를 변경하지 않는다.
3. 데이터셋 상세에서 문항의 원문·추가 필드·답안·메모를 편집한다. 이전 버전을 선택하면 읽기 전용으로 당시 내용을 본다. 운영 복사 문항은 수정 후에도 내부 모델 전용이다. 수동 편집한 답안은 분석가 참고 답안으로 기록한다.
4. 테스트 분석 → 검증 데이터셋 분석에서 선택하고 실행한다. 새 TestRun에 데이터셋 버전과 입력·답안·모델·지침을 고정한다. 이름을 비우면 자동 생성한다. 현재 스키마에 맞지 않는 문항이 하나라도 있으면 실행 전체를 접수하지 않는다.
5. 분석 결과의 개별 또는 일괄 참고 답안을 저장할 수 있다. 기존 답안이 있는 개수를 저장 전에 안내한다. 변경한 답안은 목록·개별 비교에 즉시 적용하지만 기존 테스트 점수는 유지한다.
6. 테스트 결과에서 수정 답안으로 재평가하면 당시 최신 답안을 별도 평가 버전으로 저장한다. 평가 기준을 전환해 접수 당시 평가와 재평가를 볼 수 있다. 문항 처리나 API 접수가 진행 중이면 재평가를 막는다.

## 관리자 API

모든 아래 경로는 `/api/v1` 기준이고 관리자 세션이 필요하다. 데이터셋 변경 시 `expected_revision`을 보내며 다른 사용자가 먼저 변경했으면 409다. 원문 조회는 감사 기록과 `Cache-Control: no-store`를 적용한다.

| 작업 | 경로 |
| --- | --- |
| 데이터셋 목록·생성 | `GET/POST /validation-datasets` |
| 상세·이전 버전·수정·삭제 | `GET/PATCH/DELETE /validation-datasets/{id}` |
| 분석 결과 복사 | `POST /validation-datasets/{id}/imports` (`analysis_ids`, `expected_revision`) |
| 문항 추가 | `POST /validation-datasets/{id}/items` |
| 문항 상세·수정·삭제 | `GET/PUT/DELETE /validation-datasets/{id}/items/{item_id}` |
| 데이터셋 판정 실행 | `POST /validation-datasets/{id}/runs` (`expected_revision`, `name`, `idempotency_key`) |
| 선택 분석의 답안 버전 확인 | `POST /evaluation-labels/selection` (`analysis_ids`) |
| 참고 답안 일괄 저장 | `POST /evaluation-labels/bulk` (`targets`, `verdict`, `comment`, `idempotency_key`) |
| 답안·메모 이력 | `GET /analyses/{id}/evaluation-labels` |
| 재평가 목록·생성 | `GET/POST /test-runs/{id}/evaluations` |
| 재평가 결과 | `GET /test-runs/{id}?evaluation_id={evaluation_id}` |

문항 쓰기는 `event`, `reference_verdict`(null 가능), `comment`, `case_name`, `difficulty`, `test_category`, `expected_revision`을 받는다. 문항 상세의 `version_id` query는 문항 버전 ID이며, 데이터셋 상세의 `revision` query는 데이터셋 구성 버전 번호다. 논리 문항 ID와 개별 버전 ID는 구분한다. 단일 선택은 같은 일괄 API에 한 건을 보낸다. 일괄 저장의 targets는 `{analysis_id, expected_revision}` 배열이다.

일괄 선택은 최대 500건, 데이터셋·테스트는 최대 5,000행이다. 목록은 페이지 단위로 조회한다. 삭제는 과거 이력을 없애는 개인정보 삭제 기능이 아니며 보존·파기 정책에 따른 별도 운영 절차가 필요하다. 답안 없는 문항은 판정만 실행한다. 실패·대기·모의 결과는 기존 평가 제외 정책을 유지한다.

Test 서비스 키의 접수·그룹 관리 계약은 [Production/Test API](Production_API_v0.1.md)의 Test API 키 사용 절을 따른다. 동일 event_id를 새로 판정하려면 새로운 test-session을 만든다. 용도·연동 시스템이 같아도 서로 다른 테스트 실행의 리뷰 중복 키는 독립적이다.

## 배포 시 주의

다른 서버에 배포할 때에도 기존 worker를 중지하고 일관된 DB 백업을 확보한 뒤 `alembic upgrade head`를 적용해야 한다. 새 ORM 모델은 구버전 스키마에서 기동할 수 없다. 데이터셋·Test 키·새 답안 이력을 사용한 후 0017 downgrade는 차단한다. 복구에는 배포 전 백업과 당시 암호화 키가 필요하며 배포 이후 데이터를 잃지 않도록 현재 DB도 먼저 보존하고 이전 절차를 검토한다. 새 스키마 필드 때문에 과거 0008만 적용한 DB를 최신 ORM으로 검사해서는 안 된다.
