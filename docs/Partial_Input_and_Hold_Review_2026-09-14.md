# 부분 로그·보류 안내 보완 — 2026-09-14

## 결과와 적용 범위

[이전 보완의 다음 작업](Context_Judgment_v2_2026-09-14.md#다음-작업) 1~2번을 구현했다. HTTP 버전만 빠진 부분 로그의 본문 상태를 제한적으로 검사하고, 최종 보류에 기록된 확인 조건 또는 관련 근거 검토를 상세·보고서로 연결한다.

**코드·오프라인 검증 범위다. 재배포, 실제 LLM 호출, 설정 활성화, Git 작업은 하지 않았다.** 실행 중 서비스는 기존 v2.10이다. 아래 변경만으로 판정 정확도나 보류율이 개선됐다고 볼 수 없다. 이전 평가의 운영 확대 보류 권고를 유지한다.

## 1. 부분 로그 입력 검사

새 처리 규칙은 `waf-system-v2.12`, 새 접수 버전은 `waf-judgment-v2.12/policy-N`이다. **v2.11과 지침 문구는 동일하며**, 입력 검사 계약을 실행 시점에 고정하기 위한 버전 변경이다. Production/Test 및 Primary/Verifier에 같은 기준을 적용한다.

- `request-integrity-v2`는 파서 경고가 HTTP 버전 미인식 하나뿐이고 요청 줄이 두 요소로 끝나는 경우만 추가 검사한다. 요청·헤더 경계가 불명확하거나 다른 파싱 경고가 있으면 기존처럼 미지원으로 남긴다. `parse_status=partial` 자체는 보류 원인이 아니다.
- 명시된 Content-Length가 유효하고 서로 일치할 때, 수집본의 빈 본문 또는 선언보다 짧은 ASCII 본문을 관찰한다. 프로토콜을 HTTP/1.1로 채우거나 빠진 본문을 복원하지 않는다. 파서 상태도 success로 바꾸지 않는다.
- Transfer-Encoding이 있거나, 비어 있지 않은 본문이 비ASCII·압축 등으로 바이트 길이를 비교할 수 없으면 검사하지 않는다. 서로 다른 길이 선언·깨진 헤더·이스케이프된 줄바꿈·없는 구분자·크기 제한 초과도 부분 로그 경로에서는 추정하지 않는다. JSON·chunked 추가 분석은 기존 HTTP/1.0·1.1 성공 경로만 사용한다.
- 수집본 전체가 모델 입력에 포함되고 검사 결과도 생략되지 않았을 때에만 해당 관찰을 판정 제한에 사용한다. **영향 구간을 근거로 한 정상 판정만** 보류로 제한한다. 공격 판정이나 다른 온전한 구간에 있는 근거는 일괄 보류하지 않는다.
- 길이는 선언됐지만 본문이 없으면 Content-Type 헤더도 영향 구간에 포함한다. 본문 없이 `application/json` 등 형식 선언만을 정상 근거로 사용할 수 없도록 한 것이다. 원문 출처의 위치 겹침은 보수적 제한 기준이지 모델의 의미 해석을 증명하는 것은 아니다.

Content-Length는 원래 메시지의 바이트 수를 나타내므로 Unicode 수집 텍스트의 문자 수를 무조건 원본 바이트 수로 취급할 수 없다. [RFC 9112의 메시지 본문 길이 규칙](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)을 참고하되, 이번 검사는 원본 통신 검증이 아닌 **수집된 텍스트의 제한적 대조**다. 본문이 없거나 짧다는 관찰만으로 수집기 장애·공격·실제 서버 처리 방식을 단정하지 않는다.

## 2. 보류 이유와 확인 항목

| 기록된 상태 | 표시 방식 |
| --- | --- |
| 실제 정상 판정 제한 사유가 본문 없음 | “요청 본문 확인 필요”: 길이는 선언됐지만 수집된 로그에는 본문이 없다고 설명 |
| 실제 사유가 선언보다 짧은 본문 | “본문 길이 확인 필요”: 수집 생략과 실제 입력의 길이 문제를 구분하도록 안내 |
| 실제 사유가 닫히지 않은 JSON | “JSON 본문 확인 필요”: 닫는 구문과 실제 입력 규격 확인 안내 |
| 근거에 연결된 미확인 조건이 있고 확인 항목이 비어 있음 | 저장된 조건을 그대로 옮기고 관련 근거 번호·확인 위치 안내를 덧붙임 |
| 근거 해석은 있으나 추가로 필요한 조건이 기록되지 않음 | 관련 발췌와 판단 이유를 대조하도록 안내. 추가 자료가 반드시 필요하다고 표현하지 않음 |
| 서버 결합에서 보류했지만 판단 쟁점이 없음 | 저장된 요청 근거의 위치와 번호에 연결해 해석 검토 안내. 새로운 미확인 조건은 만들지 않음 |
| 실행 오류·근거 대조 실패 | 기존 기술 문제 안내가 우선. 업무 자료 확인 요구로 바꾸지 않음 |

`input_integrity_observed`, 파서 partial 또는 일반적인 본문 관련 문구만 보고 원인을 고르지 않는다. 실제 `input_integrity_limited` 및 `downgraded_to_inconclusive=true`와 영향 코드가 함께 기록된 경우에만 구체화한다.

화면·Markdown·PDF·Excel이 같은 기준을 사용한다. 기존 구체적 확인 항목은 보존하고, 보류의 표시 목록이 비어 있을 때만 보완한다. 확정 판정의 빈 목록을 채우지 않는다. 완전히 같은 확인 항목만 중복 제거하고, 근거나 목적이 다른 항목은 유지한다. **문장이 유사하다는 이유로 의미를 합치거나 반대 근거를 삭제하는 기능은 추가하지 않았다.**

저장된 `analyst-assessment-v1`의 유효한 근거 연결만 사용한다. 중복 식별자·잘못된 연결·미지원 버전·근거 없는 레거시 결과에서 조건을 만들어내지 않는다. 중간 Primary/Verifier 결과나 원문을 추가로 읽어 과거 판정을 다시 판단하지 않는다. 새로 붙인 안내는 표시용이며 API의 저장된 `result`에 소급 저장하지 않는다. 사람이 실제 확인을 완료했다는 기록도 아니다.

## 3. 호환성과 보존

- v2.9~v2.11로 고정된 과거 실행은 `request-integrity-v1` 동작과 요약을 유지한다. 그 이전의 원문 후보·지침·출력 계약도 유지한다.
- v2.12의 파서 이력, 양 역할의 입력, 최종 진단, 전처리 버전 목록에 선택된 v2를 기록한다. 역할별 원래 판정·근거, 암호화된 원문·지침 스냅샷은 변경하지 않는다.
- 조회 시 설명이 개선되는 과거 결과도 저장된 판정·요약·근거를 덮어쓰지 않는다. 모델 입력에 새 확인 안내를 역으로 주입하지 않는다.
- DB 스키마, 운영 의존성, API 결과 버전 `waf-analysis-v2`, 관리자 편집 지침, 모델 배정, Primary→조건부 독립 Verifier→서버 정책 구조는 유지한다. LLM 파서·오케스트레이터·외부 조회를 추가하지 않았다.
- 운영 API 정의서 원본과 패키지 사본에 코드 버전과 제한 범위를 함께 반영했다. 재배포 전에는 실행 중인 정의서가 바뀌지 않는다.

## 오프라인 자료 대조

기존 파싱 난이도·Hard·Medium 각 50건과 별도 요청 의미 검수 자료 18건의 파일 해시는 이전과 같다. 입력 검사만 v1/v2로 비교했으며 **모델 판정 재평가가 아니다.** [집계 JSON](evaluations/Partial_Capture_Offline_2026-09-14.json)에 관찰 코드와 해시를 보존했다.

- 파싱 자료의 `waf-parser-v1-005`: 기존 미지원 → 명시된 길이에 비해 수집된 본문이 없음을 관찰.
- `waf-parser-v1-004`: 기존 미지원 → 제한된 길이 대조에서 문제 미관찰. 원문 완전성이나 정상 요청의 증명은 아니다.
- 나머지 파싱 48건, Hard 50건, Medium 50건, 별도 18건의 관찰 코드·상태는 동일하다. 기존 본문 없음 사례의 영향 구간에는 v2의 Content-Type 확장이 있으므로 최종 판정까지 동일하다는 의미는 아니다.
- 전체 168건 중 추가로 발견된 관찰은 본문 없음 1건이다. 이 숫자는 정답 일치 증가나 보류 감소 건수가 아니다.

## 검증

테스트는 임시 DB·가짜 모델 출력·공개 테스트 자료만 사용했다. 실제 운영 DB·볼륨과 LLM은 연결하지 않았다.

- 전체 백엔드: **1,907항목 통과**, 613.36초. Starlette/AnyIO의 사용 중단 예고 경고 1건, 실패 0건. 읽기 전용 코드·지원 파일과 네트워크가 차단된 임시 Python 3.12 컨테이너에서 `pytest -o addopts= -q -p no:cacheprovider`로 실행했다.
- 새 입력 검사·보류 안내 회귀 72항목은 위 전체 수에 포함된다. 미지원 형식·크기 한도·원문 증명 생략·영향 구간 제한·과거 스냅샷·양 역할 동일 입력·기존 암호문 보존·PDF/Excel 출력 등을 검사했다.
- 전체 프런트엔드: **402항목 통과**, 27.84초. Node 22 임시 컨테이너에서 `node --test --test-reporter=spec --test-concurrency=1 src/*.test.mjs`를 실행했다. 정의서와 백엔드 공유 fixture도 읽기 전용으로 연결했다.
- 공유 보류 사례 21개를 Python/JavaScript 양쪽에서 대조했다. 정탐·오탐·실패·레거시·잘못된 연결·없는 근거·우선순위·악성 HTML 문자열·입력 불변을 포함한다.
- 실제 React 화면: **24개 확인 통과**. 12개 상태 × 데스크톱/모바일 다크 테마에서 요약·근거 양쪽 배치·확인 항목 순서·보고서 일치·넘침·스크립트 오류·HTML 비실행을 검사했다. `frontend/scripts/decision-explanation-smoke.mjs`가 모든 API를 fixture로 가로채며 실제 API·LLM 호출은 0회다. 임시 Vite 서버와 브라우저는 종료했다.
- Vite 배포 빌드 성공. JS 묶음 518.21 kB로 500 kB 초과 경고가 남아 있다. 이번에는 별도 코드 분할이나 패키지 변경을 하지 않았다. 빌드 산출물은 `/tmp`에만 두었고 실행 중 UI는 교체하지 않았다.
- 기존 150건·별도 18건 파일 해시 및 운영 API 문서 두 사본의 바이트 일치를 확인했다.

초기 새 백엔드 테스트의 Excel 셀 비교를 XML 객체에서 실제 셀 텍스트 비교로 바로잡았고, 프런트엔드 격리 실행의 문서 경로 누락을 수정한 뒤 위 전체 검사를 통과했다. 이는 실제 LLM 출력이나 판정 정확도 검증을 대체하지 않는다.
