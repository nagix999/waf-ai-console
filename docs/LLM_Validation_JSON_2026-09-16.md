# LLM 출력 형식 검증 보완

2026-09-16 코드 변경입니다. GitHub 게시 대상은 `nagix999/waf-ai-console`의 `main`이며 기존 v0.2.0 버전과 태그는 유지합니다. Docker 재배포·실제 Qwen/Gemma 호출은 하지 않았습니다. 기존 [9월 15일 기록](LLM_Validation_Output_2026-09-15.md)의 256토큰 상한에 관한 안내보다 이 문서가 우선합니다.

## 적용 내용

연결·기능 검증의 ‘출력 형식’ 항목은 다음 값만 요청합니다. `status`, `code`, `message` 모두 JSON Schema의 `enum`으로 고정하고, 응답을 받은 뒤에도 필드·타입·값을 검사합니다. 중복 키와 JSON 표준에 없는 상수도 허용하지 않습니다.

```json
{"status":"ok","result":{"code":200,"message":"OK"}}
```

vLLM 연결·기능 검증은 `min(1024, 프로필의 max_output_tokens)`를 출력 상한으로 사용합니다. 실제 WAF 분석 한도와 프로필 설정 자체는 바꾸지 않습니다. 프로필 한도가 256이면 새 검증도 256이며, 1,024보다 커도 검증 상한은 1,024입니다. 상한을 늘린 것이지 매번 1,024토큰을 생성하도록 요구하는 것은 아닙니다. 길게 생성하는 모델의 검증 시간은 늘 수 있습니다.

OpenAI도 같은 짧은 JSON으로 출력 형식을 검증하지만 출력 한도는 기존 프로필 값을 유지합니다. 실제 WAF 판정 형식 검증은 그대로입니다. vLLM의 `temperature=0`, `enable_thinking=false`와 공급자별 요청 옵션도 유지합니다.

## 실패 원인과 기록

- 서버가 `finish_reason=length`를 반환하면 기존처럼 `vllm_output_incomplete` 또는 `openai_output_incomplete`입니다. JSON이 이미 완성되어 있어도 실패합니다.
- 정상 종료했지만 JSON 문법·필드·값이 맞지 않으면 `json_schema_validation_failed`입니다. JSON 문법 오류를 통신 응답 오류와 구분합니다.
- 검증을 자동 재시도하거나 실패를 통과로 바꾸지 않습니다. 연결·기능 검증 실패 시 선택한 데이터셋 평가는 시작하지 않습니다. 실제 Primary/Verifier의 응답 교정 재시도는 별도 기능입니다.

설정 → LLM 공급자 → 검증 결과 → 확인 내용에서 기존 토큰 표 아래에 ‘응답 상태’를 표시합니다. JSON 요청에 대해서만 다음 메타데이터를 기존 `response_diagnostics[].json_output`에 추가합니다.

| 필드 | 의미 |
| --- | --- |
| `status` | `complete`, `complete_with_trailing_content`, `invalid_or_incomplete`, `empty`, `unavailable`, `inspection_limit` 중 하나 |
| `content_chars` | 응답 텍스트 문자 수. 추론 토큰 수가 아님 |
| `trailing_whitespace_chars` | 끝부분의 JSON 공백·줄바꿈 문자 수 |
| `trailing_content_chars` | 첫 JSON 값 뒤에 남은 추가 내용의 문자 수. 앞뒤 공백 제외 |
| `repeated_suffix_unit_chars`, `repeated_suffix_count` | 끝부분에서 확인한 동일 문자열의 길이·연속 반복 횟수 |

기록할 수 없는 값은 `null`입니다. 문법상 완성된 JSON이라는 관찰과 검증 통과는 다릅니다. 미완성 JSON과 잘못 작성된 JSON은 응답만으로 확실히 구분할 수 없어 ‘JSON 미완성 또는 문법 오류’로 표시합니다. 특정 서버 설정이 원인이라고 단정하지 않습니다.

형태 검사는 최대 65,536자·중첩 깊이 64로 제한합니다. 반복 검사는 끝부분 최대 4,096자 안에서 1~64자 단위가 최소 4회, 총 32자 이상 정확히 반복되는 경우만 기록합니다. 비슷한 문장을 의미상 비교하지 않으며 전체 응답의 반복 횟수로 해석하면 안 됩니다. 길이·깊이 한도 초과는 형태 확인을 생략하고, 짧은 고정 JSON 검증도 실패 처리합니다.

응답 원문, 반복 문자열 자체, 추론 텍스트, 거절 문구, API Key는 기록하지 않습니다. 관리자 조회 API와 검증 이력 저장을 통해 고정된 상태·숫자만 전달합니다. 과거 검증 기록을 수정하거나 누락 값을 추정하지 않습니다.

## 유지하는 범위

새 DB 컬럼·마이그레이션·운영 의존성은 없습니다. 기존 검증 상태, 모델 배정, 공통 지침, 실제 분석 출력 한도, 동시 처리 설정, 내부 연결 제한을 유지합니다. 서버 이미지·reasoning parser·chat template 설정도 바꾸지 않았습니다.

## 검증

관련 백엔드 **339개 테스트 통과**, 프런트엔드 **42개 테스트 파일 통과**, UI 빌드 성공입니다. 백엔드 전체 테스트를 실행한 결과는 아닙니다. 기존 Starlette/AnyIO 폐기 예정 경고와 프런트엔드 번들 크기 경고는 남아 있습니다.

실제 서버가 아닌 가상 응답으로 다음을 확인합니다.

- 고정 JSON 요청, 공급자별 출력 한도, 낮은 프로필 한도 보존
- JSON이 완성된 경우에도 출력 중단·거절 차단, 자동 재시도 없음
- JSON 문법 오류·잘못된 값·중복 키 구분, 길이·깊이 제한
- 공백·반복·추가 출력 메타데이터와 원문·추론 내용 미저장
- worker 저장 및 관리자 API 조회, 검증 실패 뒤 데이터셋 평가 차단
- 기존 프로필 지정·동시 처리·Primary/Verifier 교정 동작 회귀 테스트
- 화면의 기존 기록 호환성·응답 상태 표시 및 UI 빌드

실제 운영 Qwen의 성공률 개선이나 장애 해소는 아직 확인하지 않았습니다.

## 배포 후 최소 확인

1. 기존 Qwen 프로필에서 검증 동시 요청 수를 1로 유지합니다.
2. 먼저 간단 검증으로 ‘모델 연결 → 기본 응답 → 출력 형식’을 확인합니다. 이후 데이터셋 평가 없이 전체 연결·기능 검증을 실행합니다.
3. 새 기록의 출력 한도가 `min(1024, 프로필 한도)`인지 확인합니다. 과거 기록의 256은 그대로 남습니다.
4. 실패하면 종료 사유, 출력 한도·사용량, 응답 상태만 확인합니다. 원문이나 인증 키는 공유할 필요가 없습니다.
5. 1,024토큰에서도 중단되면 공백·반복·추가 출력 관찰에 따라 서버의 채팅 템플릿·종료 처리·사고 모드 적용 여부를 별도 비교합니다. 상한 증가만으로 해결되었다고 간주하지 않습니다.
