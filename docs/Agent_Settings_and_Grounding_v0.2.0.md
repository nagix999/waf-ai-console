# Agent 설정·원문 근거 검증 1차 개선

> 후속 변경: [원문 인용 교정 v2](Evidence_Citation_Repair_v2_2026-09-10.md)가 아래 전체 결과 재작성·일부 근거 탈락 후 확정 설명에 우선한다. 역할별 모델과 기존 설정 API는 유지하며, 새 교정은 인용만 수정하고 미해결 근거가 남으면 보류한다. 활성 지침·실행 중 Docker는 이번 후속 코드 작업으로 변경하지 않는다.

2026-09-10 구현 계약. 기존 문서의 단일 Primary/Verifier 프로필 설명과 근거 탈락 즉시 보류 설명에 우선한다. 코드·가상 데이터 검증 범위이며 운영 데이터·실제 LLM의 정확도 개선을 입증한 기록은 아니다.

## 설정 화면

설정 → **Agent 설정**에서 다음을 관리한다.

- 모델 배정: Production·Test 각각 Primary와 Verifier 선택. Primary 미지정과 Verifier의 **Primary와 동일** 선택을 명확히 구분한다.
- 공통 지침: 기존 불변 프롬프트 버전 저장·복제·비교·적용·복귀를 그대로 사용한다. Test/Production의 지침을 분리하거나 기존 버전을 덮어쓰지 않는다.
- 처리 현황: 최근 7/30/90일, 전체/Production/Test의 보류·교정·실행 실패 집계. 내부 절차는 이 기술 화면에 두고 일반 분석가의 설명에 강제로 추가하지 않는다.

LLM 프로필 탭에는 연결 주소·공급자·API Key·연결/기능 검증을 유지한다. 기존 프롬프트 북마크 `#settings/prompts`는 `#settings/agents`로 연결한다. 모델 배정과 지침 적용은 각각 명시적으로 저장하며 서로를 암묵적으로 변경하지 않는다.

## 모델 선택·보안

Primary는 기존 `status=production`, `is_test` 지정을 재사용한다. `agent_configurations`의 두 Verifier 참조가 null이면 해당 용도의 Primary를 사용한다. 새 설치와 업그레이드 기본값은 모두 기존 단일 모델 동작이다. 다른 용도의 Primary나 다른 provider로 장애 우회하지 않는다.

네 역할 모두 현재 설정 지문과 일치하는 전체 검증 성공이 있어야 새로 배정한다. 별도 Verifier로 배정된 프로필은 편집·비활성화를 거부하므로 먼저 Agent 설정에서 해제/교체한다. 기존 Primary 비활성화 API의 지정 해제 동작은 유지한다. OpenAI가 어느 한 역할에라도 있으면 UI·API에서 외부 전송과 비용을 다시 확인한다. 이 확인은 사내 데이터 반출 승인을 대신하지 않는다.

프로필별 자격·URL·승인·API Key를 확인하고 각 역할·교정·전송 재시도 직전에 최신 프로필 지문과 연결 허용을 재검사한다. API Key를 역할/provider 간 복사하지 않는다. 실제 OpenAI 또는 vLLM 호출은 테스트에서 수행하지 않는다.

일반 테스트는 접수 당시 두 모델의 ID/지문을 `test_runs.profile_metadata`에 고정한다. Production은 최초 실행 시작에 두 모델을 고정한다. `analyses.execution_snapshot_ciphertext`의 v2 스냅샷은 두 프로필과 기존 지침·스키마·이벤트 연결 정보를 포함하며 재선점·실패 재실행에서도 재사용한다. 현재 배정을 바꿔도 고정한 모델을 바꾸지 않는다. 모델 비활성화·설정 변경·연결 허용 철회 시에는 이후 요청을 차단한다.

이전 v1 실행 스냅샷과 Verifier 기록이 없는 기존 이름 있는 테스트는 **당시 Primary와 같은 모델**이라는 기존 계약을 유지한다. 후보 150건 모델 검증은 설정된 Agent 조합이 아니라 **선택한 후보를 양 역할에 사용**한다. 후보 자격 검증에 다른 모델의 판정이 섞이지 않게 하기 위함이다. 서로 다른 두 프로필을 사용하는 판정 품질은 별도의 이름 있는 테스트로 평가해야 한다.

## 공통 입력·근거 검증

`generic-http-v3`가 요청 힌트와 원문 문자 위치 `raw_source_spans`를 함께 생성한다. 근거 검증은 별도의 HTTP 요청 라인 정규식 대신 같은 결과를 사용한다. 프로토콜이 없거나 불완전해도 구간이 식별된 쿼리·헤더·본문의 근거는 인정할 수 있다. HTTP/2 표기를 인식하며, 헤더 종료가 없으면 본문을 생성하지 않는다. 해석 불가능한 요청은 전체 `payload` 인용만 가능하다.

원문·Cookie는 수정하거나 마스킹하지 않는다. 문자로 저장된 `\\r\\n` 등 모호한 줄바꿈을 일괄 복원하지 않는다. 벤더별 복원·LLM 보조 파싱은 이번 범위가 아니다. URL 쿼리 이름은 원문 이름을 힌트로 전달하며 디코딩한 이름으로 필드를 찾지 않는다. 특정 필드에 없는 문자열을 전체 payload에서 찾았다는 이유로 통과시키지 않는다.

두 프로필의 `context_window - max_output_tokens` 중 작은 값을 공통 입력 예산으로 사용한다. 기존 지침 예산 외에 근거 교정용 2,048 토큰 추정 여유를 예약한다. 실제 tokenizer 상한 보장이 아니며 예전 실행보다 입력이 더 잘릴 수 있다. 필드 정의 설명은 기존처럼 암호화 이력에만 기록하고 LLM 입력에는 넣지 않는다.

## 근거 오류 교정

각 역할의 구조화된 출력에 대해 원문 검증을 수행한다. 근거가 하나라도 탈락하면 해당 역할에만 한 번 교정을 요청한다. 오류 코드와 인덱스는 서버가 만들고, 이전 필드명·발췌문은 비신뢰 user JSON으로 전달한다. 이 값들을 system 지침으로 보간하지 않는다. 이전 판정을 유지하도록 강요하지 않으며 정상 인용 또는 필요한 보류로 수정할 수 있다.

- `source_not_found`: 지정한 원문 필드를 식별하지 못함.
- `excerpt_not_in_source`: 지정한 필드에 정확한 발췌문이 없음.
- `empty_excerpt`: 공백뿐인 인용.

교정 피드백은 최대 4,096자 안에서 항목 단위로 선택하고 생략 여부를 표시한다. 교정 요청에서 다시 출력 형식 교정을 시작하지 않는다. 한 역할의 논리적 실행은 최초 판정 + 기존 출력 형식 교정 최대 1회 + 원문 근거 교정 최대 1회이며, 각 호출의 기존 네트워크 재시도는 별도다. 두 역할 모두 최대 1회의 근거 교정이 가능하다.

교정 후에도 근거가 모두 탈락하면 기존 정책대로 보류·UNKNOWN으로 낮추고 튜닝 제안을 비활성화한다. 교정 호출 자체가 실패하면 Primary는 실행 실패, Verifier는 필요한 검증 실패로 최종 보류다. 형식이 맞는 마지막 결과가 있어도 근거가 없으면 확정하지 않는다. Verifier 실패·불일치의 보류 정책과 독립성은 유지한다.

`grounding_history`에 교정 전·후 구조화 출력과 교정 입력을 기존 Agent 단계 출력 암호화로 저장한다. raw provider body나 private reasoning은 저장하지 않는다. 일반 metadata에는 고정 오류 코드·근거 인덱스·건수·사용량·실행 식별자만 기록한다. 이력 조회는 기존 관리자 권한과 감사 기록을 사용한다.

근거 검증은 **출처와 문자열 일치**만 검사한다. 의미적으로 타당한 공격 근거인지 또는 실제 앱에서 같은 방식으로 해석되는지 보증하지 않는다.

## 진단·결과 계약

기존 `waf-analysis-v2` 결과에 서버가 작성한 선택 필드 `diagnostics`와 `agent.role_profiles`를 추가한다. 기존 `agent.model_profile_id` 등 단일 모델 메타데이터는 Primary를 뜻하며 각 역할의 실제 설정은 `role_profiles.primary/verifier`로 구분한다. 과거 결과에는 값을 추정해 채우지 않는다.

`diagnostics.roles`에는 최초 모델 판정, 교정·근거 검증 후 판정, 근거 강등 여부와 교정 여부를 기록한다. 보류 사유는 모델 자체 보류, 역할별 근거 탈락, 검증 실패, 판정 불일치로 나눈다. 파싱 불완전·입력 잘림은 별도 `input_signals`이며 원인으로 단정하지 않는다. 모델 자체 보류는 출력 상태의 분류이지 빠진 업무 정보가 실제 원인이었음을 입증한 분류는 아니다.

교정 성공은 원문 검사를 통과했다는 뜻이며 정답률 개선과 다르다. 보류 사유·교정 집계는 새 진단 버전으로 **완료한 분석** 기준이고 미기록·stub·실패는 보류율 분모에서 제외한다. 전체 실패는 별도 표시한다. LLM 실패 유형은 분석별 마지막 실행의 실패 단계만 집계하고 출력 형식 오류/출력 미완성/모델 거절/호출 실패로 구분한다. 여러 사유의 합은 보류 건수보다 클 수 있다.

최상위 usage와 교정 시도 usage는 중복 합산하지 않는다. 테스트 실행 비교는 근거 교정 안의 출력 형식 교정까지 합산하되 누락된 사용량을 0으로 만들지 않는다. `output_repair_steps`는 출력 형식 또는 근거 교정이 발생한 단계 수이며 같은 단계는 한 번만 센다. 실행 시간은 기존 단계 측정에 모든 교정이 포함된다.

## 관리자 API

- `GET /api/v1/admin/agent-settings`: revision, state_token, assignments, 검증 상태를 포함한 profiles 반환. 원문 키는 반환하지 않는다.
- `PUT /api/v1/admin/agent-settings`: `expected_state_token`, `production/test` 각각의 `primary_profile_id`, `verifier_profile_id`, `external_transfer_acknowledged`를 받는다. 네 배정을 원자적으로 변경한다. 조회 뒤 기존 용도 API·프로필·공통 지침이 바뀌면 409로 재확인을 요구한다.
- `GET /api/v1/admin/agent-settings/diagnostics?days=7&purpose=all`: 기간 1~90일, purpose=all/production/test. 원문·암호화 이력을 읽거나 LLM을 호출하지 않고 서버 집계만 반환한다. 재실행도 별도 분석으로 포함한다.

기존 `/model-profiles/{id}/promote`, `/assign-test`, `/unassign-test`는 Primary 지정 호환 API로 유지한다. 프롬프트 API도 이름·버전·이력을 그대로 유지한다. 모든 새 API는 관리자 전용이며 기존 Origin/CSRF 정책을 적용한다.

## 배포와 검증 범위

새 운영 패키지는 없으며 **Alembic `0014_agent_configuration`**이 필요하다. 기존 테이블/암호화 이력은 재작성하지 않는다. 운영에 적용할 때는 일관성 백업과 암호화 키 복구 가능 여부를 확인하고 API·두 worker를 중지한 뒤 마이그레이션, 같은 코드 버전의 API·worker·웹 UI 배포 순서로 진행한다. 혼합 버전 worker는 지원하지 않는다. 새 설정이나 실행 기록이 있으면 downgrade를 거부하며 롤백은 업그레이드 전 백업 복구가 필요하다.

실제 운영 DB 마이그레이션·Docker 재배포·실모델 호출·GitHub 게시는 이 구현 요청에서 수행하지 않는다. 운영 로그의 실제 파싱 형식, Gemma 토큰 예산, 교정 성공률·오판·지연시간은 내부 환경에서 별도 확인해야 한다.

### 로컬 검증 기록 · 2026-09-10

- Python 3.12, 프로젝트 기존 개발 의존성으로 백엔드 전체 회귀 **1,537건 통과**. 실행 중 보완한 교정 집계와 관련 회귀 **34건도 별도 재검증 통과**했으며 두 수치는 중복되므로 합산하지 않는다. Starlette/AnyIO의 폐기 예정 API 경고 1건은 남아 있다.
- 프런트엔드 자동 테스트 **29개 파일 통과**, Vite 운영 빌드 성공.
- 실제 Chromium의 데스크톱 밝은 테마·모바일 어두운 테마에서 모델 선택, 미검증 모델 선택 차단, 외부 전송 동의, 배정 저장, 공통 지침·처리 현황 이동, 브라우저 뒤로 가기와 가로 넘침을 확인했다. API는 모두 모의 응답이며 임시 확인 서버는 종료했다.
- 임시 DB에서 `0013` → `0014` 이전·재실행, 기존 Primary 배정과 검증 이력 보존, 설정 사용 후 안전하지 않은 downgrade 차단을 확인했다. 실제 데이터 볼륨은 사용하지 않았다.

### 후속 배포·실모델 평가 · 2026-09-10

사용자의 별도 요청으로 기존 로컬 Docker에 `0014`와 동일 버전의 API·worker·웹 UI를 배포했다. 배포 전 백업 및 기존 행·암호화 값 보존을 확인하고, 새 파싱 난이도 50건과 기존 hard50을 `gpt-5.4-mini`로 실제 실행했다. 100건 완료·기대 라벨 80건 일치이며 운영 데이터 또는 Gemma4의 정확도 향상을 입증한 결과는 아니다. 상세 내용은 [100건 평가 보고서](evaluations/Parser_Stress_GPT54Mini_100_2026-09-10.md)를 참고한다. 기존 구현 단계의 미검증 범위와 이번 후속 평가를 구분하며, 기대 라벨과 판정 정책은 평가 중 변경하지 않았다.
- 서로 다른 provider의 역할 분리, 공통 입력·Verifier 독립성, 근거 교정 횟수 제한, 암호화된 전후 이력, 당시 두 역할로 실패 재실행, 전송 직전 Verifier 사용 차단, 후보 150건 검증의 후보 모델 격리를 모의 LLM으로 확인했다.

실행 명령: 백엔드 `.venv/bin/python -m pytest -o addopts='' -q`, 프런트엔드 `node --test src/*.test.mjs`, `node node_modules/vite/bin/vite.js build`. 브라우저 점검 스크립트는 `frontend/scripts/agent-settings-smoke.mjs`이며 로컬 Vite `127.0.0.1:15173`과 사전 설치한 Playwright·Chromium을 사용한다. 운영 의존성 추가나 브라우저 패키지 자동 설치는 하지 않는다.
