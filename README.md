# WAF AI Analysis Console v0.2.0

WAF 이벤트를 비동기로 접수하고 AI 분석 결과와 분석가 리뷰, Agent 실행 이력을 관리하기 위한 내부용 MVP 골격입니다.

현재 버전은 용도별로 지정한 검증된 Production·Test LLM 프로필(vLLM / OpenAI)을 ModuAgent에 연결하고, Primary/Verifier 정책으로 구조화된 판정을 생성합니다. 안전한 초기 기동을 위해 Docker Compose 기본값은 여전히 명시적인 `stub` 모드입니다.

## 빠른 실행

```bash
docker compose up --build
```

- UI: http://localhost:8080
- API 문서: http://localhost:8000/docs
- 기본 관리자: `admin` / `change-me-now`
- 서비스 API 키: 관리자 로그인 후 설정 → 서비스 API Key에서 발급(기본 키 없음)

위 기본값은 로컬 확인 전용입니다. 내부 환경에 배포할 때는 반드시 `.env.example`을 복사해 비밀번호, 세션 비밀키, 암호화 키를 교체하고 서비스 API Key는 관리자 설정에서 발급하세요.

## 로컬 개발

백엔드:

```bash
cd backend
python -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
alembic upgrade head
uvicorn app.main:app --reload
```

워커:

```bash
cd backend
python -m app.worker
```

프론트엔드:

```bash
cd frontend
npm install
npm run dev
```

## 입력 스키마·필드 정보 버전 관리 — v0.2.0

**설정 → 입력 스키마**에서 기존 11개 필드를 기본으로 새 버전을 복제하고 필드 설명·필수·null 허용·타입·길이·숫자 범위·허용값·객체/배열 구조를 정의합니다. 기존 필드의 이름·타입과 최소 계약은 보호하고 추가 필드는 자유롭게 설정합니다. 서버 제어값과 정답 필드는 등록할 수 없습니다. 저장한 버전은 수정·삭제하지 않으며, 합성 샘플이 해당 버전의 접수 기준을 통과해야 별도로 적용할 수 있습니다. 이전 버전 복귀도 같은 검증 절차를 사용합니다.

새 접수의 분석·이름 있는 테스트·후보 검증에는 당시 필드 정의를 암호화해 고정합니다. 재전송·재시도·적용 버전 변경은 이를 바꾸지 않습니다. **필드 설명은 LLM 입력에 추가하지 않습니다.** Agent 입력 단계의 암호화 이력에 전체 정의를 남기고 일반 메타데이터는 버전·지문·필드 수만 제공합니다. 과거 완료 데이터에 버전을 추정해 채우지 않고, 과거 미완료·미기록 작업은 원래 기본 11개 정의와 `legacy_default` 출처로 기록합니다.

현재 적용한 정의는 Production 접수 검증, Production API 화면과 Markdown 다운로드, `/openapi.json`에 같은 기준으로 반영됩니다. 설정 변경 뒤 열려 있는 문서는 새로고침하세요. 추가 필드의 타입은 엄격히 검사합니다. CSV는 기존 포트만 숫자로 변환하므로 숫자·객체·배열 추가 필드는 JSON 업로드를 사용하세요. 미등록 벤더 필드는 기존처럼 보존하며, 새로운 검색 컬럼·필드 매핑·LLM 출력 스키마 편집은 이번 범위가 아닙니다.

**Alembic `0012_input_schemas`**가 필요하며 새 운영 패키지는 없습니다. 이번 릴리스는 코드·테스트·GitHub 게시 범위이며 실행 중인 Docker와 운영 DB는 변경하지 않습니다. 배포 전 일관성 백업과 암호화 키 복구 가능 여부를 확인하고 모든 worker를 중지한 뒤 마이그레이션 및 같은 버전의 API·worker 배포를 진행하세요. 상세 계약은 [입력 스키마 정의서](docs/Input_Schemas_v0.2.0.md)를 참고하세요.

## 테스트 실행 관리·공통 평가 지표 — 2026-09-07

**테스트 분석**에서 직접 입력·파일 업로드마다 테스트명을 입력하고, 설정의 150건 판정 평가에도 이름을 지정합니다. 실행 이력에서 이름으로 찾고 난이도·유형별 문항 및 지표를 확인합니다. 같은 파일의 새 실행은 이전 결과를 보존하며, 같은 접수의 통신 재전송은 동일 접수 키로 중복 실행을 방지합니다. 테스트명·난이도·문항명·답안은 모델 입력에서 분리합니다. 기존 일반 테스트는 실행 묶음 없이 보존합니다.

**분석 결과 → 테스트**는 테스트명으로 찾는 실행 목록을 기본으로 표시합니다. 테스트명을 누르면 해당 실행의 Confusion Matrix·평가 지표와 문항별 분석 결과를 한 화면에서 확인합니다. 문항 상세에서 돌아오면 평가 범위·문항 필터·페이지가 유지되고, 실행 목록으로 돌아오면 테스트명 검색과 페이지가 유지됩니다. 직접 입력·파일 접수 결과와 설정의 새 150건 검증 결과도 같은 실행 상세로 연결합니다. **전체와 프로덕션은 기존 단건 분석 목록·검색·평가 지표를 유지**합니다.

테스트 탭의 **테스트 문항 전체 보기**에서는 이름 있는 실행과 실행 묶음이 없는 이전 분석을 함께 검색합니다. 과거 자료를 날짜나 파일명으로 추정해 묶거나 새 테스트명을 생성하지 않습니다. 이 개별 목록은 최신 참고 답안을 사용하고, 이름 있는 실행 상세는 접수 당시 고정 답안을 사용합니다. 테스트명 검색·문항 검색·운영 검색 조건은 분리합니다. 이 화면 연결 수정은 프런트엔드만 변경하며 DB·API·LLM 호출 정책을 바꾸지 않습니다. 실행 중인 Docker에는 별도 재배포 전까지 반영되지 않습니다.

**분석 결과의 테스트와 프로덕션 모두** 현재 검색 범위 전체의 참고 답안 평가를 제공합니다. Accuracy/Precision/Recall/F1 외에 Specificity, 과탐률·미탐률, Balanced Accuracy, Macro F1, MCC와 커버리지·보류율·보류 포함 정답률·답안 연결률을 표시합니다. 각 지표 옆 `?`에 마우스를 올리거나 키보드로 포커스하면 정의와 높고 낮을 때의 의미를 확인합니다. Production은 답안이 있는 표본만 평가하며 일부 표본의 수치를 전체 트래픽 정확도로 표현하지 않습니다.

이진 지표는 확정 판정 기준이며 보류와 기대 보류 답안을 구분합니다. 실패·미완료·stub 등은 별도 제외 건수로 남기고 빈 분모는 계산 불가입니다. 출처·AI 열람 여부별 집계를 유지합니다. 새 테스트 실행은 접수 당시 답안을 고정하고 일반 분석 목록은 최신 답안을 사용하므로 사후 정정 시 기준이 다를 수 있습니다.

이 변경은 **Alembic `0010_test_runs`**가 필요하고 새 운영 패키지를 추가하지 않습니다. 기존 분석·Label·암호화 원문을 보존하며 일반 Production 접수 계약을 변경하지 않습니다. API, 수식·분모, 모델 고정, 백업·마이그레이션 절차는 [테스트 실행 및 평가 정의서](docs/Test_Runs_and_Evaluation_v0.1.md)를 참고하세요.

## 테스트 분석·프롬프트 관리 — 2026-09-07

**테스트 분석** 메뉴에서 직접 입력과 파일 업로드를 전환합니다. 기존 테스트 분류·유입 기록·업로드 오류 안내·결과 이동·Label 평가는 유지하며 별도 모델·큐를 만들지 않습니다. 분석 상세와 보고서는 기존 순서를 유지하면서 원문 위치를 읽기 쉬운 이름과 정확한 필드 경로로 표시하고 내용 없는 정황·정책 제안 카드를 생략합니다. 실제 제한이나 위험 설명은 보존합니다.

**설정 → 프롬프트**에서는 판정·작성 지침을 최대 4,000자로 저장하고, 미검증 안내를 확인한 뒤 별도로 운영 적용합니다. 보안 규칙·출력 계약·판정 결합은 읽기 전용입니다. 새 접수에 전체 지침을 암호화해 고정하므로 운영 버전 변경·재시도·재선점이 기존 작업의 지침을 바꾸지 않습니다. 자동 평가·후보 비교 실행은 후속 범위입니다.

이 기능에는 **Alembic `0006_prompt_policies`**가 필요하며 새 외부 의존성은 없습니다. 저장/적용 구분, 최초 기본 지침 등록, 기존 작업 처리, 관리자 API와 백업·배포 주의사항은 [프롬프트 버전 관리 정의서](docs/Prompt_Policies_v0.1.md)를 참고하세요. 실제 모델의 문체·인용 정확성·입력 한도는 별도 검증해야 합니다.

## GPU 없는 로컬 검증 범위

### 1차 안정화 — 2026-09-07

- 범용 파서는 요청 라인·HTTP 버전·헤더 형태와 헤더 종료 구간을 확인하고, 인식하지 못한 입력은 `failed`, 일부만 인식한 입력은 `partial` 힌트로 전달합니다. 잘못된 URI로 분석이 중단되지 않도록 처리하며 원문이나 본문의 이스케이프 문자열을 자동으로 고치지 않습니다. `success`는 HTTP 메시지 길이·전송 프레이밍·공격 성공을 검증했다는 뜻이 아닙니다.
- 새 parser 단계에 `parser_version=generic-http-v2`와 실제 `parse_status`를 기록합니다. 별도 Payload Extractor는 아직 없으므로 `fallback_llm_used=false`입니다. 파싱 불완전 시 같은 원문을 Primary에 전달하고 기존 조건에 따라 독립 Verifier를 실행합니다.
- 새 Agent 실행의 `usage`와 교정 시도별 `usage`는 `input_tokens`, `output_tokens`, `total_tokens`의 숫자/null 객체로 기록하고 provider 원문은 넣지 않습니다. 프레임워크가 누락된 사용량도 모두 0으로 만들기 때문에 전체가 0인 값은 미측정(null)으로 취급합니다. 최상위 `usage`는 마지막 교정 시도이며, 전체 사용량 계산 시 `output_validation_retry.attempts`와 중복 합산하면 안 됩니다. 이전 문자열형 사용량은 덮어쓰지 않습니다. API가 일부 카운터를 누락한 경우의 완전한 계측과 요금 계산은 별도 검증 범위입니다.
- 분석 상세는 대기/처리 중에만 자동 갱신하고 완료/실패 뒤에는 멈춥니다. Agent 입출력은 Agent 탭을 열 때만 조회합니다. 별도 창에서 변경한 Label·리뷰는 **새로고침**으로 다시 조회하며, 새로고침은 재분석이나 LLM 호출을 하지 않습니다. 일시적인 조회 오류는 제한된 횟수만 재시도하고 기존에 읽은 결과는 유지합니다.

이 변경에는 새 운영 패키지나 DB 마이그레이션이 없습니다. 기존 분석·Label·프롬프트와 판정 결합 규칙은 유지합니다. 파서 상태가 더 정확해지면 **새 분석**의 Verifier 호출 여부는 달라질 수 있으므로 실제 품질·지연시간 효과는 별도로 확인해야 합니다.

로컬 `stub` 모드는 UI와 접수·처리 흐름 확인용이며 실제 LLM 판정이나 품질 평가가 아닙니다. 대시보드와 메뉴의 실행 모드 표시는 **API 프로세스의 설정**을 의미하고 worker heartbeat나 GPU 연결 성공을 보장하지 않습니다. API와 worker 설정이 다르면 실제 실행도 다를 수 있습니다.

대시보드는 관리자 전용 `GET /api/v1/dashboard/summary?days=7`로 기간 내 Production 전체 건수를 집계합니다. 기간은 접수 시각 기준이며 테스트·기존 미분류는 제외합니다. 판정 분포와 우선 확인 항목은 해당 기간의 완료 분석 기준입니다. 최신 분석 표는 기간 선택과 별개인 전체 기간 최신 10건입니다. 판정 분포·완료율은 정확도 지표가 아닙니다.

모델 입력은 payload뿐 아니라 이벤트 메타데이터와 파싱 힌트를 포함한 전체 JSON의 길이를 제한합니다. 긴 URI가 파싱 힌트로 재유입되는 경우와 깊거나 큰 메타데이터를 제한하고 `input_truncation`에 축소 영역을 기록합니다. 저장 원문은 수정·마스킹하지 않습니다. `3 × (context_window - max_output_tokens - 4096)` 문자 예산은 추정치이며 실제 Gemma tokenizer·chat template 토큰 상한을 보장하지 않습니다. 최소 입력 공간도 부족하면 모델 호출 전에 `agent_context_budget_too_small`로 실패합니다.

기존 업로드 응답의 오류·바로가기 링크는 최대 100건입니다. 새 이름 있는 테스트 실행은 행 이력을 보존하고 상세에서 페이지 조회합니다. 테스트와 Production의 큐 공유는 유지하되 새 일반 테스트는 접수 당시 모델·프롬프트를 고정합니다.

## 운영 API와 검색

외부 연동 계약은 [Production API v0.2.0 기본 정의서](docs/Production_API_v0.1.md)와 현재 적용 스키마를 기준으로 합니다. `/docs`에서 `X-API-Key` 인증을 입력해 호출할 수 있으며 `/openapi.json`에도 인증과 v2 결과 구조를 제공합니다.

웹 UI의 **Production API** 메뉴 또는 `/#production-api`에서 정의서 전체를 볼 수 있습니다. 목차·본문 검색·예시 복사·Markdown 다운로드를 제공하며, `GET /api/v1/production-api`의 같은 서버 문서를 화면과 다운로드에 사용합니다. 입력 스키마 적용에는 프런트엔드 재빌드가 필요 없습니다. 일반 계약 템플릿 수정은 백엔드 패키지의 `app/data/production_api.md`에도 동기화해 배포합니다. UI Origin의 `/docs`와 `/openapi.json`도 API로 프록시합니다. 정의서 페이지는 요청을 실행하지 않지만 Swagger의 `Try it out`은 실제 API를 호출하며 관리자 세션이 서비스 키보다 우선하므로 주의하세요. Swagger 기본 화면은 외부 CDN 리소스를 사용하므로 완전한 격리망에서는 로딩이 제한될 수 있습니다. 정의서 페이지 자체에는 외부 리소스가 필요 없습니다.

운영 수집기는 기존 `POST /api/v1/analyses`, `POST /api/v1/uploads`를 사용합니다. 웹 테스트 분석은 관리자 전용 이름 있는 테스트 API를 사용합니다. 일반 테스트와 Production은 같은 worker 큐를 사용하되 새 테스트는 접수 당시 **Test 용도로 지정한 모델**을 고정합니다. Test가 없으면 실제 모델 테스트를 접수하지 않으며 Production으로 대체하지 않습니다. 후보 150건 검증만 별도 model-test worker를 사용합니다.

분석 결과에서 `전체 / 테스트 / 프로덕션`을 선택하고 이벤트·회사·IP·시그니처·위협 유형을 검색할 수 있습니다. 기간, 상태, 판정, 심각도, WAF Action, 벤더, 리뷰, 모델, 입력 잘림, 포트와 신뢰도 조건을 조합합니다. 목록의 총 건수는 필터와 권한 범위를 반영합니다. 암호화된 원문과 Agent 입출력은 검색 대상이 아닙니다.

이 변경은 Alembic `0003` 마이그레이션을 포함합니다. 기존 분석은 `legacy_unknown`(이전 미분류)으로 남기고 실제 저장된 심각도만 검색 컬럼에 복사합니다. 이전 결과 JSON과 Agent 이력을 변경하지 않습니다. 이전 단계는 실측 시간이 없어 `측정 전 데이터`로 표시합니다. 배포 전 SQLite 일관성 백업을 만들고 API의 `alembic upgrade head`가 끝난 뒤 worker를 시작해야 합니다.

전체 경과 시간은 접수부터 종료까지, 처리 시간은 worker 최초 선점부터 종료까지입니다. 진행 중에는 현재 시각까지의 경과를 보여 줍니다. 재선점·복구 대기도 처리 시간에 포함됩니다. 각 LLM 단계에는 네트워크 및 교정 재시도와 출력 검증을 포함합니다.

## 분석 결과 v2

새 분석은 `waf-analysis-v2` 계약을 사용합니다. 위협 분석에 `severity`를 포함하고, 판정 근거는 원문 발췌(`excerpt`)와 상세한 한국어 판정 해석(`interpretation_ko`)을 구분합니다. 별도의 `uncertainties` 목록은 생성하지 않으며, 추가 확인이 필요한 작업은 `recommended_checks`에 기록합니다.

서버는 각 발췌문이 지정한 `field`의 실제 원문에 존재하는지 검증합니다. 예를 들어 시그니처에만 있는 문자열을 `payload.query` 근거로 제시하면 제거합니다. HTTP 하위 구간은 원문 그대로 비교하고, 디코딩된 문자열·모르는 경로·다른 필드의 발췌문은 인정하지 않습니다. 출처 검증은 해석의 의미적 정확성이나 모델에 전달된 잘림 구간까지 보장하지는 않습니다. 유효한 원문 근거가 없는 정탐·오탐 결과는 `inconclusive`와 `UNKNOWN`으로 강등합니다.

현재 프롬프트 코드 기준은 `waf-judgment-v2.5`이며 결과 계약은 `waf-analysis-v2`를 유지합니다. 기존 v1/v2 결과와 실행 이력은 변경하지 않습니다. 이전 v2.4 입력·근거·분석가 UI 보강에는 DB 변경이 없었으나 프롬프트 버전 관리에는 `0006`이 필요합니다. 목적 분류와 검색 컬럼에는 기존 `0003`이 필요합니다. 이전 결과에 심각도가 없으면 UI에서 `미평가(이전 결과)`로 표시합니다.

### 분석가 안내와 인코딩 문자열 — 2026-09-07

- 상세와 보고서는 판정 요약 → 세부 분석 결과 → 판정 근거 → 나머지 정보 → **추가 확인 사항** 순서입니다. 보류에는 판정 구분에 필요한 확인을 안내하고, 정탐·오탐에는 영향 범위·대응 안전성 등에 실제로 유용한 선택적 후속 확인만 요청합니다. 확정 판정에서 확인이 없으면 섹션을 숨기며 신뢰도만으로 확인을 지우지 않습니다. 모델의 신뢰도는 보정된 정탐 확률이 아닙니다.
- 프롬프트는 같은 관찰을 반복한 근거를 만들지 않도록 요구합니다. 서버는 최종 결합 시 같은 출처·원문·해석의 완전 중복을 제거하고, 화면은 같은 출처·원문을 한곳에 모아 표시하되 다른 해석을 보존합니다. 유사한 문장이라는 이유로 근거를 삭제하지 않으며 의미상 반복 제거를 보장하는 검증은 아닙니다. 기존 결과와 개별 Agent 출력은 덮어쓰지 않습니다.
- 원문 출처 검증에서 일부 발췌를 제외했다는 시스템 안내는 추가 확인 업무가 아니라 해석 주의사항으로 표시합니다. 이전 결과의 동일한 시스템 문구도 저장 내용을 바꾸지 않고 화면에서 구분합니다.
- 기본 목록은 분석과 참고 답안 비교를 한 표로 제공합니다. 판정·심각도, 이벤트·요약, 회사·통신 정보, 참고 답안 비교, 전체 소요 시간, 접수 시각의 6열이며 WAF 조치는 상세와 필터에 보존합니다. 처리 상태는 행 배경과 문구로 구분하고 완료된 보류는 실패색으로 표시하지 않습니다. 상세의 답안 비교는 판정 요약 아래에 배치하며 출처·연결 이력은 펼쳐 확인합니다. 내부 판정 간 차이를 일반 안내로 제시하지 않으며, 모델·검증·실패 코드·단계 시간은 기술 정보에서 확인합니다. 보류와 실패, 모의 실행은 그대로 구분합니다.
- 새 모델 출력에는 선택 필드 `analyst_checks`가 추가됩니다. 각 항목의 `source_ko`는 확인할 자료, `check_ko`는 확인할 내용, `why_ko`는 판단에 도움이 되는 이유와 구분 조건입니다. 서버는 최종 결과에 `analyst_guidance`를 더합니다. 기존 `recommended_checks`와 판정 결합 정책은 유지하며, 이전 결과는 새로 분석하거나 덮어쓰지 않고 화면용 대체 안내만 사용합니다. 구체적인 안내 품질과 새 출력 스키마의 실제 모델 호환성은 실모델 검증이 필요합니다.
- `waf-text-decoder-v2` 로컬 도구가 URL percent, legacy `%uNNNN`, 세미콜론이 있는 HTML 엔티티, `\uNNNN`/`\xNN`/`\u{...}`, 표준/URL-safe Base64 후보와 Log4j 스타일 조회식 난독화를 검사합니다. Base64 패딩이 생략된 충분히 긴 텍스트 후보에는 보완 가정을 명시하며 비정규 pad bits·잘못된 padding·혼합 alphabet은 거부합니다. `+`를 공백으로 바꾸거나 UTF-8 아닌 바이트, 압축, 임의 hex/octal/CSS 문법을 추정 해석하지 않습니다. 후보가 없다고 정상 요청이나 인코딩 부재를 뜻하지 않습니다.
- JNDI 자체는 문자 인코딩이 아니라 조회식입니다. `${lower:...}`/`${upper:...}`의 ASCII 문자열과 중첩 식을 정적으로 단순화하고 `${::-j}`/`${:-j}`는 속성 미정 조건의 기본값 후보로만 표시합니다. `${env:...}`/`${sys:...}` 등 실제 환경값과 `$${...}` 지연 조회식은 남기며 JNDI·LDAP·RMI·DNS·환경 조회를 실행하지 않습니다. 변환하지 않은 조회식은 원본=결과, 단계 0개와 경고로 표시합니다. 존재만으로 취약 Log4j 사용이나 침해 성공을 뜻하지 않으며 Agent는 버전·설정·로그 도달 경로·외부 연결 기록 등 확인할 자료를 안내합니다.
- 각 항목에 원문 문자 위치·디코딩 전 문자열·변환 결과·단계가 있습니다. 최대 원문 검색 262,144자, 후보 시도 256회, 표시 20개, 원문 조각 1,024자, 결과 4,096자, 연속 변환 3단계 및 JSON 출력 32 KiB로 제한합니다. 한 정적 해석 단계 안의 Log4j 조회식은 중첩 깊이 8·노드 128·연산 예산 65,536으로 별도 제한합니다. 제한·오류는 정해진 경고로 표시하고 원문을 고치거나 디코딩한 코드/URL을 실행하지 않습니다. Base64 등은 해석 후보이며 실제 애플리케이션이 같은 방식으로 처리했다는 증거가 아닙니다.
- worker는 디코딩 도구를 모델 호출 전에 결정론적으로 실행합니다. Primary와 Verifier에는 동일한 원문 및 예산에 맞는 파생 힌트를 전달하며, 실제 제출된 연속 원문 구간 안에 있는 항목만 포함합니다. 파생 항목을 일부만 잘라 가짜 변환 결과를 만들지 않습니다. 원문 발췌 검증은 디코딩 전 문자열을 기준으로 유지합니다. 이 도구 때문에 별도 LLM 호출은 추가하지 않습니다.
- 디코딩과 입력 구성 단계의 입출력은 기존 Agent 암호화 저장을 사용하고, 일반 결과 JSON에는 전체 디코딩 내용을 복사하지 않습니다. `agent.tools=[]`는 그대로이며 `agent.preprocessors`가 사용한 도구 버전을 기록합니다. 이는 모델이 선택해서 호출한 ModuAgent Tool이 아닙니다.
- 상세의 **인코딩 문자열**을 펼치면 기존 관리자 전용 원문 API를 통해 조회 시점 도구의 결과를 확인합니다. 원문과 동일한 접근 감사를 남기며 과거 모델이 그 결과를 보았다고 표시하지 않습니다. 이미 조회한 디코딩만 보고서에 포함하며 보고서가 원문을 자동으로 조회하지는 않습니다.

### 분석 보고서

분석 결과의 상세 화면에서 **보고서** 탭을 선택하면 **보고서 보기 / Markdown 원본**으로 전환할 수 있습니다. 저장된 분석 상세를 고정 템플릿으로 정리하며 두 보기는 같은 Markdown을 사용합니다. 기본 본문은 판정·심각도·상세 근거·구체적 확인 항목·튜닝 자문·소요 시간과 이미 조회한 디코딩을 포함합니다. Label 평가·독립 검증·모델/프롬프트는 **평가·실행 부록 포함**을 선택할 때만 넣습니다. 추가 LLM 호출, 결과 재판정, 별도 보고서 저장, 신규 운영 의존성·DB 변경은 없습니다. 템플릿은 프론트엔드 빌드에 포함됩니다.

진행 중·실패한 분석은 최종 보고서가 아님을 표시하고, 저장된 메타데이터가 stub 실행을 나타내면 실제 LLM 판정과 구분합니다. 이전 결과의 누락 항목은 추정하지 않습니다. 보고서에는 판정 근거로 저장된 원문 발췌가 포함되지만 HTTP 전체 원문·Agent 단계 입출력은 포함하지 않으며, 이 자료의 기존 관리자 조회·감사 정책은 그대로 유지합니다. 모델 텍스트와 발췌문은 HTML·링크·외부 이미지로 실행되지 않는 일반 텍스트로 표시합니다.

### 정답 Label 연결과 평가

별도 분석/평가 보기 전환 없이 한 목록에서 판정과 참고 답안을 확인합니다. 답안 비교 필터는 항상 접근할 수 있고, 적용된 검색 조건은 태그로 표시합니다. **참고 답안 연결** 버튼으로 연결 양식을 열고, **비교 집계**를 펼쳐 현재 검색 범위 전체의 집계를 확인합니다. 답안이 없으면 대시를 표시하지만 평가 정보 누락·조회 오류·평가 제외를 답안 없음으로 처리하지 않습니다. 상세에서는 답안이 있는 경우 요약 아래에 비교를 표시하고 출처·이력은 접어 둡니다.

분석 결과 화면의 **참고 답안 연결**에서 정답 파일을 선택하고 원래 분석의 `source_system`을 지정합니다. 이전 일반 테스트의 source는 `admin-ui`이며, 새 실행은 테스트 상세의 정확한 `source_system`을 사용합니다. 미리보기에서 연결 대상과 미연결·중복·변경 항목을 확인한 뒤 명시적으로 확정하세요. 매칭 키는 `event_id` 단독이 아니라 **정확한 `(source_system, event_id)`**이며, 없는 분석을 생성하거나 LLM을 다시 호출하지 않습니다. 현재 목록의 검색 조건은 파일 연결 범위를 제한하지 않습니다.

Label은 이벤트와 분리된 추가형 이력으로 저장합니다. 새 Label로 정정해도 이전 이력·AI 최종 결과·분석가 리뷰는 유지됩니다. 미리보기 이후 다른 Label 변경이 있으면 다시 미리보기해야 합니다. 리뷰의 `confirmed`는 AI 정답 여부가 아니고 `deferred`는 정답 `inconclusive`로 자동 변환하지 않습니다.

`samples/waf-dummy-v1/reference/*_answers.json`은 **합성 기대값**으로 연결하세요. 이 파일들은 측정된 모델 성능이나 검증된 정답이 아닙니다. 실제 참고 정답과 합성 기대값, AI 결과를 보고 작성한 답안·보지 않은 답안·열람 여부 미확인을 구분합니다. `inconclusive` 참고값은 합성 기대값의 기대 보류에만 허용하며 이진 정답 지표와 분리합니다.

목록·상세·보고서는 Label과 **정책·Verifier를 거친 최종 AI 판정**을 비교합니다. 미탐(참고 정탐 → AI 오탐), 과탐(참고 오탐 → AI 정탐), 모델 판단 보류, 기대 보류의 일치 여부를 구분합니다. Label이 없거나 분석이 미완료·실패·stub인 경우에는 오답으로 세지 않습니다. 실행 출처를 확인할 수 없는 이전 결과도 별도로 표시합니다.

평가 집계는 현재 페이지가 아니라 **권한과 적용된 검색 조건에 맞는 전체 분석**을 대상으로 합니다. 출처·AI 열람 여부별 건수와 분모를 함께 표시하며, 합성 기대값 또는 AI 지원 판정과의 일치율을 독립적인 정확도로 해석하면 안 됩니다. 모델이 보류한 표본도 별도로 집계하고 확정판정 coverage를 표시합니다. 심각도 채점, 모델·프롬프트 비교, 재분석은 이번 범위가 아닙니다.

별도 Label 이력 테이블은 Alembic `0005`를 사용합니다. 운영 패키지 의존성은 추가하지 않습니다. Label 연결은 입력 fingerprint·암호화 원문·Agent 입력을 변경하지 않습니다. Production과 기존 직접 입력 이벤트는 `label`, `expected_verdict` 등 정답 필드를 계속 거부합니다. 테스트 파일은 최상위 답안·난이도·유형·문항명을, 새 직접 테스트는 이벤트와 분리된 답안·분류 필드를 받습니다. 이벤트를 검증·저장하기 전에 분리해 같은 트랜잭션에서 참고 답안으로 연결합니다. `true_positive` / `false_positive` / `inconclusive`를 지원하며 누락·JSON null·CSV 빈칸은 답안 없음입니다. 같은 접수 키의 재전송은 최초 실행을 반환하고, 새 키의 실행은 이전 답안·분석을 보존하며 별도 분석을 만듭니다. 최신 답안 정정은 별도 연결의 미리보기·확정 절차를 사용하세요. 과거에 이미 모델에 전달된 정답 정보는 사후 Label 연결로 제거되거나 독립 평가로 바뀌지 않습니다.

`samples/waf-dummy-v1/all_150.json`과 난이도별 50건 파일 모두 기존 참고 답안의 `expected_verdict`를 포함합니다. 업로드 결과의 `label_attached` / `label_unchanged`로 연결 건수를 확인하고 분석 완료 후 목록·상세·보고서에서 비교합니다. 파일의 답안은 합성 기대값이며 AI 열람 여부는 미확인으로 기록합니다. 임의의 payload 본문이나 중첩 필드 속 정답 문장까지 제거하는 기능은 아닙니다.

## 서비스 API Key 관리

**설정 → 서비스 API Key**에서 수집기/연동 시스템별 키를 발급하고 이름 수정·폐기할 수 있습니다. LLM 공급자 인증 키와는 별개입니다. 유효기간은 없으며 관리자가 폐기할 때까지 사용할 수 있습니다. 원문은 발급 응답에서 한 번만 표시하고 DB에는 고엔트로피 키의 SHA-256 해시와 공개 식별자만 저장합니다. 안전한 비밀 저장소로 옮긴 뒤 닫으세요. 원문 재조회·폐기 취소는 없습니다.

키마다 `source_system`과 `ingest` / `review` 권한을 지정합니다. 같은 source의 키들은 분석 조회 범위와 중복 접수 기준을 공유합니다. 발급 후에는 이름만 수정할 수 있고 source·권한 변경은 새 키 발급 후 기존 키 폐기로 진행합니다. 생성·폐기·마지막 인증 시각을 표시하며 마지막 인증 시각은 DB 쓰기를 줄이기 위해 최대 분당 한 번 갱신합니다. 관리자 권한은 서비스 키에 부여하지 않습니다.

**환경변수 기반 배포 키는 제거했습니다.** `WAF_BOOTSTRAP_API_KEY`, `WAF_BOOTSTRAP_SOURCE_SYSTEM`, `WAF_BOOTSTRAP_API_KEY_ENABLED`가 이전 배포 설정에 남아 있어도 새 버전은 이를 읽거나 인증에 사용하지 않습니다. 기존 키를 자동으로 DB에 등록하지 않으며 기본 서비스 키도 없습니다. 새 버전 배포 후 관리자가 키를 발급하고 연동 시스템을 변경해야 합니다. 관리자 로그인은 기존 방식으로 유지합니다. 관리자 API와 전환 절차는 [서비스 API Key 정의서](docs/Service_API_Keys_v0.1.md)를 참고하세요.

## LLM Provider 등록과 검증

설정의 **LLM 프로필**에서 provider를 선택합니다. 프로필 등록은 설정 저장만 수행하며 모델을 호출하지 않습니다. provider 전체에서 **Production과 Test를 각각 최대 하나씩** 지정합니다. 같은 프로필을 양쪽에 명시적으로 지정할 수 있지만 자동 공유·전환이나 다른 provider로의 장애 우회는 없습니다.

두 용도 모두 **현재 설정 지문과 일치하는 전체 검증 성공 이력**이 있어야 지정할 수 있습니다. 빠른 테스트만 통과한 프로필은 지정할 수 없습니다. Production은 운영 API, Test는 웹의 직접 입력·파일 업로드에 사용합니다. Test 미지정 시 실제 모델 테스트는 차단하며, 명시적인 `stub` 모드는 모의 실행으로 유지합니다. 150건 후보 검증은 역할 지정 전 모델을 검증하는 과정이므로 선택한 후보를 직접 사용합니다.

Production·Test 지정 중인 프로필은 수정할 수 없습니다. 다른 검증 프로필로 교체하거나 지정 해제/비활성화한 뒤 수정하고 전체 검증을 다시 수행하세요. Test 지정 변경은 이미 접수된 이름 있는 테스트의 고정 모델을 바꾸지 않습니다. 비활성화는 해당 프로필의 용도 지정을 해제하며 이름 있는 테스트의 이후 모델 요청을 차단합니다. 다시 활성화해도 자동 재지정하지 않고 전체 검증부터 다시 수행해야 합니다.

이 구분에는 **Alembic `0011_model_test_role`**가 필요합니다. 기존 Production·프로필·검증·분석 이력은 보존하고 Test는 미지정으로 시작합니다. 새 운영 패키지나 큐는 추가하지 않습니다. 상세 API·배포 주의사항은 [LLM 용도별 설정 정의서](docs/LLM_Profile_Assignments_v0.1.md)를 참고하세요.

| Provider | 연결 주소 / 인증 | 분석 입력의 전송 범위 |
| --- | --- | --- |
| `vllm` | Internal Egress에 등록한 IP·포트의 Base URL, API Key 선택 | 등록된 내부 vLLM 대상 |
| `openai` | `https://api.openai.com/v1` 고정, API Key 필수, TLS 검증 필수 | OpenAI 외부 API; 프로필에 외부 전송 승인이 필요 |

OpenAI 선택 시 사용할 모델 ID를 직접 입력하세요. Chat Completions와 JSON Schema 구조화 출력을 지원하고 해당 API Key에 사용 권한이 있는 모델이어야 합니다. 모델별 추론 옵션을 임의로 강제하지 않으며, 모델 접근 가능 여부와 설정한 입력/출력 예산은 연결 테스트로 확인합니다. Azure OpenAI, 임의 OpenAI 호환 프록시, 다른 provider는 이번 범위에 포함하지 않습니다.

OpenAI 프로필은 `external_data_approved=true`를 명시적으로 확인해야 등록할 수 있습니다. 이 시스템은 payload·Cookie를 마스킹하지 않으므로 실제 분석 시 개인정보·인증 정보가 포함된 입력도 외부로 전송될 수 있습니다. 사내 반출 정책과 OpenAI 조직/프로젝트의 데이터 보관 설정을 확인한 뒤 승인하세요. `store=false`로 요청하지만 이것만으로 Zero Data Retention을 보장하지는 않습니다. [OpenAI 공식 데이터 관리 안내](https://developers.openai.com/api/docs/guides/your-data)를 참고하세요.

Provider 변경 시 이전 provider의 API Key를 자동 재사용하지 않습니다. OpenAI로 변경하려면 새 키와 외부 전송 승인을 명시해야 하고, 같은 provider를 수정하면서 키를 생략하면 기존 암호화 키를 유지합니다. Production·Test 지정 프로필은 수정할 수 없으며 신규/변경 프로필을 전체 검증한 뒤 수동 지정해야 합니다.

설정 화면에서 프로필을 등록한 뒤 다음 검증을 실행할 수 있습니다.

- 빠른 테스트: `/v1/models`, 기본 Chat Completion, 중첩 JSON Schema
- 전체 검증: 빠른 테스트 + system role + 설정 컨텍스트 근접 입력 + 제한된 동시 요청/p95

전체 검증 버튼은 테스트명을 입력하는 **취소 / 연결·기능 검증만 / 150건 판정 평가도 실행** 모달을 엽니다. 150건을 선택하면 기능 검증을 통과한 뒤 `waf-dummy-v1`(난이도별 50건)을 **선택한 후보 프로필**로 실행합니다. Production 프로필은 바꾸지 않습니다. 모델 호출은 Primary 150회에 조건부 Verifier·Retry·기능 검증 호출이 추가될 수 있습니다. OpenAI 선택 시 시간·비용·외부 전송 안내를 확인하세요. 모달 이후 모델/공급자 설정이 바뀌면 실행 전에 재확인을 요구합니다.

평가 문항은 `test` / `model_validation`으로 저장하며 일반 분석 worker가 아닌 model-test worker가 처리합니다. 진행률과 일치·미탐·과탐·보류 집계, 개별 분석 결과 링크를 제공합니다. 접수 시 프롬프트와 초기 참고 답안을 고정하고 중단 후에는 종료된 문항을 건너뛰어 재개합니다. 기술 검증 실패 시 150건은 호출하지 않습니다. 판정 평가의 **실행 실패**는 전체 검증을 실패 처리하지만, 답안 불일치율에 따른 자동 합격선은 없습니다. 기능 통과나 합성 답안 일치율을 실환경 정확도로 해석하지 마세요. [150건 검증 정의서](docs/Model_Validation_Dataset_v0.1.md)를 참고하세요.

프로필 테스트는 합성 문자열만 보내지만 OpenAI 테스트에도 API 사용료가 발생할 수 있습니다. 특히 전체 검증은 큰 입력과 복수 동시 요청을 사용합니다. 실제 분석·키 검증·과금은 모의 HTTP 테스트로 검증할 수 없으므로 별도로 확인해야 합니다.

vLLM 요청에는 `enable_thinking=false`를 적용합니다. **설정 → Internal Egress**에서 내부 IP·포트를 먼저 등록한 뒤 해당 주소로 vLLM 프로필을 추가하세요. RFC1918 IPv4와 ULA IPv6를 개별 주소로 등록할 수 있으며, 같은 IP라도 포트가 다르면 별도 항목입니다. 호스트명·CIDR·공인 IP·loopback·link-local은 허용하지 않습니다. 예: `10.0.0.10`/`8000` 등록 후 `http://10.0.0.10:8000/v1`, IPv6는 `http://[fd00::10]:8000/v1`.

허용 목록은 DB에 저장하며 초기에는 비어 있습니다. **기존 `WAF_VLLM_ALLOWED_TARGETS` 값은 더 이상 허용 기준으로 사용하지 않으며 자동으로 가져오지 않습니다.** 기존 `vllm.internal` 등 호스트명 프로필은 실제 내부 IP를 등록하고 프로필을 변경·재검증해야 합니다. 기존 프로필/검증/분석 이력을 삭제하거나 자동 변경하지 않습니다. 비활성화되지 않은 프로필이 사용하는 항목의 IP·포트 변경과 삭제는 거부하고 설명만 수정할 수 있습니다. 먼저 관련 프로필을 비활성화한 뒤 변경하세요. 비활성화된 프로필도 새 허용 목록을 통과해야 다시 활성화할 수 있습니다.

vLLM 프로필 등록·수정·활성화·테스트 등록·Production 승격과 worker에서 서버 검사를 수행합니다. 실제 vLLM HTTP 요청(Primary/Verifier/재시도/연결 테스트) 직전에도 DB를 다시 확인합니다. 이미 전송 중인 요청을 회수하는 기능은 아니며 변경 이후의 요청부터 차단합니다. 양쪽 provider의 실행과 연결 테스트는 HTTP redirect를 따르지 않고 환경 프록시를 무시합니다. 이 목록은 OpenAI의 공식 주소·승인 정책을 바꾸지 않으며 네트워크 방화벽을 대체하지 않습니다. OpenAI 요청은 `store=false`, `max_completion_tokens`를 사용하며 vLLM의 `chat_template_kwargs`를 보내지 않습니다. 구조화 출력은 [OpenAI 공식 규격](https://developers.openai.com/api/docs/guides/structured-outputs)에 맞춘 스키마를 사용하고 기존 Pydantic 판정·근거 검증을 그대로 수행합니다.

Internal Egress는 Alembic `0007_internal_egress`의 새 테이블 하나를 사용하며 새로운 운영 패키지 의존성은 없습니다. 관리자 세션으로만 목록을 관리하고 변경 작업을 감사 기록에 남깁니다. API와 배포 전환/롤백 주의사항은 [Internal Egress 정의서](docs/Internal_Egress_v0.1.md)를 참고하세요.

Provider 구분 도입은 Alembic `0004`에 포함되어 있습니다. 기존 `vllm_profiles` 테이블 이름과 `/api/v1/model-profiles` 경로는 호환성을 위해 유지합니다. 기존 분석 JSON·암호화 키·검증 이력은 변경하지 않습니다. 서비스 키 테이블(`0008`), 선택형 검증 메타데이터·분석 연결(`0009`), 이름 있는 테스트 실행(`0010`)에 이어 Test 용도 지정(`0011`)과 입력 스키마·필드 정보 버전(`0012`)이 추가됩니다. 새 운영 패키지 의존성은 없습니다. 배포 전 SQLite 일관성 백업을 만들고 API와 기존 worker를 중지한 다음 최신 마이그레이션(`0012_input_schemas`까지)과 필요한 vLLM 허용 목록 전환을 마친 뒤 같은 버전의 API·worker를 시작하세요. 마이그레이션은 키·샘플 분석을 자동 발급/접수하지 않습니다. 키 이력이나 분석 이력이 존재하는 스키마 downgrade는 데이터 보호를 위해 제한됩니다.

## 실제 Agent 활성화

1. vLLM은 설정 → Internal Egress에서 내부 IP·포트를 먼저 등록하고 프로필을 만듭니다. OpenAI는 기존 외부 전송 승인 절차로 등록합니다.
2. 전체 검증을 통과시킨 뒤 운영 API에 사용할 프로필은 Production, 일반 테스트에 사용할 프로필은 Test로 각각 지정합니다.
3. `.env`의 `WAF_AGENT_MODE=moduagent`를 설정하고 analysis worker를 재기동합니다.

```bash
docker compose up --build -d worker
```

vLLM 모델 호출은 `temperature=0`, `enable_thinking=false`를 사용하며 최대 출력 토큰은 해당 실행에서 선택한 프로필 값으로 실행됩니다. OpenAI에는 provider용 생성 옵션을 적용하고 추론 비활성화를 보장한 것으로 기록하지 않습니다. 네트워크/timeout/HTTP 408/5xx는 1회 재시도합니다. Pydantic/JSON Schema 출력 검증이 실패하면 검증 오류와 요구 스키마를 반영한 교정 지시로 1회 다시 요청합니다. Primary 교정도 실패하면 분석을 실패 처리하고, Verifier 교정이 실패하면 최종 판정을 `inconclusive`로 처리합니다. HTTPS 프로필은 인증서 검증을 끌 수 없습니다. 사설 CA가 필요하면 컨테이너 신뢰 저장소에 CA를 설치해야 합니다.

상세 정책은 `backend/app/agent/README.md`를 참고하세요.
